# Go2 导航全量日志与轨迹避障分析实施计划

创建日期：2026-07-23

安全复审：2026-07-23，已按“日志不得影响真机控制”原则修订

适用蓝图：`unitree-go2-relocalization-memory-agentic-deepseek`

目标：在不改变现有规划、控制、重定位和真机指令下发行为的前提下，为每一次导航建立一套可以离线回放、定量分析和追溯根因的完整数据链路。最终需要能够回答：

1. 规划路线是什么，机器人实际走了什么路线。
2. 实际轨迹与规划路线相差多少，是否出现蛇形、过冲、反复纠偏或异常重规划。
3. 墙或障碍物在原始点云、合并地图、二值 costmap、膨胀 costmap、规划路径和局部避障判断中分别是什么状态。
4. 机器人撞墙时，问题发生在传感器、坐标变换、costmap、规划、局部避障、速度复用、WebRTC 下发还是 Unitree 本体避障中的哪一层。
5. 网络延迟或数据陈旧是否让控制器持续纠正旧位置。

---

## 1. 实施原则

### 1.1 第一阶段只增加观测，不修改运动规则

本计划第一阶段禁止顺手修改以下参数或行为：

- `LocalPlanner._speed`
- `LocalPlanner._control_frequency`
- `PController` 的比例系数和最小线速度、最小转向量
- lookahead 距离
- goal tolerance
- 偏离路径后的重规划阈值
- costmap 的占用、膨胀和梯度算法
- Unitree 避障开关
- WebRTC DataChannel 可靠性和有序性

原因：如果采集日志时同时修改控制规则，就无法判断轨迹变化究竟来自原有问题还是新参数。

### 1.2 普通运行日志和全量导航追踪分开

现有 `<run-id>.jsonl` 继续用于：

- 模块启动、停止和异常。
- 新目标、状态切换、到达、取消和重规划。
- 一次导航的摘要指标。
- 追踪文件路径和 `navigation_session_id`。

高频和大体量数据写入独立的导航追踪目录，不直接塞进主 JSONL：

- 10 Hz 控制周期。
- 约 18 Hz Go2 里程计。
- 完整规划路径点。
- costmap 数组。
- 局部点云快照。
- WebRTC 发送队列状态。

现有主日志使用 10 MiB 轮转，并且多个 worker 可能同时写同一个文件。全量数据如果继续写主日志，会导致高频轮转、记录丢失和分析困难。

### 1.3 不增加中心高频订阅模块

复审后不采用“新增一个 `NavigationDiagnostics` 中心模块，订阅 odom、cmd_vel、costmap 和点云”的原方案。原因：

- 新订阅者会增加跨 worker 的序列化、IPC、调度和反序列化开销。
- costmap 和点云属于大消息，即使只用于日志，也可能与规划和感知争用 CPU、内存带宽和共享内存。
- 新模块还可能改变 worker 分配和蓝图启动顺序，使“只加日志”变成运行架构变化。
- 为了把 session ID 传到所有模块而改造 Twist、OccupancyGrid 等控制消息，会扩大行为风险。

改为每个现有生产模块在本 worker 内记录自己已经拥有的数据：

- `ReplanningAStarPlanner`：session、plan、planner-used odom、LocalPlanner 控制周期。
- `MovementManager`：nav cmd、teleop 状态和最终 cmd。
- `GO2Connection/UnitreeWebRTCConnection`：原始 odom 时间、最终 Twist、joystick 映射和 DataChannel 状态。
- `CostMapper`：输入地图来源、costmap 摘要和被请求的快照。
- `RelocalizationModule`：TF、merged map 和重定位版本。

每个 worker 只写自己的唯一文件，不允许多个进程写同一个高频追踪文件。离线分析器再按同一主机的 monotonic 时间和消息时间拼接。

### 1.4 非阻塞 TraceSink

所有在线追踪统一复用轻量 `TraceSink`：

- `trace_level=off` 时不创建线程、队列、文件或额外订阅，热路径只允许一次极低成本的布尔判断。
- 标量事件只构造小型 dataclass/dict，并使用 `put_nowait()` 进入有界队列。
- JSON 序列化、格式化、文件 flush、数组落盘全部在后台执行。
- 控制线程、里程计回调和 costmap 回调不得同步等待磁盘。
- 队列同时限制“事件数量”和“估算字节数”，不能只用 `4096` 个元素限制包含大数组的队列。
- 标量队列与 blob 队列分开；拥塞时先停 blob，再降采样标量。
- 不在控制线程执行全图 hash、压缩、PNG、Rerun、Matplotlib、全数组复制或 `fsync()`。
- 诊断代码的任何异常只能关闭对应 TraceSink，不得向规划器或连接回调继续抛出。
- 所有丢弃都记录聚合计数和时间范围，不能逐条 warning 刷屏。
- 模块停止时先执行原有零速度、躺下和连接清理，再关闭 TraceSink；writer join 最多等待 100ms，超时直接丢弃尾部诊断，不能为了补齐日志延迟真机安全停止。

### 1.5 真机运行硬约束

以下条件属于实现门禁，而不是优化项：

1. 不新增或改变任何控制消息字段、类型和传输。
2. 不改变现有 worker 数量、模块放置、蓝图连接关系和控制流订阅关系。
3. 不在 `cmd_vel`、odom、LocalPlanner 10 Hz 回调中进行磁盘 I/O。
4. 不在在线阶段生成图表、Markdown 报告或 `.rrd`。
5. 追踪关闭时，规划路径和输出 Twist 必须与改动前逐样本一致。
6. 追踪异常、磁盘满、目录不可写或队列满时，导航继续运行，日志自动降级。
7. 未通过 replay、simulation、静止真机和低速短路径性能门禁前，不允许在正常真机任务中启用 `full/forensic`。
8. 不得为了插入日志改变现有锁范围、publish/send 顺序、异常传播、重试次数或 stop/lie-down 顺序；时间戳可在动作前采集，但记录入队应放在原业务动作之后。

### 1.6 复审后的主要风险和处理

| 风险 | 原方案问题 | 修订后的处理 |
|---|---|---|
| 额外 IPC | 中心模块订阅 odom/cmd/costmap/点云 | 取消中心模块，各生产者在现有 worker 本地旁路记录 |
| worker 布局变化 | 给蓝图增加诊断 Module | 不修改蓝图模块集合和 worker 数量 |
| 控制线程阻塞 | 在线 JSON、磁盘和数组处理 | hot path 只 `put_nowait` 小记录，后台序列化和写盘 |
| CPU 抢占 | 在线算连续投影、曲率、全图统计 | 几何指标、全图统计、碰撞校验全部离线 |
| 压缩开销 | 在线写压缩 NPZ、PNG、RRD | 在线写受控 NPY/JSONL，压缩和报告全部离线 |
| 内存上涨 | 大数组进入普通事件队列 | scalar/blob 双队列，blob 最多 2 个且受字节预算 |
| 点云复制 | full 模式持续 ROI 采样 | 点云移到短时 forensic，最高 0.2 Hz，拥塞立即关闭 |
| 磁盘抖动 | 周期性保存完整 costmap | 仅本 worker 可观察的规划、重规划和异常事件保存，取消 5 秒全图轮询 |
| 错误传播 | writer 异常冒泡到导航回调 | TraceSink 自我关闭，任何异常不得离开诊断边界 |
| 在线报表 | 会话结束立即生成图表 | 进程停止后通过 CLI 离线生成 |
| 默认行为变化 | trace 默认 summary | 默认改为 off，关闭时不创建资源 |
| 结论过度 | odom 当物理真值、send 当执行 ACK | 明确 odom 只是估计，跨层关联带证据等级 |

### 1.7 对真机影响的明确结论

不能笼统承诺“增加日志一定零影响”。Python 后台线程仍可能争用 GIL，数组写盘仍可能争用内存带宽和磁盘，点云裁剪还会增加 CPU 负载。按本计划实施后的风险分级是：

- `off`：必须做到不创建 writer、队列、目录，不读取额外时钟，不构造记录对象；除一次启用状态判断外不增加运行链路。这是合入后的默认状态。
- `summary`：只有低频标量，预期风险低，但仍必须通过 replay 和静止真机 A/B。
- `full`：有 10 Hz 控制记录、全频 odom 和事件 costmap，存在 GIL、内存和写盘竞争风险；未通过 Gate 1 至 Gate 5 前不能用于正常真机任务。
- `forensic`：还要处理局部点云，是最高风险模式，只能在显式确认后短时启用，并按 Gate 6 从静止、低速到复现场景逐级测试。

因此安全保证不是来自“异步”两个字，而是来自默认关闭、热路径硬约束、有界队列、丢弃优先、自动降级和真机 A/B 门禁共同成立。任意一项未实现，计划都不能进入移动真机阶段。

## 2. 当前链路与主要缺口

### 2.1 当前导航链路

```text
SpatialMemory / NavigationSkill
  -> ReplanningAStarPlanner.set_goal()
  -> GlobalPlanner 生成 A* 路径
  -> smooth_resample_path() 生成 0.1m 间隔路径
  -> LocalPlanner 每 100ms 计算一次控制量
  -> PController 计算 linear.x / angular.z
  -> MovementManager 在导航和遥控之间做复用
  -> GO2Connection.move()
  -> WebRTC rt/wirelesscontroller
  -> Go2 执行模拟摇杆指令
```

地图和避障链路：

```text
实时 global_map
  + RelocalizationModule 的 world <- map
  -> merged_map
  -> CostMapper
  -> binary global_costmap
  -> NavigationMap 膨胀 + gradient/voronoi
  -> A* 全局规划
  -> PathClearance 检查前方 3m 路径掩码
```

### 2.2 当前已有信息

当前日志已经有：

- 新目标和 safe goal。
- `initial_rotation`、`path_following`、`final_rotation`、`arrived` 状态。
- 到达、取消、卡住、偏离路径和重规划事件。
- 重定位 fitness、耗时和 `world <- map` 矩阵。
- FreeAvoid 启用状态和 ACK。
- WebRTC 发送异常。

当前流中已经有：

- `path`
- `odom`
- `global_costmap`
- `navigation_costmap`，但目前受 `DEBUG_NAVIGATION` 环境变量控制。
- `nav_cmd_vel`
- MovementManager 输出的最终 `cmd_vel`

### 2.3 当前无法回答的问题

当前日志缺少：

- 每次导航的唯一 ID，无法稳定关联 Agent、规划、重定位、控制和连接层事件。
- 原始 A* 路径、平滑后路径以及每次重规划后的路径版本。
- 每周期机器人 odom 估计位姿和轨迹。
- 连续路径段上的横向误差，目前只在需要重规划时计算最近离散路径点距离。
- lookahead 点、目标航向、偏航误差和控制器中间值。
- 转向量是否被最小速度规则从小值抬高到 `0.2`。
- `nav_cmd_vel` 是否被 MovementManager 放行、覆盖或丢弃。
- 最终 Twist 到 Unitree 摇杆值的映射结果和发送时刻。
- Go2 原始里程计时间、Mac 接收时间、规划器使用时间之间的差值。
- costmap 的来源、版本、生成耗时、更新时间、统计值和完整快照。
- 路径前方 mask 中命中了哪些占用栅格。
- 原始点云中有墙但 costmap 没有墙时的中间证据。
- Unitree 自带 `obstacle_avoidance` 和 `free_avoid` 是否真正 ACK，以及是否可能实际介入。
- 自动生成的规划路线和 odom 估计轨迹叠加图。

## 3. 导航会话和统一时间线

### 3.1 `navigation_session_id`

每个外部新目标创建一个导航会话：

```text
nav-0001-20260723T154703.583
```

规则：

- `handle_goal_request()` 接收一次真实的新目标调用时创建新会话。
- 同一目标内部的 obstacle、stuck、deviation 重规划不创建新会话。
- 每次重新生成路径只递增 `plan_version`。
- 手动取消、遥控接管、目标替换、规划失败和正常到达都必须关闭会话。
- `cancel_goal(but_will_try_again=True)` 不能误关闭当前会话。
- 进程异常退出时，下次离线分析把未关闭会话标为 `aborted_process_exit`。

这里的 navigation session 只表示“一次 planner 目标生命周期”，不是 Agent 的完整任务。一次“寻找某个物体”可能因为历史点、沿途回看、分段目标或重新搜索而产生多个 navigation session。第一阶段不修改 `set_goal(PoseStamped)` 接口来传播高层 task ID；如果需要分析完整寻物任务，只能用 NavigationSkill 本地事件和时间窗做可选离线分组。

### 3.2 路径版本

每一次全局规划保存：

```text
navigation_session_id = nav-0001-...
plan_version = 1
plan_reason = initial_goal
```

后续版本示例：

```text
plan_version = 2
plan_reason = obstacle_found

plan_version = 3
plan_reason = veered_off_path
```

Planner 自己记录的每个控制周期必须带当前 `plan_version`。MovementManager、GO2Connection 等其他 worker 不修改 Twist 消息来携带该字段，而是在 run 级追踪文件中记录本地序号、时间和完整数值，由离线分析器按会话时间窗关联。

### 3.3 时间字段

所有高频记录至少包含：

- `wall_ts`：ISO 8601 墙上时间，供人工阅读和跨文件关联。
- `monotonic_ns`：本机单调时钟，用于精确计算间隔。
- `producer_seq`：每个生产者进程内单调递增序号。
- `session_event_seq`：仅 planner 会话事件使用的会话内序号。
- `source_ts`：传感器消息中的原始时间。
- `host_rx_ts`：Mac 收到消息的时间。
- `host_rx_monotonic_ns`：Mac 收到消息时的本机单调时间。
- `planner_used_ts`：该数据被规划器使用的时间。
- `command_generated_ts`：控制器生成指令的时间。
- `command_muxed_ts`：MovementManager 放行指令的时间。
- `command_send_ts`：WebRTC 调用 DataChannel send 的时间。

注意：

- 当前 Go2 `Odometry.from_msg()` 可以解析机器人 header 时间，但随后 `time_is_now()` 会把它覆盖。
- 第一阶段保留现有下游时间戳行为，避免改变运行逻辑。
- 在覆盖前写入当前 connection worker 的本地 TraceSink，同时保存原始 `source_ts` 和 `host_rx_ts`，不新增跨进程诊断流。
- 只有确认机器人时钟与 Mac 时钟属于同一时钟域后，才能把两者直接相减并称为“单向延迟”。
- 如果时钟域不一致，只分析到达间隔、抖动、数据年龄排序和控制链路本机耗时，不伪造网络 RTT。
- manifest 记录 Python monotonic clock implementation；只有同一主机进程间单调时钟可比较时，才使用 monotonic 时间拼接 worker 文件。

## 4. 追踪目录和文件格式

每次运行沿用现有 run 目录。高频文件按生产者拆分，避免跨进程争抢同一个文件：

```text
~/.local/state/dimos/logs/<run-id>/  # 或 RunRegistry 中配置的 log_dir
├── <run-id>.jsonl
└── navigation/
    ├── manifest.json
    ├── planner-<pid>.jsonl
    ├── mux-<pid>.jsonl
    ├── connection-<pid>.jsonl
    ├── costmapper-<pid>.jsonl
    ├── relocalization-<pid>.jsonl
    ├── plans/
    │   ├── nav-0001-plan-0001-raw.json
    │   └── nav-0001-plan-0001-smoothed.json
    ├── blobs/
    │   ├── costmap-000001.npy
    │   └── pointcloud-roi-000001.npy
    └── reports/
        └── nav-0001-20260723T154703.583/
            ├── summary.json
            ├── report.md
            ├── trace.rrd
            └── plots/
                ├── planned-vs-actual.png
                ├── cross-track-error.png
                ├── heading-and-command.png
                ├── latency-and-jitter.png
                ├── costmap-overlay.png
                └── obstacle-timeline.png
```

说明：

- 根目录必须从当前 run 的 RunRegistry `log_dir` 获取，不能在 worker 中另行猜测或硬编码；旧运行若只有 `main.jsonl`，离线工具保持兼容。
- 在线阶段只产生 manifest、生产者 JSONL、路径文件和受控 blob。
- `reports/` 只由停止运行后执行的 `dimos nav analyze` 生成。
- session 的开始/结束时间保存在 planner 文件中，分析器用该时间窗切分其他生产者文件。
- 不要求 GO2Connection 知道 Agent 的 navigation session ID。
- 跨 worker 的指令关联使用“本地序号 + monotonic 时间 + Twist 数值 + 顺序”尝试匹配，并输出匹配置信度；重复的相同 Twist 可能无法一一对应，不能伪装成精确 trace ID 或机器人端 ACK。
- `manifest.json` 只由运行入口写一次；每个 worker 把自己的启动参数写入各自生产者文件的 header 事件，禁止多个进程并发改写 manifest。

### 4.1 `manifest.json`

记录不可变运行条件：

- schema version。
- run ID；导航会话列表由离线分析器从 planner 文件重建，不写入不可变 manifest。
- blueprint 名称。
- Git branch、commit 和 dirty 状态。
- 启动命令，凭据和密钥必须脱敏。
- LocalSTA、Remote、4G 或 STA-T 连接方式。
- map file、map key、文件大小和修改时间；地图 hash 只由离线分析生成并写入 report，不能延迟导航启动，也不能回写不可变 manifest。
- 重定位配置。
- controller 类型和全部参数。
- speed、control frequency、lookahead、各 tolerance。
- robot width、rotation diameter。
- CostMapper 算法和参数。
- `obstacle_avoidance`、`free_avoid` 的启动请求值；动态响应和 ACK 写入 connection 生产者事件。
- motion mode、rage mode。
- trace level、采样率、磁盘预算。

### 4.2 JSONL 与数组文件职责

- JSONL 保存时间序列和标量，便于 `jq`、Python 和人工查看。
- 在线 blob 优先使用未压缩 `.npy`，避免 `np.savez_compressed()` 在真机运行期间持续占用 CPU。
- 离线分析阶段可以再压缩归档，不得在线压缩全图或点云。
- 每个数组文件必须在对应生产者 JSONL 中有索引、shape、dtype、时间和写入结果。
- 全量 hash 只在 blob 已经落盘后由后台或离线阶段计算，不能在 costmap 更新回调中计算。
- JSONL 后台定期 flush，但不周期性强制 `fsync()`；正常停止时只在 100ms 关闭预算内做 best-effort 最终 flush，宁可丢诊断尾部也不能拖延机器人停止。
- 图表、summary、Markdown 和 Rerun 文件只在运行停止后离线生成。
- 大数组不得在控制回调中复制后再入队。生产者只有在数据所有权稳定、不会被后续原地修改时才能把只读引用交给 blob 队列；无法保证所有权时直接放弃该快照并增加 drop 计数。
- 后台线程不等于零开销：JSON 序列化仍可能争用 Python GIL，NPY 写入仍会争用内存带宽和磁盘。因此热路径只创建固定数量的标量字段，不把 numpy 数组转换成 Python list，也不拼接大字符串。

## 5. 路径规划日志

### 5.1 目标信息

每次目标请求记录：

- 原始目标位置和四元数。
- frame ID。
- 当前机器人位姿。
- planner 真实入口：`rpc_set_goal`、`goal_request`、`target` 或 `clicked_point`。
- 原始目标到 safe goal 的距离。
- safe goal 搜索参数和最终结果。
- planner 本地当前 `costmap_id` 和数据年龄。

planner worker 不拥有 `world <- map`。目标事件只记录 planner 当时实际使用的数据；离线分析器再把该时刻与 Relocalization 文件中的最近 TF 关联，不给 planner 增加 TF 订阅。

planner 也无法仅凭 `PoseStamped` 判断 `rpc_set_goal` 背后是空间记忆、普通 Agent 导航还是其他技能。报告不得把入口来源扩写成未经记录的业务语义；高层来源缺失时标为 `UNKNOWN`。

### 5.2 A* 输入

记录：

- planner 类型和 Python/C++ 后端。
- 起点、目标点的世界坐标和栅格坐标。
- costmap frame、origin、resolution、width、height。
- gradient 策略：`voronoi` 或 `gradient`。
- robot width multiplier，当前代码为 `1.1`。
- occupied threshold。
- unknown penalty。
- 起点和目标点栅格值。
- planning start/end、耗时。
- 成功、失败和失败原因。

### 5.3 路径输出

分别保存：

- A* 原始栅格路径。
- 世界坐标原始路径。
- `smooth_resample_path()` 后的最终跟踪路径。
- 每个路径点的 `x/y/z/yaw/frame_id`。
- 路径点和基本元数据；总长度、曲率统计在离线阶段计算。
- 起终点和 safe goal 偏差。
- 每个路径点对应的 binary cost、inflated cost由离线分析器从同版本快照计算。
- 路径沿线最小障碍物间距由离线分析器计算。
- 路径 footprint 覆盖的 occupied、unknown、inflated 栅格数量由离线分析器计算。

离线分析阶段做只读一致性校验：

```text
路径是否穿过 binary occupied cell
路径膨胀 footprint 是否碰到 occupied cell
路径是否穿过超阈值 gradient cell
路径是否超出 costmap 边界
```

在线规划阶段只保存 raw/smoothed path 以及 A* 真正使用的 costmap 引用/快照请求，不执行额外 footprint 扫描、距离变换或碰撞判断。离线校验不参与路径接受或拒绝。

## 6. 实际轨迹与局部控制日志

这里的“实际轨迹”严格定义为：

```text
Go2 内部 odom 在当前 world/odom 坐标系下估计出的行进轨迹
```

它不是外部测量的物理真值。它适合回答“控制器是否按同一坐标系下的规划路径跟踪”，但不能单独证明机器人相对真实墙体的绝对位置没有漂移。

报告必须分别标注：

- `planned_path`：规划器使用的路径。
- `odom_estimated_trajectory`：Go2 里程计估计轨迹。
- `external_ground_truth`：可选，只有接入动捕、独立 SLAM、AprilTag 或其他外部定位时才存在。

没有外部真值时，报告不得把 odom 估计轨迹简称为 ground truth。

### 6.1 connection 文件中的 `odom` 事件

由 connection worker 在覆盖消息时间戳前，按实际到达频率记录原始里程计：

- source sequence。
- source timestamp。
- host receive wall/monotonic timestamp。
- frame ID。
- position `x/y/z`。
- quaternion 和 roll/pitch/yaw。
- 相邻样本位置增量、yaw 增量、推导线速度、横向速度和 yaw rate均在离线阶段计算。
- 数据间隔、抖动和丢帧估计。

离线推导速度必须保留未滤波值和滤波值，不能只保存滤波后的结果。

connection worker 不拥有 navigation session、plan 或 `world <- map` 版本，因此不得为填充这些字段新增订阅或修改 odom 消息。离线分析器根据 planner 会话时间窗、同机 monotonic 时间和消息顺序做关联，并给出关联置信度。

### 6.2 planner 文件中的 `control_cycle` 事件

LocalPlanner 每个 10 Hz 控制周期记录：

- planner state。
- 当前 plan version。
- current pose。
- planner 实际收到的 PoseStamped 时间、planner 回调接收时间和本周期使用时间。
- 最近离散路径点 index。
- lookahead point。
- distance to goal。
- 最终输出的完整 Twist。
- 本周期计算耗时。
- 实际 sleep 时间和控制周期抖动。

以下内容不在 10 Hz 控制线程重复计算，而由离线分析器根据“完整路径 + 当前 pose”计算：

- 连续路径段投影点和 segment index。
- along-track progress。
- unsigned/signed cross-track error。
- 实际轨迹曲率。
- desired yaw、robot yaw、yaw error，以及是否进入 rotate-then-drive 分支。
- 控制器比例项、clamp 前后 angular/linear 值和最小转向量触发标志。

控制周期只记录现有代码已经持有的 closest index、lookahead、current pose、state 和最终 Twist。离线分析器根据运行时配置重放 `PController` 公式，并把“重建 Twist”与“实际输出 Twist”对比；不为日志修改 `Controller.advance() -> Twist` 的签名或控制分支。LocalPlanner 必须先按原顺序发布 Twist，再把已采集的标量记录入队，TraceSink 失败不能阻止本周期指令发送。

原始 robot source timestamp 只存在于 connection worker。离线分析器可把 planner 使用的 PoseStamped 与 connection 侧 odom 按时间、位姿和顺序匹配；匹配不唯一时只能报告区间或 `UNKNOWN`，不能把估算值写成精确数据年龄。

### 6.3 最近路径点算法的诊断

当前 `PathDistancer.find_closest_point_index()` 在全部离散路径点中找最近点。日志需要同时记录：

- 当前代码真正使用的离散 `closest_index`。
- 分析器计算的连续路径投影 segment。
- index 相比上一周期是前进、停留还是后退。
- 是否出现跨越多个路径点的大幅跳变。

分析器不得用更精确的连续投影结果冒充控制器当时的真实输入。

### 6.4 MovementManager 速度复用

记录导航控制量进入和离开 MovementManager 的过程：

- 收到 `nav_cmd_vel` 的时间和数值。
- 当前是否处于 teleop cooldown。
- 指令是 `forwarded`、`suppressed_by_teleop` 还是 `scaled`。
- 最终输出 `cmd_vel`。
- 导航指令与最终指令的差值。
- 遥控接管和取消目标的精确时间。

这样可以区分：

```text
规划器算对了，但 MovementManager 没有放行
```

和：

```text
MovementManager 已经放行，但 Go2 没按预期运动
```

### 6.5 Go2 指令下发

在 `GO2Connection.move()` 和底层 `UnitreeWebRTCConnection.move()` 记录：

- connection worker 本地 command sequence。
- 收到最终 Twist 的时间。
- Twist 的 linear 和 angular 全量值。
- 映射后的 `{lx, ly, rx, ry}`。
- DataChannel ready state。
- 发送前后 `bufferedAmount`。
- 调用 `publish_without_callback()` 的开始、结束和耗时。
- 调用是否抛出异常。
- `cmd_vel_timeout` 定时器创建、取消和真正触发的时间。
- connection 层只记录收到零速度的事实；到达、取消、超时、异常或遥控释放等来源由 planner/mux 事件离线关联。

必须明确：

- `publish_without_callback()` 成功只代表指令交给本地 DataChannel。
- 当前没有 Go2 对每条摇杆指令的执行 ACK。
- 报告中不能把“本地发送成功”写成“机器人已经执行”。
- 不为传递 trace ID 而修改 Twist 类型或控制 topic。
- planner、mux、connection 三层序号彼此独立，离线分析按顺序、时间和数值匹配，并给出匹配置信度。
- `bufferedAmount` 只能在现有 WebRTC asyncio loop 内读取，不能从新线程跨线程访问 aiortc 对象。

## 7. 蛇形、画龙和过冲分析

### 7.1 基础轨迹指标

每个 plan version 和整次会话输出：

- planned path length。
- odom estimated trajectory length。
- 路径效率：`planned_length / odom_estimated_length`。
- 横向误差 mean、RMS、P50、P95、max。
- 航向误差 mean、P95、max。
- along-track progress 是否单调。
- 最近路径点 index 后退次数。
- 到达目标耗时。
- goal overshoot 距离。
- 停止后残余移动距离。

### 7.2 蛇形检测不能只看轨迹弯不弯

正常规划路径本身可能有弯道，因此蛇形检测必须基于“相对规划路径的 signed cross-track error”，不能直接根据世界坐标中的左右转弯次数判断。

记录和计算：

- signed cross-track error 的零交叉次数。
- 相邻正负峰值的幅度。
- 峰值间周期和沿路径距离。
- angular command 正负翻转次数。
- angular command 翻转与横向误差过零之间的时间差。
- 最小转向量 `0.2` 被触发的占比。
- 误差接近零时仍保持非零转向的持续时间。
- forward velocity 非零时的角速度翻转次数。
- 实际曲率与规划曲率之差。

第一版蛇形候选规则建议：

```text
连续路径跟踪阶段内
  signed cross-track error 至少出现 3 次交替峰值
  且峰峰值超过 0.15m
  且 angular command 同期反复换向
```

该阈值必须配置化，并在报告中同时显示原始数据。第一次真机测试后，需要用现场视频人工标注“有蛇形/无蛇形”，再校准阈值。

### 7.3 区分控制器蛇形与网络放大

判断顺序：

1. 横向误差过零后，控制器何时改变 angular 符号。
2. 控制器改变后，MovementManager 何时输出新指令。
3. MovementManager 输出后，DataChannel 何时 send。
4. send 后，实际 yaw rate 何时开始改变。

分类：

- 控制器本身很晚才换向：路径跟踪或控制器问题。
- 控制器及时换向，但 MovementManager 没放行：速度复用问题。
- 最终指令及时产生，但 DataChannel 队列持续增长：发送拥塞问题。
- 发送正常，但实际 yaw rate 很晚才改变：网络、Go2 运动控制或本体状态问题。
- 指令和 yaw rate 都及时，仍反复过冲：控制增益、最小转向量和机器人动力学问题。

## 8. costmap、地图与避障日志

### 8.1 CostMapper 输入来源

当前 CostMapper 优先使用 `merged_map`，没有时回退到 `global_map`。每次生成 costmap 必须记录：

- `map_source = merged_map | global_map`
- source map timestamp 和 CostMapper 进程内本地 sequence。
- source map frame ID。
- source pointcloud timestamp 和 host receive time。
- 点数。
- XYZ bounds 只在低频后台采样或 forensic 快照中计算。
- 地图在生成 costmap 时的数据年龄。
- occupancy 算法名称和全部参数。
- costmap 计算耗时。

必须区分以下数据语义：

- `raw_lidar`：Go2 本次传来的原始/解码后雷达帧。
- `global_map`：本次运行累计形成的地图。
- `merged_map`：累计地图与预加载地图经过重定位后的融合结果。
- `binary_costmap`：CostMapper 从 global/merged map 生成的二维占用结果。

累计地图中存在一堵墙，不等于当前这一帧 LiDAR 仍然看到了墙；反过来，原始 LiDAR 有墙但累计地图没有，才支持“建图/融合丢失”的判断。

### 8.2 二值 costmap

每次更新保存摘要：

- 生产者本地 sequence 和 producer-qualified `costmap_id`。
- `costmap_fingerprint`：timestamp、frame、shape、resolution 和 origin 的组合，只用于跨 worker 候选匹配。
- frame ID。
- timestamp。
- origin position、origin quaternion/yaw、resolution、width、height。
- hot path 只记录 shape、timestamp、origin、resolution 和本地 sequence。
- 机器人所在 cell/value、goal cell/value由已经同时持有 odom、goal 和 costmap 的 planner 在规划事件中采样，不能为此给 CostMapper 增加 odom/goal 订阅。
- occupied/free/unknown 全图统计最高 0.2 Hz 在后台计算。
- 路径沿线 occupied/unknown 数量由离线分析器对快照计算。
- costmap 的 `world_to_grid()` 当前假设 origin 无旋转；如果 origin yaw 非零，必须记录为高风险诊断事件。

完整二值 costmap 不需要每帧保存。`full` 模式只在以下条件保存未压缩 NPY：

- 首次规划。
- 每次重规划。
- obstacle、stuck、deviation 事件。

不再每 5 秒周期性保存完整全图。持续更新只记录标量摘要、`costmap_id` 和 `costmap_fingerprint`。`costmap_id` 由 producer ID 加本地 sequence 构成，只在该生产者文件内严格唯一；跨 worker 使用 fingerprint、monotonic 时间和内容元数据做带置信度关联，不修改 OccupancyGrid 消息格式，也不假装存在全局版本号。

上述“事件触发快照”只允许在已经持有该 costmap 的 planner/CostMapper 本地实现。若某个 worker 不知道 obstacle、stuck 或 TF 事件，则不为此增加跨 worker 信号，改由最近一次已有快照和时间窗做离线关联。路径碰撞本身是离线计算结果，不能反向触发已经过去时刻的在线快照。

所有快照请求都必须执行以下保护：

- 同一生产者中的相同 `costmap_id` 只落盘一次，后续 plan/event 只引用已有 blob。
- 除首次规划外，所有新快照都受 `navigation_trace_costmap_min_interval_sec` 限制；被限流时保留标量事件和 drop reason。
- 入队前只用 `array.nbytes` 做 O(1) 大小检查，单个 blob 超过上限直接丢弃，不能先复制再判断。
- 快速重规划不能形成 NPY 写盘风暴；诊断完整性让位于控制实时性，缺失快照在报告中明确标为 `INSUFFICIENT_EVIDENCE`。

### 8.3 膨胀和梯度 costmap

每次规划保存 A* 实际使用的 costmap 引用或受控快照，以及以下配置：

- 使用 `gradient` 还是 `voronoi`。
- inflation radius。
- gradient max distance，当前为 1.5m。
- robot width multiplier。

以下结果统一由离线分析器计算，不能在规划热路径上再次扫描数组：

- 路径点上的 cost 序列。
- 路径到 lethal occupied 的最小距离。
- 原始 A* 路径和 smoothed 路径分别与 occupied/inflated/unknown 的相交情况。

只有保存 A* 真正使用的 costmap，才能分析“地图明明有墙，规划路径为什么仍然穿墙”。

必须单独识别：

- `UNKNOWN_SPACE_TRAVERSED`：A* 因当前 unknown penalty 允许穿过未知区域。
- `RAW_PATH_COLLISION`：A* 原始路径已经穿过不可通行区域。
- `SMOOTHING_COLLISION`：原始路径安全，但平滑/重采样后切过墙角。

### 8.4 PathClearance 前方避障

当前 PathClearance 检查当前路径 index 之后约 3m 的路径 mask，并缓存 mask。需要把单一 bool 扩展为只读诊断报告：

- path lookup distance。
- 当前 pose index。
- 当前 `costmap_id`、timestamp 和 age。
- mask 是新计算还是复用缓存。
- 缓存基于的 path index。
- mask 实际覆盖的路径起止 index 和有效前视距离。
- `is_obstacle_ahead` 最终结果。

保留现有 `is_obstacle_ahead() -> bool` 行为，诊断报告不能改变判断结果。

性能约束：

- 10 Hz hot path 只记录现有 bool 判断、pose index、costmap timestamp 和 mask cache 状态。
- mask 覆盖栅格数、occupied/unknown/free 计数、最近 occupied 坐标和沿路径距离，只在 obstacle 为 true、规划/重规划事件或最高 1 Hz 采样时交给后台计算。
- 不得为了诊断在每个控制周期再次遍历 mask 或 costmap。

### 8.5 原始点云证据

为了判断“点云看得到墙，但 costmap 没看到”，点云数组归入风险更高的 `forensic` 模式，不放入普通 `full`：

- 每次 raw lidar、global map、merged map 更新只记录点数、frame、timestamp 和本地 sequence。
- bounds 需要扫描点集，只在 forensic 采样周期由后台计算，不能每帧执行。
- 在 GO2Connection 已有 lidar 回调中旁路采样 raw lidar，不增加第二个点云订阅。
- 在地图 worker 已有数据处理中采样 global/merged map，不把完整地图发送给新的诊断模块。
- 机器人周围可配置 ROI，建议默认 10m x 10m，每一类点云最高 0.2 Hz 保存降采样 NPY。
- 保存快照使用的 voxel size 和裁剪范围。

安全要求：

- 不新增中心模块或第二个订阅者接收完整点云。
- ROI、降采样和数组写盘只能在已经持有该点云的现有生产者 worker 中异步进行；raw lidar 属于 connection worker，global/merged map 属于现有地图/重定位 worker。
- blob 队列只保留最新候选，旧候选直接丢弃。
- 不持续保存完整全局点云。
- `forensic` 仅用于短时复现，必须先通过 full 模式性能门禁。
- 不实现跨 worker 的“事故瞬间点云触发”。forensic 依靠低频滚动 ROI 提供最近证据；如果 0.2 Hz 仍无法覆盖现场，先评估录像和传感器录包方案，不能直接提高在线点云日志频率。

### 8.6 重定位与 TF

每次重定位尝试和成功发布记录：

- mode：global、cached start 或 subsequent fast ICP。
- 输入点数、fitness、耗时。
- `T_map_world` 和 `T_world_map`。
- transform version。
- 相比上一版本的平移和 yaw 变化。
- transform 发布时机器人是否正在导航。
- Relocalization 进程内的 merged map sequence、timestamp 和发布时刻。

离线分析器按 timestamp、monotonic 时间和生产者 sequence 建立关联链：

```text
tf_version 3 at t0
  ~> merged_map local_seq 18 at t1
  ~> costmap local_seq 41 at t2
  ~> active_plan_version 1 at t3
```

`~>` 表示时间关联而不是消息中携带的严格因果 ID。报告必须给出时间差和置信度；证据不足时输出 `UNKNOWN`。这样既能判断“路径可能基于旧地图、局部避障已经看到新地图”，也不会为了构造全局版本链修改业务消息。

## 9. Unitree 本体状态和两套避障

### 9.1 启动状态

manifest 只记录配置请求值。机器人启动后的实际结果写入 connection 生产者文件的 `robot_startup_state` 事件：

- `obstacle_avoidance` 请求值、API 响应码和 ACK。
- `free_avoid` 请求值、API 响应码和 ACK。
- motion mode。
- BalanceStand 是否成功。
- Rage mode。
- WebRTC connection method 和机器人报告的 network status。

当前 `set_obstacle_avoidance()` 没有把详细响应保留下来。计划中在方法内部缓存并记录脱敏后的响应状态，但不改变现有公开方法签名和上层调用返回值，避免日志改造影响业务接口。请求异常时也只能按现有业务规则处理，TraceSink 不得吞掉、改写或重试机器人 API。

### 9.2 LowState 摘要

LowState 不需要全量高频写入。建议 2 Hz 保存：

- IMU roll/pitch/yaw。
- foot force。
- 电池 SOC、电压、电流。
- 电机最大温度。
- motor lost 的最大值和异常电机 index。

用途：

- 判断机器人是否打滑、被墙顶住或发生异常姿态。
- 判断规划器持续前进指令时，本体是否实际上没有移动。

### 9.3 推断本体避障是否介入

目前没有每条运动指令对应的本体避障执行 ACK。第一版只能通过证据组合推断：

```text
DimOS 持续下发前进
  + odom 线速度接近 0
  + 前方局部点云存在障碍
  + obstacle_avoidance / FreeAvoid 已 ACK
  = 本体避障可能介入
```

报告中必须使用“可能介入”，不能写成确定结论。

## 10. 避障根因矩阵

离线报告按下面的顺序逐层判断：

| 层级 | 要检查的证据 | 可能结论 |
|---|---|---|
| 原始感知 | 局部点云中是否有墙，点云是否新鲜 | 雷达盲区、点云丢失、数据陈旧 |
| 坐标变换 | 点云和墙在 world/map 中是否正确对齐 | TF 方向、重定位漂移或版本不一致 |
| 地图融合 | 墙是否进入 merged_map | merge 时机、裁剪或地图源选择问题 |
| CostMapper | 墙是否变成 occupied cell | 高度阈值、过滤参数或 costmap 生成问题 |
| Inflation | occupied 周围是否形成足够安全区 | robot width 或 inflation 问题 |
| A* | 规划路径 footprint 是否穿 occupied/inflated cell | A* cost、坐标转换或路径平滑问题 |
| PathClearance | 前方 3m mask 是否命中墙 | mask、pose index、缓存或地图版本问题 |
| Planner stop | 命中后是否产生 stop/replan | LocalPlanner 状态机问题 |
| MovementManager | 零速度/新指令是否被放行 | teleop mux 或指令覆盖问题 |
| WebRTC | 指令是否及时入队，bufferedAmount 是否增长 | 发送拥塞或连接抖动 |
| Go2 本体 | 指令与实际速度是否一致，本体避障是否 ACK | 本体控制、运动模式或避障状态问题 |

每个自动分类必须带证据等级：

- `OBSERVED`：由同一层原始记录直接证明。
- `CORRELATED`：通过时间、数值和顺序高置信度关联。
- `INFERRED`：根据多层现象推断，但缺少机器人端 ACK 或外部 ground truth。
- `UNKNOWN`：证据不足。

报告不得只输出一个看似确定的根因名称而不列证据和置信度。

### 10.1 “墙在点云里但路径穿墙”的自动分类

报告至少给出以下分类之一：

- `SENSOR_MISSING`：事件窗口内局部点云没有墙。
- `POINTCLOUD_STALE`：点云存在但时间过旧。
- `TF_MISALIGNED`：点云有墙，但变换到 costmap 后位置明显错位。
- `MERGE_MISSING_OBSTACLE`：局部/预地图有墙，merged map 没有。
- `COSTMAP_CLASSIFICATION_MISS`：merged map 有墙，binary costmap 不是 occupied。
- `INFLATION_INSUFFICIENT`：墙 occupied，但安全膨胀不足。
- `UNKNOWN_SPACE_TRAVERSED`：A* 按当前 unknown penalty 穿过未知区域。
- `RAW_PATH_COLLISION`：A* 原始路径已经穿过 occupied/inflated cell。
- `SMOOTHING_COLLISION`：原始路径安全，但平滑/重采样路径切入 occupied/inflated cell。
- `PATH_CLEARANCE_MISS`：路径前方有 occupied，但局部检查返回 false。
- `STOP_NOT_PROPAGATED`：局部规划器要求停止，但最终 cmd_vel 仍前进。
- `CONTROL_TRANSPORT_DELAY`：零速度或转向指令在发送链路明显积压。
- `ROBOT_EXECUTION_MISMATCH`：发送链路正常，但实际运动与指令明显不一致。
- `INSUFFICIENT_EVIDENCE`：缺少必要数据，不强行下结论。

## 11. 网络和数据新鲜度分析

### 11.1 可以直接测量的内容

- odom 到达频率。
- odom inter-arrival jitter。
- source timestamp 是否连续。
- host receive 到 planner use 的本机排队时间。
- controller 计算耗时。
- controller 到 MovementManager 的耗时。
- MovementManager 到 WebRTC send 的耗时。
- DataChannel `bufferedAmount`。
- DataChannel ready state。
- WebRTC connection/ICE/DTLS 状态。
- RTP stats 中可获得的 RTT，只能标为“共享链路代理指标”，不能冒充每条控制指令 RTT。

WebRTC stats 最多 1 Hz 在已有 asyncio loop 的低优先级后台任务中采样。若采样造成事件循环延迟或底层库不稳定，则关闭该项，只保留 bufferedAmount、odom jitter 和本机阶段耗时。

### 11.2 当前不能直接测量的内容

- 每条无线摇杆指令到达 Go2 的精确时间。
- Go2 开始执行每条指令的精确时间。
- 没有时钟同步时的单向网络延迟。

分析器需要用以下方式估算响应：

```text
最终 angular command 换向时刻
  -> 实际 odom yaw rate 换向时刻
  = command-to-motion response lag
```

该值包含：

- 下行网络延迟。
- Go2 内部处理延迟。
- 电机和机身动力学响应。
- 上行 odom 延迟。

报告必须叫“闭环响应延迟”，不能直接叫“网络延迟”。

## 12. 采样率和数据量控制

新增全局配置：

```python
navigation_trace_level: Literal["off", "summary", "full", "forensic"] = "off"
navigation_trace_costmap_min_interval_sec: float = 5.0
navigation_trace_roi_interval_sec: float = 5.0
navigation_trace_lowstate_hz: float = 2.0
navigation_trace_webrtc_stats_hz: float = 0.0
navigation_trace_scalar_queue_items: int = 2048
navigation_trace_blob_queue_items: int = 2
navigation_trace_scalar_max_bytes_per_producer: int = 67_108_864
navigation_trace_blob_max_bytes_per_producer: int = 134_217_728
navigation_trace_blob_max_item_bytes: int = 33_554_432
navigation_trace_min_free_disk_bytes: int = 5_368_709_120
navigation_trace_forensic_ack: bool = False
```

模式定义：

### `off`

- 保留现有日志。
- 不创建导航追踪目录。
- 不启动 writer、不创建队列、不增加流订阅。
- 这是默认值，确保现有真机运行不会因为合入诊断代码自动增加负载。

### `summary`

- 会话、路径、状态、重规划和终态事件。
- 1 Hz odom 估计轨迹。
- 1 Hz 控制摘要。
- costmap ID、时间和 shape 等标量元数据，不保存 costmap NPY。
- 不保存周期性点云。

### `full`

- 全频率 odom。
- 每个 10 Hz 控制周期。
- nav cmd、mux 后 cmd 和 WebRTC send。
- costmap 摘要和事件触发快照。
- 2 Hz LowState。
- 网络队列和时间链。
- 不保存点云数组。

### `forensic`

- 包含 `full` 的全部内容。
- 低频滚动局部点云 ROI。
- 只用于短时复现墙体/避障问题，不用于普通长时间运行。
- `navigation_trace_forensic_ack=false` 时拒绝启用，并输出明确说明；该确认只表示操作者知道风险，不能替代专项性能门禁。

一般轨迹和蛇形分析使用 `full`；需要判断“点云有墙但 costmap 没墙”时，使用短时 `forensic`。

性能目标：

- 标量 `TraceSink.record()` P99 同步耗时小于 0.5ms，最大值小于 2ms。
- trace 开启后，LocalPlanner 控制周期 P99 相比 trace off 基线增加不超过 1ms。
- trace 开启前后 `nav_cmd_vel` 发布频率差异不超过 1%，不得出现由追踪引入的 200ms watchdog 零速。
- full 相比 trace off 的 odom、global_map 和 costmap 有效处理频率下降均不超过 1%。
- full 相比 trace off 的全部 DimOS worker 总 CPU 中位数增加不超过 5 个百分点、P95 增加不超过 10 个百分点；若机器本身已高负载，则以不造成控制周期或消息频率越线为更高优先级。
- full 稳态总 RSS 增量不超过 128 MiB，且 30 分钟测试中无持续正斜率；summary 稳态总 RSS 增量不超过 32 MiB。
- Connection asyncio loop 的调度延迟 P99 增量不超过 2ms；该测量使用轻量 loop heartbeat，不能依赖默认关闭的 WebRTC `getStats()`。
- 不允许诊断写盘、压缩、全图 hash 或报告生成进入 100ms 控制周期。
- 30 分钟 `full` 追踪以总量不超过 256 MiB 为验收目标，但不能把它误写成未经实测的保证。
- 各 worker 不共享在线计数器，分别执行本地硬预算；剩余磁盘低于 5 GiB、达到本地预算或 blob 队列拥塞时，立即停止该生产者的大文件快照。
- scalar 队列异常拥塞时从 `full` 自动降为 `summary`，仍拥塞则降为 `off`。
- 自动降级只关闭诊断，不取消导航、不发送运动指令、不改变规划状态。
- 每个生产者文件记录 `requested_trace_level`、`effective_trace_level`、实际文件大小、事件数和丢弃数；run 总量由离线分析器汇总。
- `getStats()` 默认关闭，只有专项网络测试才显式设置低于等于 1 Hz；普通 full 只读取现有 asyncio loop 可安全访问的轻量状态。

### 12.1 运行时降级顺序

```text
forensic
  -> 停止点云 blob，退化为 full
  -> 停止 costmap blob，保留标量 full
  -> 降采样为 summary
  -> 完全 off
```

触发条件：

- blob/scalar 队列超过水位。
- TraceSink 单次调用超时。
- 写盘异常。
- 剩余磁盘不足。
- writer 心跳停止。
- 在线观测到控制周期 overrun 明显增加。

降级事件只允许聚合记录一次，不能在故障中继续刷日志。

降级是 producer-local 的，不增加新的跨 worker 控制通道。只有 planner TraceSink 可以根据本 worker 控制周期 overrun 降级；其他生产者只根据自身队列、写盘和磁盘状态降级。离线报告必须标出各生产者实际生效的级别和缺失时间窗。

## 16. 测试计划

### 16.1 数据模型和写盘单测

- session ID 唯一且单调。
- replanning 只递增 plan version，不创建新 session。
- arrived、cancelled、failed、superseded 正确关闭会话。
- 进程异常留下的会话可被识别。
- JSONL 每行可独立解析。
- NPY 索引、shape 和 dtype 一致。
- 写盘队列满时按优先级丢弃，不阻塞调用者。
- 敏感配置正确脱敏。
- trace off 时不创建 writer、线程、目录或额外订阅。
- trace off 的热路径不读取时钟、不构造 dict/dataclass、不复制数组，只做启用状态判断。
- TraceSink 异常不会从控制/里程计/costmap 回调抛出。
- 达到磁盘、字节和队列预算后按规定降级。
- 每个生产者可以独立降级，离线报告能正确识别混合 trace level 和数据缺口。
- 大数组在入队前用 `nbytes` 拒绝超限项，测试确认 hot path 没有隐式 `copy()`、`tolist()` 或压缩。
- TraceSink shutdown 超时不会延迟原有零速度、躺下和连接停止。

### 16.2 路径指标单测

构造：

- 完全贴合直线的轨迹。
- 与路径平行偏移 0.2m 的轨迹。
- 正弦蛇形轨迹。
- 正常弯道但不蛇形的轨迹。
- 到达后过冲再返回的轨迹。
- 最近离散点 index 跳回的轨迹。

验证：

- 连续横向误差正确。
- 误差正负号正确。
- 正常弯道不被误报为蛇形。
- 正弦轨迹被识别并输出正确幅度、周期和翻转次数。

### 16.3 控制链路单测

- Controller 原始 Twist 与新增日志完全一致。
- LocalPlanner、MovementManager 和 Connection 的原 publish/send 调用顺序、锁范围和异常传播不变。
- 注入 TraceSink 抛异常时，本周期 Twist 仍已按原路径发布/发送。
- 最小转向量触发标志正确。
- MovementManager 放行导航时 pre/post cmd 相同。
- 遥控接管时导航指令被标记为 suppressed。
- Twist 到 `{lx, ly, rx, ry}` 的映射正确。
- zero cmd 来源和 timeout 事件正确。
- 新增诊断不改变原有控制输出。
- deterministic replay 中 trace off/on 的 Path 和 Twist 数值序列完全一致。
- 不修改 Twist 消息类型、字段、topic 和 transport。

### 16.4 costmap 和避障单测

构造一堵已知墙：

- 点云中有墙。
- binary costmap 中对应 occupied。
- inflation 后形成安全区。
- A* 路径绕墙。
- PathClearance mask 能命中墙。

再分别注入故障：

- 删除点云墙点。
- 设置错误 TF。
- CostMapper 过滤掉墙。
- 禁用/缩小 inflation。
- 让路径平滑后穿墙。
- 让路径经过 unknown space。
- 设置非零 costmap origin yaw，验证报告指出当前 world/grid 转换假设风险。
- 使用过期 costmap。
- 复用错误 PathClearance mask。

验证离线报告能把问题归到正确层级。

### 16.5 网络和时间测试

在 replay/simulation 中注入：

- 固定 100ms、300ms、500ms odom 延迟。
- command 发送延迟。
- 抖动。
- 丢包后的发送队列增长。
- odom timestamp 不同 clock domain。

验证：

- 不把不同时钟域直接相减。
- 能区分 planner queue、send queue 和闭环响应 lag。
- 延迟情况下 angular 换向与实际 yaw rate 换向时间可正确关联。
- WebRTC `getStats()` 关闭和 1 Hz 开启时分别做事件循环延迟 A/B；若有可测退化则保持默认关闭。

### 16.6 重定位测试

- 导航前完成重定位。
- 导航中第一次重定位成功。
- 导航中 TF 小幅更新。
- 导航中 TF 大幅异常更新。
- merged map 和 costmap 更新顺序不同。

验证 plan、map、costmap 和 TF 能按时间窗关联，并输出时间差和置信度；故意制造歧义时必须输出 `UNKNOWN`，不能伪造精确版本链。

### 16.8 性能与真机安全门禁

必须按顺序通过，不能跳级：

#### Gate 0：静态和单元测试

- trace off 不创建运行资源。
- 诊断异常全部被隔离。
- 确认没有新增蓝图模块、worker 和大消息订阅。

#### Gate 1：deterministic replay A/B

使用同一录制输入分别运行：

```text
A = 原基线或 trace off
B = trace full
```

比较：

- Path 数值和顺序。
- Twist 数值和顺序。
- 控制周期频率和 jitter。
- CPU、RSS、磁盘写入速率。
- odom 和 costmap 消息处理频率。
- Connection asyncio loop heartbeat delay。

必须满足：

- Path/Twist 数值序列一致。
- 控制周期 P99 增量不超过 1ms。
- odom、global_map、costmap 和 nav_cmd_vel 有效频率差异不超过 1%。
- CPU、RSS 和 event-loop delay 满足第 12 节硬阈值。
- 没有新增控制 watchdog。

#### Gate 2：simulation 长时间测试

- full 连续 60 分钟。
- 队列满、磁盘不可写、writer 抛异常和空间不足故障注入。
- 导航在诊断自动降级后继续完成。

#### Gate 3：真机静止测试

- Go2 站立但不导航，分别运行 off、summary、full。
- 每档至少 10 分钟。
- 观察 CPU、内存、odom 频率、WebRTC 状态和异常零速。

#### Gate 4：低速短路径

- 空旷区域 2m 直线。
- trace off 与 full 各重复至少 3 次。
- 同步录像。
- 比较耗时、路径、控制周期和运动体感。

#### Gate 5：正常路线

- 5m 以上直线和一个 90 度转角。
- full 连续运行至少 30 分钟。
- 确认无新增停顿、蛇形、watchdog 或资源持续增长。

#### Gate 6：forensic 墙体测试

- 仅在 full 已通过后启用。
- 先静止，再低速短路径，最后才允许墙体复现场景。
- 单次取证时间和 blob 数量必须受限。

任何 Gate 不通过，先回退为 trace off 并修复诊断系统，不能通过调低导航速度来掩盖日志开销。

## 17. 真机验收场景

### 场景 A：空旷直线路径

- 规划 5m 以上直线路径。
- 不人工干预。
- 同步录像。

验收：

- 规划和 odom 估计轨迹可叠加。
- 能输出横向误差和 angular 翻转。
- 视频观察结果与蛇形检测基本一致。

### 场景 B：包含拐角的正常路线

- 选择至少一个 90 度转角。
- 验证正常转弯不会被误判为蛇形。

### 场景 C：墙体绕行

- 选择地图中清晰存在的墙。
- 目标点在墙体另一侧，但存在可行绕路。

验收：

- 点云、binary costmap、inflated costmap 和路径叠加可见。
- 报告显示路径未穿过墙体 footprint。
- 真机绕墙。

### 场景 D：复现路径穿墙

如果再次发生撞墙或穿墙：

- 不立即清理 run 目录。
- 保存现场视频和 run ID。
- 执行完整离线分析。

验收：

- 报告至少定位到感知、TF、地图融合、costmap、规划、PathClearance、指令下发或本体执行中的一层。
- 数据不足时明确输出 `INSUFFICIENT_EVIDENCE` 和缺失字段。

### 场景 E：Remote 网络抖动

- 相同路线分别使用 LocalSTA 和 Remote。
- 每种方式至少重复 3 次。

对比：

- odom 频率和 jitter。
- DataChannel bufferedAmount。
- 闭环响应 lag。
- 横向误差和蛇形幅度。
- 实际路径长度和耗时。

不能只凭单次体感得出“Remote 一定更差”或“LocalSTA 一定更好”。

## 18. 最终验收标准

本计划完成后必须满足：

1. 任意一次导航都能通过 run ID 和 navigation session ID 定位到对应数据；发生降级或丢弃时能准确列出缺失生产者和时间窗。
2. 能还原每个 plan version 的原始路径和平滑路径。
3. 能还原机器人 odom 估计轨迹和每个 10 Hz 控制周期，并明确它不是外部 ground truth。
4. 能叠加规划路径、odom 估计轨迹、binary costmap、inflated costmap 和局部点云。
5. 能计算横向误差 RMS/P95/max、odom 估计路径长度、过冲和 angular 翻转。
6. 能给出蛇形候选区间、幅度、周期和关联控制指令。
7. 能确认每次重规划的时间、原因、旧路径和新路径。
8. 证据齐全时能追溯障碍物从点云到 costmap 再到 PathClearance 的链路；证据缺失时输出 `INSUFFICIENT_EVIDENCE`，不伪造完整链路。
9. 能记录两套 Unitree 避障开关的请求值、响应状态和 ACK 是否存在。
10. 能区分 planner 输出、MovementManager 输出和 WebRTC send。
11. 能记录原始 odom 时间和主机接收时间，不再丢失时间来源。
12. 报告不把 send 成功误写成机器人执行成功。
13. trace off 不启动新线程、队列、文件或订阅，Path/Twist 与改动前一致。
14. 日志不包含账号、密码、token、API key 或 AES key。
15. full/forensic 的同步记录满足性能门限，超过预算时只降级诊断，不改变导航。
16. replay A/B 满足控制周期 P99 增量不超过 1ms，真机完成分级性能门禁。
17. 30 分钟 full trace 在磁盘预算内，并报告所有丢弃记录。

## 19. 实施顺序

### 阶段 1：会话、schema 和 worker 本地 TraceSink

- 增加配置开关。
- 定义诊断事件。
- 建立 navigation session 和 plan version。
- 建立每个生产者唯一文件和惰性 writer。
- 完成崩溃恢复和 drop accounting。
- 首先验证 trace off 零资源和异常隔离。

### 阶段 2：规划路径和 odom 估计轨迹

- 保存 raw/smoothed path。
- 保存全频率 odom。
- 增加连续路径投影和横向误差分析。
- 完成 replay A/B，确保 Path/Twist 不变。

### 阶段 3：局部控制和指令下发

- 保存 controller 输入和最终 Twist，离线重建中间值。
- 记录 MovementManager pre/post mux。
- 记录 Twist 到 joystick 映射和 DataChannel 队列。
- 完成蛇形、过冲和闭环响应分析。

### 阶段 4：地图、costmap 和避障

- 增加 CostMapper provenance、生产者本地 sequence/`costmap_id` 和候选匹配 fingerprint。
- 只在本 worker 可观察的规划/重规划/异常事件保存 binary/navigation costmap。
- 增加 PathClearance 诊断报告。
- 完成避障根因矩阵。

### 阶段 5：重定位和本体状态

- 离线关联 TF、merged map、costmap 和 plan version，并保留时间差、置信度和 `UNKNOWN`。
- 保存避障 ACK、motion mode、LowState 摘要。
- 增加本体避障介入的谨慎推断。
- full 通过门禁后，再增加 forensic 局部点云 ROI。

### 阶段 6：报告、Rerun 和真机验收

- 增加 `dimos nav analyze`。
- 只在进程停止后离线生成 summary、Markdown、PNG 和 Rerun。
- 完成 synthetic、replay、LocalSTA、Remote 和真机墙体场景测试。

只有阶段 1 至阶段 6 全部完成，才能认为“全量导航分析日志”真正可用。只增加几条 `logger.info()` 不能满足本计划目标。

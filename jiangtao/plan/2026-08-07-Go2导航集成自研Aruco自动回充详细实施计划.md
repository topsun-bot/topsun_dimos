## 0. 本计划最终要实现什么

新增一个可运行蓝图：

```text
unitree-go2-auto-recharge
```

该蓝图是在现有 `unitree_go2` 导航栈上增加自动回充模块，不再把回充作为与导航割裂的独立脚本。正常情况下机器人仍执行现有导航任务；只要前置相机稳定识别到官方回充二维码，且计算出的充电桩预停靠位在当前地图和控制能力内可达，自动回充模块就接管任务：

```text
正常导航
  -> 发现并稳定确认二维码
  -> 计算充电桩中心线、预停靠点和最终停靠点
  -> 检查目标和路径是否可达
  -> 取消原导航目标
  -> 必要时使用导航走到二维码正前方的预停靠点
  -> 切换为二维码视觉伺服独占速度控制
  -> 小步转向、前进、停下观察
  -> 到达最终位置并稳定
  -> 趴下
  -> 验证充电
  -> 成功结束；失败则站起、主动退回观察窗口并重试
```

第一版必须遵守以下决定：

1. 全流程支持当前 4G Remote WebRTC，不设置“4G 下不执行精对接”的限制。
2. 回充与导航共用一个最终 `cmd_vel` 出口，任何时刻只有一个控制源能输出非零速度。
3. 最终视觉伺服优先使用横移。
4. 最终视觉伺服的偏航误差只使用二维码中心相对相机光轴的方位角：

   ```text
   bearing = atan2(x_C, z_C)
   ```

5. 小于机械死区的微小角度不继续追，不因为 2°、3° 的误差让狗反复左右抖动。
6. 侧面或斜向看到二维码时，不允许沿斜线直接冲向二维码。先走到二维码正前方、中心线上的预停靠点，再进入最终视觉伺服。
7. 近场过冲、二维码丢失或位姿不稳定时，先停止，再沿来路后退到明确的可观测窗口；不在充电桩近场盲目连续旋转。
8. 二维码丢失时禁止趴下；只有位置、角度、稳定性、低状态新鲜度全部通过才允许趴下。
9. 官方 `/aruco_state` 只会由官方机载 `aruco_recharge` 服务发布。自研程序不运行该服务时，不能等待它替自研流程发布 `aruco_arrive/aruco_success`；自研模块应发布自己的状态，并通过本机可读的 BMS/lowstate 验证充电。

## 1. 已确认事实与不能混用的量

### 1.1 官方二维码

使用：

```text
字典：DICT_APRILTAG_36h11
ID：0
黑色编码区域边长：0.1075 m
黑色区域之外：保留约 1 cm 白边
```

当前本机代码已经使用上述字典和尺寸。旧计划中出现过的 `DICT_4X4_50` 不再使用。

### 1.2 官方安装几何

官方配置给出的平面纵向关系是：

```text
二维码中心到充电板中心：0.70 m
二维码中心到最终相机投影：0.35 m
最终相机投影到机器人中心：0.35 m
```

所以：

```text
0.35 + 0.35 = 0.70 m
```

当相机在二维码正前方、相机到二维码的平面纵向距离为 `0.35 m` 时，机器人中心正好位于充电板中心上方。

### 1.3 两个距离概念必须分开

代码中的 PnP 深度：

```text
z_C = 二维码中心在相机光学坐标系中的前向深度
```

最终几何目标：

```text
target_camera_z_m = 0.35 m
```

官方黑盒 CSV 测试里观察到的 `0.62–0.80 m`，主要用来说明“退到这个附近后，官方程序容易重新稳定观察和做小碎步修正”。该 CSV 的距离列不应在没有同帧对照标定的情况下，被直接声明为与本机 OpenCV 的 `z_C` 完全同一个量。

因此第一版采用下面的工程策略：

```text
最终趴下目标：本机 PnP z_C ≈ 0.35 m
恢复观察目标：本机 PnP z_C ≈ 0.75 m
恢复稳定带：本机 PnP z_C ∈ [0.70, 0.85] m
```

`0.75 m` 是恢复和重新对准的位置，不是最终趴下位置。真机日志必须同时记录原始 `tvec`、角点、重投影误差和 odom 位移；如果后续数据证明本机 PnP 的最佳恢复窗口不同，只修改配置，不修改状态机结构。

### 1.4 4G 控制量不是严格 SI 速度

当前 WebRTC Remote 路径下，`Twist` 会映射为无线遥控器摇杆比例：

```text
linear.x  -> ly
linear.y  -> -lx
angular.z -> -rx
```

当前真机已知死区约为：

```text
|linear.x| < 0.10：Go2 可能不前后移动
|angular.z| < 0.20：Go2 可能不旋转
```

所以控制器不能假设“发 0.02 就会慢慢动”，也不能仅按 `命令值 × 时间` 推断移动距离。每次动作距离优先由 odom 计算，动作结束后必须等新图像重新估计二维码位置。


组成：

```python
unitree_go2_auto_recharge = autoconnect(
    unitree_go2,
    AutoRechargeModule.blueprint(),

```

`unitree_go2` 已包含：

```text
GO2Connection
VoxelGridMapper
CostMapper
ReplanningAStarPlanner
WavefrontFrontierExplorer
PatrollingModule
MovementManager
```

自动回充模块直接复用它们提供的视频、odom、costmap、规划器和统一运动出口。

### 2.2 为什么要区分“回充任务接管”和“视觉速度接管”

侧面看到二维码后，需要先让导航器把狗带到二维码正前方的预停靠点；此时仍要允许 `nav_cmd_vel` 工作。到达预停靠点后，才应屏蔽导航速度并让视觉伺服输出 `recharge_cmd_vel`。

因此现有单一 `recharge_active` 要拆成两个概念：

```text
recharge_task_active：自动回充任务已经接管，外部导航目标不得覆盖它
recharge_servo_active：最终视觉伺服已经接管速度，nav_cmd_vel 必须被屏蔽
```

### 2.3 MovementManager 修改

保留当前 `recharge_cmd_vel` 和人工遥控最高优先级，增加：

```python
recharge_task_active: In[Bool]
recharge_servo_active: In[Bool]
recharge_staging_goal: In[PointStamped]

recharge_task_granted: Out[Bool]
recharge_servo_granted: Out[Bool]
recharge_cancel: Out[Bool]
```

精确行为：

```text
收到 recharge_task_active=True：
  1. 立即向机器人输出一次零速度；
  2. 取消当前用户/巡航/探索目标；
  3. 设置 _recharge_task_active=True；
  4. 后续点击目标或新外部目标不得静默覆盖回充任务；
  5. 发布 recharge_task_granted=True。

收到 recharge_staging_goal：
  1. 只有 task_active=True 且 servo_active=False 时接受；
  2. 转发给现有 goal/way_point；
  3. 允许 nav_cmd_vel 继续到达 cmd_vel。

收到 recharge_servo_active=True：
  1. 再次取消 staging 导航目标；
  2. 输出零速度；
  3. 设置 _recharge_servo_active=True；
  4. 屏蔽 nav_cmd_vel；
  5. 仅转发 recharge_cmd_vel；
  6. 发布 recharge_servo_granted=True。

收到 tele_cmd_vel：
  1. 人工遥控永远优先；
  2. 向自动回充模块发布 recharge_cancel=True；
  3. 清除 task_active 和 servo_active；
  4. 输出一次零速度；
  5. 再转发人工指令。

回充失败或取消：
  1. 自动回充模块先发布零速度；
  2. servo_active=False；
  3. task_active=False；
  4. MovementManager 输出零速度并释放控制权；
  5. 不自动恢复旧导航目标，避免机器人充电后又立即离开充电板。
```

回充成功：

```text
1. 自动回充模块持续发布零速度；
2. servo_active=False，不再运行视觉运动控制；
3. task_active=True，进入 charging_hold，阻止巡航/探索自动产生新目标；
4. 旧导航目标仍不恢复；
5. 只有人工遥控、显式 cancel_recharge 或显式 leave_charger 才解除 task_active。
```

### 2.4 自动回充模块输入输出

```python
class AutoRechargeModule(Module):
    color_image: In[Image]
    odom: In[PoseStamped]
    global_costmap: In[OccupancyGrid]
    recharge_task_granted: In[Bool]
    recharge_servo_granted: In[Bool]
    recharge_cancel: In[Bool]

    recharge_task_active: Out[Bool]
    recharge_servo_active: Out[Bool]
    recharge_staging_goal: Out[PointStamped]
    recharge_cmd_vel: Out[Twist]
    recharge_state: Out[RechargeStatus]

    _go2: GO2ConnectionSpec
```

控制循环建议 `10 Hz`，但运动不是每 100 ms 连续改变一次，而是以“动作脉冲—停止—看新图”的采样视觉伺服运行。

### 4.4 动作脉冲

```python
@dataclass(frozen=True)
```


即一次脉冲只前后移动或只旋转，不同时混合两种动作，便于从日志和轨迹判断每一步产生了什么效果。

## 6. 图像到停靠目标的公式

### 6.1 相机内参缩放

官方 K 对应 `1280×720`，当前 4G WebRTC 常见帧是 `640×360`。宽高等比例时：

```python
sx = image_width / 1280
sy = image_height / 720

K_scaled = K.copy()
K_scaled[0, :] *= sx
K_scaled[1, :] *= sy
```

畸变参数 D 不按像素比例缩放。若宽高比改变或画面发生裁剪，拒绝使用这套 K，不能继续 PnP。

### 6.2 二维码中心方位角

PnP 得到：

```text
tvec = [x_C, y_C, z_C]
```

第一版最终视觉伺服只使用：

```python
bearing_rad = atan2(x_C, z_C)
```

含义：

```text
bearing > 0：二维码在画面右侧，狗需要向右转
bearing < 0：二维码在画面左侧，狗需要向左转
|bearing| <= 6°：认为已经足够对正，不继续追小角度
```

最终视觉控制不把码面法线 yaw 和中心 bearing 同时塞进控制器。

### 6.3 前进误差

```python
forward_error_m = z_C - target_camera_z_m
```

例子：

| `z_C` | 纵向含义 | 理论剩余前进量 |
|---:|---|---:|
| 1.20 m | 还很远 | 0.85 m |
| 0.75 m | 恢复/预停靠观察窗口 | 0.40 m |
| 0.50 m | 进入近场 | 0.15 m |
| 0.35 m | 最终几何目标 | 0.00 m |
| 0.22 m | 已走过头 | 应后退约 0.53 m 到恢复点 |

### 6.4 充电桩中心线与预停靠点

侧面看到二维码时，仅靠二维码中心 bearing 无法区分“机器人横向偏在右边”与“机器人只是在原地朝左偏”。因此：

- 最终伺服仍只用中心 bearing；
- 但在接管前，允许用稳定的二维码完整姿态 `rvec/tvec` 计算一次中心线和预停靠点；
- 这个姿态只用于生成 staging goal，不参与近场每帧转向。

变换：

```text
T_O_M = T_O_B · T_B_C · T_C_M
```

其中：

```text
O：当前 odom/规划坐标系
B：机器人 base/中心
C：前置 camera optical
M：二维码
```

从 `R_O_M` 取二维码平面法向量的水平投影，选择指向二维码可见侧/充电板开放侧的符号，得到单位向量：

```text
n_O = marker 指向充电板开放端和机器人来向的单位向量
```

然后：

```python
marker_xy = position(T_O_M)
staging_base_xy = marker_xy + n_O * 1.10
final_base_xy   = marker_xy + n_O * 0.70
```

预停靠点距离为什么是 `1.10 m`：

```text
恢复/预停靠时相机到二维码：0.75 m
相机到机器人中心：0.35 m
机器人中心到二维码：0.75 + 0.35 = 1.10 m
```

最终点：

```text
最终相机到二维码：0.35 m
相机到机器人中心：0.35 m
机器人中心到二维码：0.35 + 0.35 = 0.70 m
```

`marker normal` 的符号、`T_B_C` 和二维码安装朝向必须通过一次静态现场测试确认。若法线连续 7 帧不稳定、方向翻转或无法获得同一坐标系变换，则不自动从侧面接管，只允许进入“正前方直接视觉伺服”路径。

### 6.5 回退距离公式

二维码仍可见时：

```python
requested_backoff_m = recovery_z_target_m - z_C
backoff_goal_m = clamp(
    requested_backoff_m,
    recovery_min_backoff_m,
    recovery_max_single_backoff_m,
)
```

例子：

| 触发恢复时 `z_C` | 计算结果 | 预想动作 |
|---:|---:|---|
| 0.58 m | 0.17 m | 后退约 17 cm，再停下看图 |
| 0.50 m | 0.25 m | 后退约 25 cm |
| 0.35 m 且未对准 | 0.40 m | 后退约 40 cm 到观察窗口 |
| 0.22 m | 0.53 m | 后退约 53 cm 到观察窗口 |
| 0.10 m | 理论 0.65 m | 单轮最多 0.55 m，重看后决定是否再退 |

二维码已经丢失时，用“最后一帧可靠 `z_C`”计算预期回退量，但真正停止条件不能只靠时间：

```python
odom_backed_m = hypot(
    current_odom.x - recovery_start_odom.x,
    current_odom.y - recovery_start_odom.y,
)
```

停止条件取最先到达者：

```text
1. 二维码重新出现，并连续稳定，且 z_C ∈ [0.70, 0.85] m；
2. odom_backed_m >= 本轮 backoff_goal_m；
3. 单轮已退 0.55 m；
4. 累计已退 0.65 m；
5. 后方 costmap 不再安全；
6. odom/lowstate/图像超时。
```

如果先达到第 2 条但二维码仍没出现，停止并进入受限重捕获，不继续无上限倒车。

下面按实际执行顺序给出每个状态的代码逻辑。

### 7.1 `MONITOR`：正常导航时被动看码

此状态不发布运动命令，不抢导航控制权。

每帧执行：

```python
obs = vision.observe(image)
stability.push(obs)

if not stability.has_5_valid_of_last_7:
    stay(MONITOR)
elif stable_obs.marker_id != 0:
    stay(MONITOR)
else:
    transition(VALIDATE_DOCK)
```

“看到一帧”不算发现。至少满足：

```text
最近 7 帧中 5 帧有效
marker_id 全部为 0
重投影误差 <= 2.5 px
二维码四角距画面边缘 >= 12 px
z/x/bearing 的中位绝对偏差在阈值内
图像时间戳新鲜
```

### 7.2 `VALIDATE_DOCK`：判断是否值得中断当前导航

按下面顺序判断，任何一项失败都回到 `MONITOR`，不影响当前导航：

```python
if image_stale or odom_stale or lowstate_stale:
    reject("input_stale")
elif not 0.25 <= z_C <= 2.50:
    reject("marker_outside_auto_range")
elif marker_near_image_edge:
    reject("marker_edge_clipped")
elif pose_unstable:
    reject("marker_pose_unstable")
elif no_common_frame_between_odom_and_costmap:
    reject("frame_transform_unavailable")
elif not dock_geometry_can_be_built:
    reject("dock_geometry_invalid")
elif final_base_pose_in_obstacle_or_unknown:
    reject("dock_target_blocked")
elif staging_base_pose_in_obstacle_or_unknown:
    reject("staging_target_blocked")
elif corridor_to_staging_has_no_0_35m_clearance:
    reject("staging_corridor_blocked")
else:
    freeze(DockTarget)
    transition(CLAIM_TASK)
```

直接视觉伺服可达条件：

```python
direct_servo_reachable = (
    abs(bearing_rad) <= radians(35)
    and abs(x_C) <= 0.80
    and recovery_z_min_m <= z_C <= auto_detect_max_z_m
    and marker_normal_is_consistent_with_frontal_approach
)
```

如果不满足 direct 条件，但稳定的完整二维码姿态能生成可达 staging goal，则先走 `STAGING_NAV`。如果连 staging goal 都不能可靠生成，就不自动接管。

### 7.3 `CLAIM_TASK`：取消旧导航目标

```python

publish(recharge_cmd_vel=zero)
wait(recharge_task_granted=True, timeout=1.0s)
```

超时：

```text

publish task_active=False
FAILED
```

获得 task 控制权后，根据冻结目标计算当前机器人中心到二维码中心线的垂距 `centerline_error_m`：

```text
若 direct_servo_reachable=True、centerline_error_m<=0.15m、z_C<=1.20m
  -> ACQUIRE_FOR_SERVO，直接进入最终视觉段

若已经位于 staging 容差内
  -> ACQUIRE_FOR_SERVO

其他情况
  -> STAGING_NAV
```

### 7.4 `STAGING_NAV`：从正面、侧面或斜面走到中心线观察点

发布冻结的 `staging_base_pose.position` 作为专用导航目标：

```python
publish(recharge_staging_goal=PointStamped(
    frame_id=dock_target.frame_id,
    x=staging_base_pose.x,
    y=staging_base_pose.y,
    z=0.0,
))
```

此时：

```text
task_active=True
servo_active=False
nav_cmd_vel 仍可通过 MovementManager
外部点击/巡航目标不能覆盖 staging goal
```

到达判断不能仅依赖“规划器不再发速度”：

```python
distance_to_stage = hypot(
    odom.x - staging.x,
    odom.y - staging.y,
)

arrived = (
    distance_to_stage <= 0.15
    and odom_speed <= stopped_threshold
    and held_for >= 0.50s
)
```

状态转移：

```text
arrived -> ACQUIRE_FOR_SERVO
costmap/path 变成不可达 -> FAILED(staging_path_blocked)
45 s 未到 -> FAILED(staging_timeout)
人工遥控 -> CANCELLED
```

二维码在 staging 导航过程中暂时看不见不算失败，因为目标已经由稳定观测冻结；但 odom、costmap 和原冻结目标仍必须有效。

### 7.5 `ACQUIRE_FOR_SERVO`：在预停靠点或正前方直接区重新看到二维码

先停止导航目标，输出零速度并等 `0.25 s`。然后：

1. 若二维码已稳定可见，直接进入 `CLAIM_SERVO`。
2. 若看不见，根据冻结的 marker world position 和当前 odom 计算“二维码预计在哪个方向”，不是盲扫一整圈：

   ```python
   expected_heading = atan2(marker_y - odom.y, marker_x - odom.x)
   heading_error = wrap(expected_heading - odom.yaw)
   ```

3. 用 `|angular.z|=0.20` 小脉冲转向预计方向；每次最多 `0.50 s`，每次后停 `0.25 s` 看新图。
4. 到预计方向仍没看到时，只在预计方向两侧执行有限扫描：

   ```text
   0° -> +10° -> -10° -> +20° -> -20°
   ```

5. 不做 360° 连续旋转。累计扫描超过 8 s 或偏离预计方向超过 25°仍无二维码：

   ```text
   FAILED(marker_not_found_at_stage)
   ```

### 7.6 `CLAIM_SERVO`：最终速度控制权切换

```python
publish(recharge_servo_active=True)
publish(recharge_cmd_vel=zero)
wait(recharge_servo_granted=True, timeout=1.0s)
```

确认后导航速度被屏蔽，进入 `STOP_AND_OBSERVE`。未收到确认前绝不发非零回充速度。

### 7.7 `STOP_AND_OBSERVE`：每轮动作前的统一入口

```text
输出零速度
等待至少 0.25 s
等待一帧 observed_at > 上一个运动脉冲结束时间的新图像
将最近 7 帧送入稳定性窗口
```

只有获得运动结束后的新稳定观测，才能进入下一次决策。不能用运动前缓存的二维码位置连续发第二个动作。

### 7.8 `VISUAL_SERVO`：唯一的动作决策优先级

每次只决定一个动作。判断顺序必须固定：

```python
def decide_visual_action(ctx: Context) -> Decision:
    if operator_cancelled:
        return CANCEL

    if image_stale or lowstate_stale or odom_stale:
        return FAIL_INPUT_STALE

    if rear_or_forward_corridor_unsafe_for_next_motion:
        return FAIL_OBSTACLE

    if marker_missing:
        if last_reliable_z <= 0.85:
            return RECOVER_NEAR_FIELD_LOSS
        return WAIT_THEN_LIMITED_REACQUIRE

    if pose_unstable or marker_near_edge:
        if z_C <= 0.55:
            return RECOVER_NEAR_FIELD_UNSTABLE
        return STOP_AND_REOBSERVE

    if z_C < 0.28:
        return RECOVER_CRITICAL_OVERRUN

    if z_C <= 0.55 and abs(bearing) > 15deg:
        return RECOVER_TOO_CLOSE_TO_TURN

    if 0.30 <= z_C <= 0.45 and abs(bearing) <= 15deg:
        return FINAL_SETTLE

    if abs(bearing) > 6deg:
        return YAW_PULSE

    if z_C > 0.45:
        return FORWARD_PULSE

    if z_C < 0.30:
        return RECOVER_OVERRUN

    return STOP_AND_REOBSERVE
```

这个顺序意味着：安全和恢复永远优先于转向，转向优先于前进，前进优先于趴下。

#### 7.8.1 转向脉冲

```python
yaw_duration_s = clamp(
    abs(bearing_rad) / estimated_yaw_rate_rad_s * yaw_pulse_fraction,
    min_yaw_pulse_s,
    max_yaw_pulse_s,
)
```

命令：

```text
二维码在右：angular.z 使用真机已标定的右转符号，幅值 0.20
二维码在左：angular.z 使用相反符号，幅值 0.20
linear.x = 0
linear.y = 0
```

脉冲完成后立即发零速度，回 `STOP_AND_OBSERVE`。如果 `|bearing| <= 6°`，不发旋转命令。

#### 7.8.2 前进脉冲

只有 `|bearing| <= 6°` 才能前进：

```python
if z_C > 1.20:
    axis = 0.18
    duration = 0.40
elif z_C > 0.75:
    axis = 0.14
    duration = 0.30
elif z_C > 0.45:
    axis = 0.10
    duration = 0.20
else:
    no_forward_motion()
```

每个脉冲后发零速度并看新图。不能一次按理论 `z_C - 0.35` 连续走完全程。

### 7.9 `RECOVERY_STOP`：发现异常后的第一动作永远是停

触发来源：

```text
近场二维码丢失
z_C < 0.28 m
z_C <= 0.55 m 但 bearing > 15°
近场 PnP 抖动
二维码角点靠近/越出画面
趴下后未充电并重新站起
```

动作：

```text
立即发布零速度
保持至少 0.30 s
记录 recovery_start_odom
记录 last_reliable_observation
计算本轮 backoff_goal_m
检查后方 0.35 m 宽走廊
```

后方不可确认安全时不倒车：

```text
FAILED(recovery_corridor_blocked)
```

### 7.10 `RECOVERY_BACKOFF`：主动退回观察窗口

第一原则：先沿当前机身纵向直线后退，不带 yaw，不边倒车边盲转。

原因是该方向近似刚才的进入方向，最有可能把已经过大的二维码重新缩回画面，同时轨迹最可预测。

执行循环：

```python
while recovery_total_backoff_m < recovery_max_total_backoff_m:
    publish(forward_axis=-0.10, yaw_axis=0.0)
    hold(0.20s)
    publish(zero)
    hold(0.25s)

    update_odom_backed_distance()
    obs = wait_for_new_image()

    if obs is stable and 0.70 <= obs.z_m <= 0.85:
        transition(RECOVERY_REACQUIRE)
        break

    if obs is stable and obs.z_m < 0.70:
        # 已重见码，但仍太近：继续直退，不旋转
        continue

    if obs is stable and obs.z_m > 0.85:
        # 已退过恢复带：停止，下一步只转向/前进微调
        transition(RECOVERY_REACQUIRE)
        break

    if odom_backed_m >= backoff_goal_m:
        publish(zero)
        transition(RECOVERY_REACQUIRE)
        break

    if rear_corridor_unsafe or input_stale:
        fail()
        break
```

#### 二维码在后退中何时重新出现

二维码一出现不立刻前进，也不立刻转向：

```text
z_C < 0.70：继续直退
0.70 <= z_C <= 0.85：停下，稳定观察
z_C > 0.85：已经略退多，停下，后续按正常视觉伺服小步前进
```

### 7.11 `RECOVERY_REACQUIRE`：回退后重新建立可靠观测

先零速度等待 `0.30 s`，要求最近 7 帧至少 5 帧稳定。

情况 A：二维码稳定出现：

```text
0.70 <= z_C <= 0.85 且 |bearing| <= 6°
  -> VISUAL_SERVO，下一步允许细速前进

0.70 <= z_C <= 0.85 且 |bearing| > 6°
  -> VISUAL_SERVO，下一步先做 yaw 脉冲

z_C > 0.85
  -> VISUAL_SERVO，先按 bearing 对正，再小步前进

z_C < 0.70
  -> 若累计回退未到上限，回 RECOVERY_BACKOFF
```

情况 B：已经按计划后退，但二维码仍没出现：

1. 根据冻结 marker world pose 和当前 odom 重新计算预计朝向；
2. 只在预计朝向两侧做 `±10°、±20°` 的脉冲扫描；
3. 每个角度停下看新图；
4. 不做连续整圈旋转；
5. 若仍无二维码，且累计后退小于 `0.65 m`，后方安全，则再后退 `0.20 m` 后重试一次；
6. 两轮恢复仍失败：

   ```text
   FAILED(near_field_reacquire_failed)
   ```

### 7.12 `FINAL_SETTLE`：什么情况下认为到位

不是某一帧满足就到位。连续 `1.0 s` 满足：

```text
0.30 <= median(z_C) <= 0.45 m
|median(bearing)| <= 15°
最近 7 帧至少 5 帧有效
z_MAD <= 0.025 m（近场使用更严格阈值）
bearing_MAD <= 3°
角点距边缘 >= 12 px
重投影误差 <= 2.5 px
odom 表明机器人已停
最近 0.50 s 的输出命令全部为零
图像、odom、lowstate 均新鲜
```

其中：

```text
|bearing| <= 6°：理想
6° < |bearing| <= 15°：仍允许趴下，不追机械死区内的小角度
|bearing| > 15°：不允许趴下；如果 z <= 0.55，先退回恢复窗口再转
```

稳定期间任何条件破坏：清零 settle 计时器，回 `VISUAL_SERVO` 或进入恢复。

### 7.13 `LIE_DOWN`

```python
publish(zero)
hold(pre_liedown_zero_s)
assert latest_observation_still_inside_final_envelope
assert lowstate_is_fresh
success = go2.liedown()
```

`liedown()` RPC 失败：

```text
FAILED(liedown_failed)
```

成功后进入 `VERIFY_CHARGE`。

### 7.14 `VERIFY_CHARGE`

自研程序发布自己的状态：

```text
recharge_arrive：完成趴下动作并进入充电验证
recharge_success：充电证据连续稳定通过
```

当前主证据使用已实测的 BMS 电流带：

```text
带 A：-1500 <= current <= -500
带 B： 7500 <= current <= 8500
任一带连续稳定 4 s -> charging=True
```

`15 s` 内确认：

```text
SUCCEEDED
保持 task_active，保持零速度，不恢复旧导航任务
```

`15 s` 未确认且仍有重试次数：

```text
STAND_UP_RETRY
```

无 BMS 数据不能当作“未充电”直接乱动；先按 `lowstate_stale` 安全失败。

### 7.15 `STAND_UP_RETRY`

```text
1. 发布零速度；
2. standup/balance_stand；
3. 等姿态稳定和 lowstate 新鲜；
4. 重新观察二维码；
5. 无论当前看起来是否只差一点，都先回退到 z_C≈0.75 m 的恢复窗口；
6. 重新执行 VISUAL_SERVO -> FINAL_SETTLE -> LIE_DOWN；
7. 最大总停靠尝试次数 3 次。
```

站起后相机高度和视角会恢复，不能沿用趴下时的 PnP 观测。

## 8. 从不同起始位置预想实际轨迹

为了直观看轨迹，定义二维码地面投影为：

```text
M = (0.00, 0.00)
二维码正前方/充电板开放方向为 +X
充电板中心、机器人最终中心 B* = (0.70, 0.00)
预停靠机器人中心 S = (1.10, 0.00)
```

### 8.1 正前方、基本正对

初始例子：

```text
B0 = (2.00, 0.03)
二维码在画面中心右侧约 1°
```

轨迹：

```text
B0 ------------------> S ---------> B*
  导航到预停靠点         视觉小步前进
```

具体动作：

```text
1. 稳定看到码并计算 S；
2. 取消原导航，导航到 S；
3. 到 S 后二维码已近似居中；
4. bearing <= 6°，不旋转；
5. z≈0.75，发 0.10/0.20s 前进脉冲；
6. 每次停 0.25s 看图；
7. z 进入 0.30–0.45 后保持 1s；
8. 趴下并验充。
```

### 8.2 正前方，但机身向右斜 20°

初始例子：

```text
B0 = (1.10, 0.00)
机身朝向比二维码方向右偏 20°
二维码出现在画面左侧
```

轨迹近似：

```text
先原地左转若干小脉冲
       ↶
S      · ----------------> B*
```

具体动作：

```text
1. 在 S 停稳；
2. bearing≈-20°，只发左转 0.20 摇杆脉冲；
3. 停下看新图；
4. 可能剩 -8°，再发更短的左转脉冲；
5. 剩余角度 <=6° 后停止追角；
6. 才允许向前小步走。
```

### 8.3 从二维码右侧斜着看到

初始例子：

```text
B0 = (1.60, +0.70)
二维码位于机器人左前方
```

不能直接沿 `B0 -> M` 走，因为那条斜线会让机器人最终落在充电板中心线右侧。正确轨迹：

```text
B0 (1.60,+0.70)
  ╲
   ╲  现有导航根据 costmap 到 staging
    ╲
     S (1.10,0.00) --------> B* (0.70,0.00)
                              最终视觉直进
```

具体动作：

```text
1. 稳定 rvec/tvec 计算中心线；
2. 验证 S 和通道可达；
3. 中断原导航并以 S 为自动回充 staging goal；
4. 现有规划器绕障走到 S；
5. 到 S 后根据冻结二维码位置转向二维码；
6. 重新稳定识别；
7. 最终只用中心 bearing 和 z，小步走到 B*。
```

从左侧看到时轨迹左右镜像。

### 8.4 侧面角度很大，但二维码偶尔可见

例如 bearing 约 45°，且二维码角点靠近画面边缘：

```text
1. 不因一帧检测立刻原地猛转；
2. 若完整姿态稳定、staging 可达，走 STAGING_NAV；
3. 若完整姿态不稳定或法线方向跳变，不自动接管；
4. 保持原导航，日志记录 marker_pose_unstable / marker_edge_clipped；
5. 等机器人导航到更正面的观察位置后再触发。
```

这能避免官方黑盒测试中约 45° 斜向接近后冲入近场、失去恢复空间的问题。

### 8.5 前进过程中二维码逐渐偏到右侧

轨迹是短折线近似平滑曲线：

```text
前进一步 -> 停 -> 发现码偏右 -> 右转一点 -> 停 -> 前进一步

       __
     _/  \__
S __/       \__ B*
```

不会一边高速前进一边持续转。

### 8.6 走过头，但二维码仍可见

例子：

```text
z_C = 0.22 m
bearing = 4°
```

恢复轨迹：

```text
当前过冲点 B_over
       <-------------------- S_recover
             后退约 0.53 m

S_recover -----------------> B*
          重新小步对准前进
```

执行：

```text
1. 立即零速度 0.30s；
2. 计算 0.75 - 0.22 = 0.53m；
3. 每次 -0.10/0.20s 直退；
4. 每次停下看图和 odom；
5. z 达到 0.70–0.85 后停；
6. 重新按 bearing 对正；
7. 再前进约 0.40m 到最终点。
```

### 8.7 近场走过头，同时二维码丢失

最后可靠观测：

```text
last_z_C = 0.42 m
last_bearing = +8°
```

动作：

```text
1. 立即停止，不沿 last_bearing 继续盲转；
2. 计算预期回退 0.75 - 0.42 = 0.33m；
3. 记录 recovery_start_odom；
4. 沿机身纵向直退，yaw=0；
5. 如果退到一半二维码重新出现且 z=0.58，继续退；
6. z=0.73 且稳定后停止；
7. 若退满 0.33m 仍没出现，停止；
8. 围绕冻结的二维码预计方向做 ±10°、±20° 搜索；
9. 仍失败时再安全后退 0.20m，只允许一次；
10. 累计后退上限 0.65m，仍失败则安全退出。
```

### 8.8 远处前进时短暂丢一两帧

最后可靠 `z_C > 0.85 m`：

```text
1. 立即零速度；
2. 等 0.60s，4G 视频恢复则继续；
3. 不把短暂视频抖动直接当近场过冲；
4. 超过 0.60s 仍无二维码，根据冻结 marker 方向做有限重捕获；
5. 不成功则退回 staging 或失败，不盲目前进。
```

### 8.9 趴下但没有充电

轨迹：

```text
趴下未充
  -> 站起
  -> 直退回 z≈0.75
  -> 重新对准
  -> 再前进到 z≈0.35
  -> 再趴下
```

不能在趴下姿态直接根据旧图像做移动。

## 10. 伪代码总览

```python
def control_tick(now: float) -> None:
    refresh_freshness()
    stable = stability.latest()

    if cancelled:
        stop_and_release(CANCELLED)
        return

    match state:
        case MONITOR:
            if stable_candidate_found():
                transition(VALIDATE_DOCK)

        case VALIDATE_DOCK:
            result = validate_and_build_dock_target(stable, odom, costmap)
            if result.accepted:
                dock_target = result.target
                transition(CLAIM_TASK)
            else:
                trace_rejection(result.reason)
                transition(MONITOR)

        case CLAIM_TASK:
            request_task_ownership()
            if task_granted:
                if direct_servo_reachable() and centerline_error_m() <= 0.15 and z_C() <= 1.20:
                    transition(ACQUIRE_FOR_SERVO)
                elif already_at_staging():
                    transition(ACQUIRE_FOR_SERVO)
                else:
                    transition(STAGING_NAV)

        case STAGING_NAV:
            submit_staging_goal_once()
            if staging_arrived_and_stopped():
                cancel_staging_goal()
                transition(ACQUIRE_FOR_SERVO)
            elif staging_failed_or_timed_out():
                fail(STAGING_TIMEOUT)

        case ACQUIRE_FOR_SERVO:
            publish_zero()
            if stable_marker_visible():
                transition(CLAIM_SERVO)
            else:
                run_limited_expected_heading_search()

        case CLAIM_SERVO:
            request_servo_ownership()
            if servo_granted:
                transition(STOP_AND_OBSERVE)

        case STOP_AND_OBSERVE:
            publish_zero()
            if zero_settle_elapsed() and fresh_stable_frame_after_last_pulse():
                transition(VISUAL_SERVO)

        case VISUAL_SERVO:
            decision = decide_visual_action(context)
            execute_one_decision(decision)

        case RECOVERY_STOP:
            publish_zero()
            recovery = initialize_recovery(last_reliable_obs, odom)
            if rear_corridor_safe():
                transition(RECOVERY_BACKOFF)
            else:
                fail(RECOVERY_CORRIDOR_BLOCKED)

        case RECOVERY_BACKOFF:
            execute_one_backoff_pulse()
            if recovery_window_reached_or_backoff_goal_reached():
                transition(RECOVERY_REACQUIRE)

        case RECOVERY_REACQUIRE:
            publish_zero()
            if stable_marker_visible():
                transition(VISUAL_SERVO)
            elif limited_search_exhausted():
                fail(NEAR_FIELD_REACQUIRE_FAILED)

        case FINAL_SETTLE:
            publish_zero()
            if final_envelope_held_for_1s():
                transition(LIE_DOWN)
            elif final_envelope_broken():
                transition(VISUAL_SERVO)

        case LIE_DOWN:
            publish_zero()
            if go2.liedown():
                publish_state("recharge_arrive")
                transition(VERIFY_CHARGE)
            else:
                fail(LIE_DOWN_FAILED)

        case VERIFY_CHARGE:
            if charge_verifier.confirmed():
                publish_state("recharge_success")
                succeed_and_hold_position()
            elif verify_timeout() and attempts_remaining():
                transition(STAND_UP_RETRY)
            elif verify_timeout():
                fail(CHARGE_UNVERIFIED)

        case STAND_UP_RETRY:
            if stand_up_and_stabilize():
                transition(RECOVERY_STOP)
            else:
                fail(STAND_UP_FAILED)
```

# Go2 原始 Odom 时间保真与零速度静止闭环实施计划

创建日期：2026-07-30

最后更新：2026-07-31

适用分支：`jtlinux`

适用场景：Go2 真机通过 LocalSTA 或 Remote/4G WebRTC 执行原地转向、空间记忆寻物、房间扫描和导航控制。

## 1. 目标

解决当前控制链路中的两个问题：

1. Go2 原始 Odom 已带采样时间，但 `dimos/robot/unitree/connection.py` 会将 `odom.ts` 改写为主机当前时间。这个覆盖逻辑是图像与 Odom 按同一主机时间轴配对所必需的；问题在于原始采样时间没有作为下游可用元数据保留，控制器无法判断自己读到的是新采样，还是刚刚到达的旧采样。
2. `rotate_in_place_degrees()` 在发送零速度后只固定等待 `0.35s` 就返回。`move(zero)` 成功只说明本机提交发送未报错，不能说明 Go2 已停止转动。

本次改造的目标不是声称获得 Go2 的设备执行 ACK，而是建立一个可证伪的本地闭环：**只有收到停止命令之后采样的新姿态，且连续一段时间推算角速度足够小，才允许系统认为“已静止”并进入下一步视觉确认。**

## 2. 当前事实与设计约束

### 2.1 已确认的代码事实

当前 Odom/图像同步链路：

```text
Go2 ROBOTODOM header.stamp
  -> Odometry.from_msg() 写入 Pose.ts
  -> connection_raw_odom 记录 source_ts / host_rx_ts
  -> time_is_now() 覆盖 Pose.ts 为主机 time.time()
  -> world -> base_link TF
  -> 旋转控制器 / 路径控制器读取 TF

相机 VideoFrame
  -> Image.ts 也写为主机 time.time()
  -> NavigationSkillContainer 以 image.ts 与 Pose.ts 最近邻配对
```

`NavigationSkillContainer._build_search_snapshot()` 当前以 `abs(pose.ts - image.ts)` 选择拍照时最近的位姿。这条主机时间轴用于沿途寻物截图、VLM 延迟回退、图片保存和二次确认，必须保持不变。

当前旋转结束链路：

```text
remaining 进入容差
  -> move(zero_twist)
  -> sleep(0.35s)
  -> 返回 ok=True
```

日志已反复证明 `host_rx_ts - source_ts` 存在动态变化和突发到达，但 Go2 header 的时钟域仍是 `unitree_header_unverified`。因此：

- 不能将绝对 `host_rx_ts - source_ts` 直接命名为网络延迟。
- 不能用一个固定的跨设备秒数阈值判断“旧 Odom”。
- 可以利用同一条 source 时间序列的单调性、采样间隔，以及相对稳定基线之上的额外变化，判断动态滞后风险。
- `LOW_STATE` 的当前 Remote WebRTC 类型只明确包含 IMU `rpy`，没有可直接依赖的 gyro/yaw-rate 字段；首版静止判定不能假设它可用。

### 2.2 不改变的边界

- 不修改地图坐标系、重定位 TF、空间记忆地标坐标或 VLM 业务逻辑。
- 保留 Odom、图像和 TF 当前的主机时间同步语义；不改变 `Pose.ts` 的含义。
- 不以 WebRTC `send` 成功作为执行确认。
- 不在控制回调或 WebRTC 回调中同步写磁盘或等待日志。
- 不一次性把新的反馈门禁强制用于全部路径导航；先在原地旋转验证通过后再扩展。
- 任何“不确定”状态都保持或重复下发零速度，不继续旋转，不触发视觉“找到”或打招呼。

## 3. 目标状态机

### 3.1 Odom 状态模型

为每一条 Odom 建立不可覆盖的时间来源信息：

```text
OdomFeedback
  sequence                    # 主机收到原始 Odom 时递增
  source_ts                   # Go2 原始 header 时间，永不改写
  host_rx_wall_ts             # 主机原始回调墙钟，仅用于与 source 建立关系
  host_rx_monotonic_ns        # 主机收到数据的单调时间
  pose_ts                     # 现有 Pose.ts，主机时间轴，用于图像/Odom 对齐
  tf_published_monotonic_ns   # 写入 TF 缓存的单调时间
  pose / yaw
  baseline_delta_s            # 运行内稳定基线估计
  excess_delay_s              # host-source 相对基线的额外变化
  freshness_state             # FRESH / DELAYED / CLOCK_UNCERTAIN / INVALID
```

`Pose.ts` 继续保持当前的主机时间值，确保与 `Image.ts` 可直接比较。`source_ts` 仅保存在旁路 `OdomFeedback` 中。为避免给现有 LCM `PoseStamped` 临时挂 Python 属性，时间来源信息通过新的强类型缓存/RPC 接口传递给需要做安全判断的控制器；不能改变现有消息的图像/Odom 配对行为。

首版不要求全局规划器立刻消费该接口，但 TF、odom 发布和旋转控制必须能够追溯到同一条 `sequence`。

### 3.2 原地转向状态机

```text
PRECHECK
  -> observe：只记录 freshness，不改变现有旋转行为
  -> enforce：检查阈值已标定、baseline 可用、TF 与首条 Odom 为 FRESH
WAITING_TO_START
  -> enforce 下启动条件未就绪时持续发零，最多等待 5s
  -> 恢复后进入 ROTATING；超时返回 START_FEEDBACK_NOT_READY
ROTATING
  -> FRESH：累计新 yaw 并计算 remaining
  -> GRACE_HOLD：短时间保持当前命令，但不累计重复 yaw
  -> DELAYED / NO_NEW_ODOM / INVALID / CLOCK_UNCERTAIN：立即进入 ZERO_SENT
  -> 达到角度容差、总超时或发送异常
ZERO_SENT
  -> 只下发零速度，不宣布停止
WAITING_FOR_FRESH_ODOM
  -> 丢弃零命令之前采样的历史 Odom
  -> 反馈异常暂停时：最多等待 5s，且最多恢复 2 次
  -> 拿到新鲜 Odom 后必须先确认静止，再用恢复后的 yaw 重新计算 remaining
  -> 正常转到目标时：拿到新鲜 Odom 后进入 SETTLING
SETTLING
  -> 连续采样计算 yaw 角速度与 yaw 波动
SETTLED
  -> 返回成功，允许后续视觉确认
UNCONFIRMED_STOP / RECOVERY_TIMEOUT / ROTATION_TIMEOUT
  -> 保持零速度，返回失败，禁止后续到达动作
```

`SETTLED` 不是“机器人已收到设备 ACK”，而是“在可观测反馈内，机器人已出现连续的新低角速度状态”。日志必须保留这一语义。

每次 `rotate_in_place_degrees()` 必须同时受以下三类上限约束，任何分支都不能无限等待：

1. 启动前等待 baseline 和首条 `FRESH` Odom：最多 `5.0s`。
2. 旋转中每次反馈异常恢复：最多 `5.0s`，单次旋转最多恢复 `2` 次。
3. 单次旋转硬上限：默认 `60.0s`，包含启动等待、实际旋转、异常恢复和最终静止确认。

最终正常停车的静止确认仍使用独立的 `3.0s` 上限，但它也不得突破单次旋转的 `60.0s` 硬截止时间。

### 3.3 Odom 不新鲜的精确判定与控制动作

旋转控制是 20 Hz，而真机 Odom 约 18 Hz。因此一个控制 tick 读到与上一 tick 相同的 `sequence` 是正常现象，**不能仅因 sequence 单次重复就发零速度**。判定必须以“最后一条合格 Odom 到控制器的本机单调时间间隔”作为宽限条件。

每个控制 tick 都为当前关联的 `OdomFeedback` 计算以下字段：

```text
local_feedback_age_s = controller_read_monotonic - host_rx_monotonic
source_interval_s     = source_ts_i - source_ts_(i-1)
D_i                   = host_rx_wall_ts_i - source_ts_i
excess_delay_s        = D_i - baseline
```

其中 `baseline` 是同一次连接、source 时间连续且接收节奏稳定样本的低分位稳定簇；它代表“固定时钟关系 + 最低链路耗时”的合量，不被命名为网络延迟。

| 状态 | 必须满足的判断条件 | 旋转控制动作 |
|---|---|---|
| `FRESH` | provenance 关联成功；source 严格递增；source 间隔在合理范围；预热完成；`excess_delay_s <= max_excess_delay`；`local_feedback_age_s <= max_local_age` | 使用该 yaw 更新累计角度并计算下一条转向指令 |
| `GRACE_HOLD` | 上次状态为 `FRESH`；当前 sequence 尚未推进，但距上一次 FRESH 接收仍不超过 `max_no_new_odom_s` | 允许短暂保持当前转向命令，不更新 accumulated，不根据重复 yaw 重新计算角度 |
| `DELAYED` | 新 sequence 已到达，但 `excess_delay_s > max_excess_delay`；或新样本的本机本地年龄超限 | 立即发零速度，进入有界恢复；旧 yaw 不计入 achieved |
| `NO_NEW_ODOM` | sequence 未推进持续超过 `max_no_new_odom_s` | 立即发零速度，进入有界恢复；不能持续盲转 |
| `INVALID` | source 时间重复/倒退/异常跳变，或 source 间隔无法用于速度计算 | 立即发零速度并重置相关 baseline；进入有界恢复，不能使用该样本 |
| `CLOCK_UNCERTAIN` | provenance 关联失败、预热未完成、基线不可用或 source 时钟语义异常 | observe 模式只记录；enforce 模式发零速度并进入有界恢复 |

初始候选配置如下，必须由 LocalSTA 和 Remote 分别标定后才能固化：

```bash
# 20 Hz 控制与约 18 Hz Odom 下，允许正常的一两次控制 tick 复用同一条 Odom。
DIMOS_ROTATE_MAX_NO_NEW_ODOM_S=0.20
DIMOS_ODOM_MAX_LOCAL_AGE_S=0.20

# 仅使用 source 的相对时间间隔，不依赖其与主机的绝对时钟同步。
DIMOS_ODOM_MIN_SOURCE_INTERVAL_S=0.02
DIMOS_ODOM_MAX_SOURCE_INTERVAL_S=0.20

# 由 observe 数据分别标定，不使用跨运行 host-source 的绝对秒数。
DIMOS_ODOM_MAX_EXCESS_DELAY_S=<待按连接方式标定>

# enforce 模式下的有界恢复，不允许无限等待。
DIMOS_ROTATE_START_FRESHNESS_TIMEOUT_S=5.0
DIMOS_ROTATE_RECOVERY_TIMEOUT_S=5.0
DIMOS_ROTATE_MAX_RECOVERIES=2
```

`max_excess_delay` 的取值方法：先在同一连接方式的静止与正常旋转 observe 数据中统计 `excess_delay_s`，选取能够覆盖正常样本 P99、并留出有限裕量的阈值。若远程 4G 的正常 P99 已高于安全可接受控制反馈时限，则不应简单把阈值放大，而应保持零速度并将问题归类为“该连接条件不适合闭环旋转”。

`DIMOS_ODOM_MAX_EXCESS_DELAY_S` 未完成标定或配置非法时，`observe` 模式仍可运行和采集证据；`enforce` 模式必须在旋转开始前返回 `CONFIG_NOT_READY`，不能偷偷使用猜测阈值。

### 3.4 本次运行稳定基线的精确计算

基线在连接建立后后台持续计算，不等到用户发出“转向”命令才开始。它只用于将同一次运行的固定时钟关系与动态额外滞后分开，**不修改 `Pose.ts`，不参与图像/Odom 配对。**

#### 启用时机

```text
连接 ready 且开始收到原始 Odom
  -> 收集至少 3.0 秒、且至少 40 条有效 Odom
  -> 计算首次 baseline
  -> freshness 状态从 CLOCK_UNCERTAIN 进入可判定状态
```

两项条件必须同时满足：

- `DIMOS_ODOM_FRESHNESS_WARMUP_S=3.0`
- `DIMOS_ODOM_FRESHNESS_MIN_SAMPLES=40`

按约 18 Hz Odom，通常约 3 秒即可达到 40 条；若网络差、回调慢或有效样本不足，则继续预热。`observe` 模式下只记录 `CLOCK_UNCERTAIN`；`enforce` 模式下，在基线尚未就绪时禁止下发非零旋转，持续发送零速度并最多等待 `5.0s`。等待期间 baseline 就绪且出现 `FRESH` Odom 后可以开始旋转；超时则返回 `START_FEEDBACK_NOT_READY`，不能擅自把未知反馈当新反馈。

#### 有效样本筛选

只有同时满足下面条件的样本才进入基线窗口：

1. `source_ts`、`host_rx_wall_ts`、`host_rx_monotonic_ns` 均存在且有限。
2. `source_ts` 相比上一有效样本严格递增。
3. `source_interval_s` 位于 `[0.02, 0.20]` 秒；超出范围视为时间语义异常或采样不连续。
4. 当前 Odom provenance 与覆盖后的 `Pose.ts` 一一关联成功。

不要求机器人静止。基线描述的是通信/处理时间关系，正常直行或旋转期间的有效样本也可以参与；明显积压样本会通过低分位算法自然不影响基线。

#### 首次基线公式

对预热期间所有有效样本计算：

```text
D_i = host_rx_wall_ts_i - source_ts_i
baseline_0 = P10(D_i)
```

采用 P10 而不是最小值，避免偶发的过小异常值把基线拉低；也不采用中位数，避免积压样本把正常的动态余量吞进基线。`baseline_0` 的含义始终是“当前连接下接近最低的 host-source 差”，不是纯时钟偏移，也不是单向网络延迟。

#### 运行中的更新与重标定

首次基线生效后，维护最近 `60s`、最多 `2048` 条有效样本的滑动窗口，每 `1s` 更新一次：

```text
candidate_baseline = P10(D_window)
```

更新规则：

1. 若 `abs(candidate_baseline - baseline) <= 0.10s`，直接更新为 `candidate_baseline`。
2. 若差值大于 `0.10s`，不立刻把新值用于控制；记录 `BASELINE_SHIFT`，清空基线状态并重新执行 `3.0s + 40条有效样本` 预热。
3. 重连、source 时间倒退/跳变、连接方法从 LocalSTA 切换到 Remote 时同样强制重新预热，不能沿用旧基线。
4. 重标定期间状态为 `CLOCK_UNCERTAIN`；enforce 模式保持零速度，observe 模式只记录。

这样可以处理时钟/NTP 或连接状态突变，避免把旧连接条件的基线错误套到新的数据流。

#### 单样本新鲜度计算

在基线有效时，对每个新样本计算：

```text
excess_delay_s = max(0, D_i - baseline)
```

控制器不根据单个 `D_i` 的绝对大小作结论，只根据：

```text
source 是否连续
AND provenance 是否关联成功
AND local_feedback_age 是否在限值内
AND excess_delay 是否在该连接方式已标定阈值内
```

的组合结果判为 `FRESH` 或 `DELAYED`。

### 3.5 单次旋转的无歧义伪代码

实现时不再只返回无法区分原因的裸 `bool`。内部使用 `_RotationResult`，至少包含：

```text
status
commanded_deg
achieved_deg
recovery_count
reason
```

`status` 至少区分：

```text
SUCCESS
NO_ROTATION_NEEDED
CONFIG_NOT_READY
START_FEEDBACK_NOT_READY
TF_MISSING
COMMAND_SEND_FAILED
ZERO_SEND_FAILED
FEEDBACK_RECOVERY_TIMEOUT
FEEDBACK_RECOVERY_EXHAUSTED
SETTLE_TIMEOUT
ROTATION_TIMEOUT
INTERNAL_ERROR
```

RPC 边界如暂时只能保留 `bool`，也必须在 `NavigationSkillContainer` 可消费的结构化结果或独立状态接口中保留上述原因，不能让上层把控制故障误认为视觉未命中。

```python
def rotate(delta_deg):
    hard_deadline = monotonic_now() + rotate_timeout_s
    recovery_count = 0

    if abs(delta_deg) < minimum_delta:
        return NO_ROTATION_NEEDED

    if freshness_mode == "observe":
        # 完全沿用当前命令序列，只新增非阻塞日志。
        return current_rotation_logic(delta_deg)

    if max_excess_delay is not calibrated:
        send_zero()
        return CONFIG_NOT_READY

    if not baseline_ready or latest_feedback is not FRESH:
        send_zero_repeatedly(zero_resend_hz)
        if not wait_for_fresh_odom(timeout=5.0, bounded_by=hard_deadline):
            return START_FEEDBACK_NOT_READY

    start_yaw = latest_fresh_yaw
    last_accepted_yaw = start_yaw
    accumulated = 0

    while monotonic_now() < hard_deadline:
        feedback = read_feedback_for_current_tf()

        if feedback.state == FRESH:
            accumulated += angle_diff(feedback.yaw, last_accepted_yaw)
            last_accepted_yaw = feedback.yaw
            remaining = radians(delta_deg) - accumulated
            if abs(remaining) <= tolerance:
                break
            send_rotation_command(remaining)
            continue

        if feedback.state == GRACE_HOLD:
            # 最多 0.20s，不累计相同 sequence，也不按旧 yaw 重算命令。
            keep_last_command()
            continue

        # DELAYED / NO_NEW_ODOM / INVALID / CLOCK_UNCERTAIN
        if not send_zero_repeatedly(zero_resend_hz):
            return ZERO_SEND_FAILED
        recovery_count += 1
        if recovery_count > max_recoveries:
            return FEEDBACK_RECOVERY_EXHAUSTED

        recovered = wait_for_fresh_and_settled(
            timeout=5.0,
            bounded_by=hard_deadline,
        )
        if not recovered:
            return FEEDBACK_RECOVERY_TIMEOUT

        # 将反馈中断期间真实发生的旋转一次性纳入累计值。
        accumulated += angle_diff(recovered.yaw, last_accepted_yaw)
        last_accepted_yaw = recovered.yaw
        remaining = radians(delta_deg) - accumulated
        if abs(remaining) <= tolerance:
            break
        # 尚未转够时，从静止状态恢复闭环旋转。

    if monotonic_now() >= hard_deadline:
        send_zero()
        return ROTATION_TIMEOUT

    if not send_zero_and_wait_for_settle(
        timeout=min(3.0, hard_deadline - monotonic_now())
    ):
        return SETTLE_TIMEOUT
    return SUCCESS
```

如果显式配置了 `DIMOS_ROTATE_TIMED_FACTOR`，当前上层会优先走开环定时旋转，绕过 TF/Odom 闭环。`enforce` 模式下不得静默走该 fallback：首版应禁止空间记忆标记、房间扫描和物体视觉伺服使用开环定时旋转；若未来需要支持，必须为它单独设计停止与执行确认，不得复用本计划的 Odom 成功结论。

### 3.6 标记房间的业务状态路径

房间标记的关键事实是：初始 ROOM 坐标、初始朝向图片、CLIP/Chroma 写入和第一帧异步 VLM 都发生在第一次旋转之前。因此后续旋转失败不能回滚已经真实保存的数据，但也不能宣称全景采集完整。

```python
def tag_location(name, rotations):
    if skill_not_started:
        raise SkillNotStarted
    if no_odom:
        return TAG_FAILED_NO_ODOM

    record_room_pose(name)
    initial_image_saved = snap_image_to_clip_and_start_vlm(name)
    completed_photos = 1 if initial_image_saved else 0

    if no_camera:
        return TAG_PARTIAL_NO_CAMERA

    for index in range(rotations):
        result = rotate(rotation_step_deg)
        if result.status not in {SUCCESS, NO_ROTATION_NEEDED}:
            # 不再执行剩余旋转；已保存图片和已启动 VLM 线程继续保留。
            return TAG_PARTIAL(
                completed=completed_photos,
                expected=rotations + 1,
                rotation_index=index + 1,
                reason=result.status,
            )
        wait_camera_settle(0.3)
        if snap_one(name):
            completed_photos += 1

    if completed_photos == rotations + 1:
        return TAG_COMPLETE
    return TAG_PARTIAL_IMAGE_FAILURE
```

具体分支：

| 条件 | 动作 | 对用户结果 |
|---|---|---|
| 启动时没有任何 Odom | 不写 ROOM，不旋转 | `TAG_FAILED_NO_ODOM` |
| 有 Odom、无相机 | 可保存 ROOM 坐标，不旋转或继续空转均无业务价值，首版直接结束 | `TAG_PARTIAL_NO_CAMERA` |
| 初始图成功，全部旋转和拍图成功 | 保存全部帧并启动各帧 VLM | `TAG_COMPLETE` |
| 第 K 次旋转控制失败 | 立即停止后续旋转；保留前 K 张有效图和 ROOM | `TAG_PARTIAL_ROTATION_FAILURE` |
| 旋转成功但某次图片保存失败 | 不伪造图片数量；可继续后续角度采集 | `TAG_PARTIAL_IMAGE_FAILURE` |
| VLM 异步请求失败 | 不影响已经完成的 ROOM/CLIP 标记；单独记录识别失败 | `TAG_COMPLETE_WITH_VLM_ERRORS` 或 partial 明细 |

返回文案必须包含实际完成数量，例如：`办公室已标记，但全景采集不完整：完成 2/6 张；第 2 次旋转因 Odom 反馈恢复超时终止。`

### 3.7 到达物体后的转向与视觉确认状态路径

到达历史物体位置只代表“到达曾经观察它的位置”，不能直接触发找到动作：

```text
到达历史位置
  -> 若有 stored_yaw，先尝试转向历史朝向
  -> 当前帧 VLM 检测目标
  -> bbox 偏差 < 3°：无需转向，直接进入新帧确认
  -> bbox 偏差 >= 3°：执行闭环旋转
  -> 旋转 SUCCESS + SETTLED：进入新帧确认
  -> 旋转 CONTROL_ERROR：终止当前旋转搜索，禁止打招呼
```

新帧确认继续沿用现有闭环：

```text
等待画面稳定 0.3s
  -> 最多等待 2.0s，要求 frame sequence、image.ts、接收单调时间都推进
  -> VLM 命中且中心偏差 <= 5°：CONFIRMED
  -> VLM 命中但偏差 > 5°，且尚有检查次数：再转向一次并获取下一张新帧
  -> 无新帧 / VLM 未命中 / bbox 异常 / 两次仍未居中：UNCONFIRMED
  -> corrective rotation 控制失败：CONTROL_ERROR
```

业务结果必须分开：

| 结果 | 后续行为 |
|---|---|
| `CONFIRMED` | 保存确认 JPG，回复“找到”，执行打招呼 |
| `UNCONFIRMED` | 不保存成功快照、不打招呼；继续当前房间其他视角或下一个房间 |
| `CONTROL_ERROR` | 不得当成“当前视角没有目标”；中止当前房间的旋转搜索，并向上返回“运动反馈异常，无法安全完成寻找” |

以下当前调用点必须显式消费旋转结果，不能继续忽略：

1. `tag_location()` 的逐步全景旋转：失败后返回 partial，而不是普通 `Tagged`。
2. `_scan_room_for_object()` 转向 `stored_yaw`：失败后不得继续假装已经面向历史朝向。
3. `_scan_room_for_object()` 的逐步扫描：每一步都必须检查结果；控制失败后不得继续拍图并发下一次旋转。
4. `_servo_to_bbox()` 与 `_confirm_visual_lock()` 的纠偏旋转：失败统一返回 `CONTROL_ERROR`，不能丢失成 `None`。

## 4. 实施方案

### 阶段 A：时间来源保真与旁路反馈缓存

涉及文件：

- `dimos/robot/unitree/connection.py`
- `dimos/robot/unitree/go2/connection.py`
- `dimos/robot/unitree/go2/connection_spec.py`
- 新增 Odom 时间来源类型与单元测试

实施内容：

1. 保留真机 `odom_stream()` 中现有 `time_is_now()` 覆盖逻辑；图像和 Odom 继续使用同一主机时间轴。
2. 在调用 `time_is_now()` **之前**生成单调递增的 `sequence`、`source_ts`、主机墙钟和主机单调接收时间；覆盖后保存对应的 `pose_ts`。解析完成、TF 发布完成时补齐对应的单调时间。
3. 在 `Go2Connection` 模块缓存最近一条 `OdomFeedback`，并以明确的 RPC/Spec 方法暴露给 `UnitreeSkillContainer`。返回值必须包含采样时间、接收时间、sequence、yaw 和 freshness 判断，不能只返回裸 TF。
4. 保留现有 `connection_raw_odom` trace，但增加 `sequence`、TF 发布 sequence、控制器消费 sequence 等关联字段。
5. 所有同主机时延使用 `time.monotonic_ns()`；`source_ts` 与主机墙钟仅用于建立运行内相对基线。

兼容性审计：

- 回归检查 `Pose.ts` 与 `Image.ts` 的最近邻配对，尤其是沿途寻物 `_build_search_snapshot()`、VLM 延迟回退、TF 缓存、Rerun、导航 trace 和回放代码。
- Replay、MuJoCo、DimSim 后端没有原始 Unitree source clock 时，构造明确的 `CLOCK_UNCERTAIN` 或模拟实现，不得伪造真机新鲜度。
- 原始 source 时间的旁路缓存必须在 Go2Connection 工作进程内与已覆盖时间的 Pose 一一关联；关联失败时 freshness 为 `CLOCK_UNCERTAIN`，不得猜测或错配到另一帧。

### 阶段 B：运行内新鲜度估计器

新增一个小型、无阻塞的 `OdomFreshnessEstimator`，仅维护有限窗口，不做文件 IO。

计算规则：

```text
D_i = host_rx_wall_ts_i - source_ts_i
baseline = 稳定、单调样本中 D_i 的低分位稳定簇
excess_delay_i = D_i - baseline
```

判定条件：

- `source_ts` 必须严格推进，且相邻间隔处于合理范围；重复、倒退、巨大跳变进入 `INVALID`。
- 在完成最小预热样本数前仅报告 `CLOCK_UNCERTAIN`：observe 模式不强制停车；enforce 模式禁止非零旋转并按启动等待上限处理。
- `excess_delay_s` 超出配置阈值时标记 `DELAYED`；阈值以实际 LocalSTA/Remote 分开标定，不使用跨运行的绝对 `host-source` 秒数。
- 接收序号虽递增、但 source 时间明显落后于零命令前的时间水位时，该样本不能证明停止后的姿态。
- 控制频率高于 Odom 频率时，同一 sequence 在短宽限窗口内仅为 `GRACE_HOLD`；只有超过 `max_no_new_odom_s` 才判为 `NO_NEW_ODOM` 并发送零速度。

估计器应输出原因码，例如：`WARMUP`、`SOURCE_NON_MONOTONIC`、`EXCESS_DELAY`、`POST_STOP_SOURCE_NOT_REACHED`、`FRESH`，便于日志和测试判断。

### 阶段 C：零速度发送与静止确认

涉及文件：

- `dimos/robot/unitree/unitree_skill_container.py`
- `dimos/robot/unitree/go2/connection.py`
- 必要时 `dimos/robot/unitree/connection.py`

将当前旋转结束处的 `move(zero) + sleep(0.35)` 替换为统一的私有流程 `_send_zero_and_wait_for_settle()`：

1. 记录最后一个非零控制命令的 ID、值、生成时间、发送开始/完成单调时间。
2. 显式下发零 Twist，记录零命令 ID、`move()` 返回值、WebRTC send 事件关联 ID；发送异常立即进入失败路径。
3. 从零命令开始，以受限频率重复显式零 Twist，直到确认静止或超时，避免上一摇杆值被继续保持；不能依赖当前只取消 timer 的 `stop_movement()` watchdog 行为。
4. 记录零命令前的 `source_ts` 水位、sequence、主机单调时间和运行内 source-to-host 基线；只接受 sequence 增大、source 时间严格推进、且按该基线估计的采样时刻不早于零命令安全界限的新 Odom。
5. 对连续合格 Odom 用 source 时间差计算 yaw 角速度；若 source 时间间隔异常，不计算角速度，也不能进入 `SETTLED`。
6. 同时要求：
   - 至少 `N` 条停止后新 Odom；
   - 连续稳定窗口内 `abs(yaw_rate)` 小于阈值；
   - 同窗口 yaw 总波动小于阈值；
   - 每条样本 freshness 为 `FRESH`；
   - 稳定持续时间达到最小值。
7. 满足全部条件才返回 `SETTLED`；超时或反馈异常返回带原因的 `_RotationResult`，状态为 `SETTLE_TIMEOUT`、`FEEDBACK_RECOVERY_TIMEOUT` 等，并保持零速度。若兼容 RPC 暂时仍返回 `False`，结构化原因不得丢失。
8. `ZERO_SEND_FAILED` 是最高优先级控制故障：不得继续发送旋转命令，不得进入视觉成功路径；日志必须保留最后一条非零命令、零命令发送异常和连接状态。它不等于已经物理停车。

首版不把 `LOW_STATE.rpy` 作为静止成功条件。额外记录原始 LOW_STATE payload 和到达时间；若真机确认其中稳定提供 gyroscope/yaw-rate，再以独立、可选的第二证据接入，而不是替换 Odom 判据。

### 阶段 D：控制器接入与业务保护

1. `rotate_in_place_degrees()` 继续从 TF 读取当前姿态值，但同时读取同 sequence 的 `OdomFeedback`；TF 的 `Pose.ts` 继续服务于图像同步，不能单独作为新鲜度证据。
2. 反馈 `DELAYED`、`INVALID`，或 sequence 未推进超过 `max_no_new_odom_s` 时，立即进入 `ZERO_SENT`，不再根据旧 yaw 累积 `achieved` 或继续下发非零转向。短宽限内的正常 sequence 重复仅进入 `GRACE_HOLD`，不误停。
3. `rotate_in_place_degrees()` 只有在 `SETTLED` 后才可返回成功。
4. 引入结构化 `_RotationResult`；如 RPC 兼容性要求保留 `bool`，必须增加可关联的结果查询接口，禁止上层丢失故障原因。
5. `tag_location()` 将旋转失败映射为 `TAG_PARTIAL_ROTATION_FAILURE`，停止剩余全景旋转，但保留已写入 ROOM、CLIP/Chroma、图片和已启动的 VLM 线程。
6. `_scan_room_for_object()` 的 `stored_yaw` 转向和每一步扫描必须检查旋转结果。普通视觉未命中可以继续搜索；`CONTROL_ERROR` 必须中止旋转搜索并向上传播。
7. `_servo_to_bbox()`、`_detect_and_servo()`、`_detect_and_servo_by_list_recognition()` 和 `_confirm_visual_lock()` 保留 `CONTROL_ERROR`，不得压缩为 `None` 或普通 `UNCONFIRMED`。
8. 只有视觉结果 `CONFIRMED` 才可触发成功 JPG、回复“找到”和打招呼；控制故障与视觉未命中都不得触发到达动作。
9. 路径导航控制器第一期只记录 freshness，不改变运行行为；待原地旋转真机验收完成后，以独立开关接入相同门禁，避免一次修改影响现有导航链路。

### 阶段 E：配置、日志和故障降级

建议配置项：

```bash

DIMOS_ODOM_FRESHNESS_MODE=observe           # observe | enforce
DIMOS_ODOM_FRESHNESS_WARMUP_S=3.0
DIMOS_ODOM_FRESHNESS_MIN_SAMPLES=40

DIMOS_ODOM_BASELINE_MAX_SHIFT_S=0.10
```

日志要求：

- 只写入有界 navigation trace，使用小型标量事件和后台 writer；控制线程不能被日志阻塞。
- 每个旋转周期关联 `rotation_session_id`、control tick、Odom sequence、freshness 原因、源/接收/控制单调时间。

- 明确区分 `local_send_completed`、`fresh_feedback_observed`、`settled_by_odom`；禁止记录成不存在的 `robot_execution_ack`。

## 5. 测试计划

### 5.1 单元测试

1. Odom 经 `odom_stream -> TF -> odom publish` 后，`Pose.ts` 仍与同一时刻的 `Image.ts` 可最近邻配对；原始 `source_ts` 在旁路 `OdomFeedback` 中保持不变。
2. `OdomFeedback.sequence` 单调，source/接收/覆盖后的 `Pose.ts` 与 TF 发布时间可关联。
3. 固定时钟偏移但 source/host 节奏正常：判为 `FRESH`，不误触发停车。
4. source 时间正常、host 突发接收历史帧：判为 `DELAYED`。
5. 单次或短时间 sequence 重复但不超过宽限：判为 `GRACE_HOLD`，不发送零速度。
6. sequence 未推进超过宽限：判为 `NO_NEW_ODOM`，发送零速度。
7. source 时间倒退、重复、跳变：判为 `INVALID`，不能计算 yaw-rate。
8. 零命令后只有旧 source 时间的 Odom：不能进入 `SETTLED`。
9. 零命令后连续新 Odom 且 yaw-rate、yaw span 均合格：进入 `SETTLED`。
10. yaw-rate 长期高于阈值、反馈延迟、无新 Odom、发送异常：返回 `UNCONFIRMED_STOP` 并持续零速度。
11. observe 模式完全不改变当前旋转命令序列；enforce 模式在异常反馈时停止非零旋转。
12. TraceSink 满、写入失败或禁用时，不影响命令发送和控制频率。
13. enforce 启动时 baseline 未就绪：最多等待 `5s`；期间恢复则开始旋转，超时返回 `START_FEEDBACK_NOT_READY`。
14. 旋转中第一次反馈异常：零速度、等待 `FRESH + SETTLED`，恢复后按最新 yaw 重新计算 remaining，不从旧命令继续盲转。
15. 单次恢复超过 `5s`：返回 `FEEDBACK_RECOVERY_TIMEOUT`；连续异常超过 2 次：返回 `FEEDBACK_RECOVERY_EXHAUSTED`。
16. 恢复、静止确认和真实旋转耗时之和超过 `60s`：统一返回 `ROTATION_TIMEOUT`，不存在无限等待。
17. `DIMOS_ODOM_MAX_EXCESS_DELAY_S` 未标定：observe 可运行，enforce 返回 `CONFIG_NOT_READY` 且不发非零旋转。
18. 显式启用 `DIMOS_ROTATE_TIMED_FACTOR` 时，enforce 的空间记忆相关旋转不得绕过新鲜度门禁。
19. 零速度发送失败：返回 `ZERO_SEND_FAILED`，不得记录为已静止或进入视觉确认。

### 5.2 回放与模拟测试

- 使用现有 `raw_odometry_rotate_walk` 回放，验证时间保真、yaw-rate 计算和状态机转换。
- 构造带固定时钟偏移、动态积压、burst、重复帧、无 Odom 的确定性输入。
- MuJoCo/DimSim 明确走模拟 freshness 适配，不因缺少 Unitree header 误报失败。
- 回放“反馈异常 -> 1s 后恢复 -> 重新计算 remaining -> 成功”的完整路径。
- 回放“反馈异常 -> 5s 未恢复”及“恢复后再次异常超过 2 次”，确认分别返回准确原因。
- 验证所有等待都受单次旋转 `60s` 硬截止约束。

### 5.3 业务链路测试

1. 标记房间完整成功：初始图加全部旋转图数量正确，返回 `TAG_COMPLETE`。
2. 标记房间第 K 次旋转发生 Odom 故障：停止剩余旋转，ROOM 和前 K 张有效图保留，返回实际完成数与失败原因。
3. 标记房间无相机：不执行无意义的全景空转，返回 `TAG_PARTIAL_NO_CAMERA`。
4. 单张图片或异步 VLM 失败：不回滚已写入 ROOM/CLIP 数据，返回结果明确区分图片失败和识别失败。
5. 到达历史物体点后 `stored_yaw` 转向失败：不得继续记录成已面向目标，不得打招呼。
6. 房间逐步扫描第 K 步旋转失败：不得在不确定朝向继续 VLM 拍摄或执行第 K+1 次旋转。
7. bbox 本身已在 `3°` 内：不触发旋转，仍必须用新相机帧完成最终视觉确认。
8. bbox 需要纠偏且旋转成功：只有 `SETTLED` 后才等待新帧；确认居中后保存 JPG 并执行一次打招呼。
9. 最终确认 VLM 未命中或两次仍未居中：返回 `UNCONFIRMED`，继续正常搜索其他视角或房间。
10. 任一纠偏旋转发生 `CONTROL_ERROR`：中止当前旋转搜索并向上返回运动反馈异常，不得降级成普通视觉未命中。
11. 原有沿途寻物、历史点寻物、房间遍历和二次视觉确认回归全部通过。

### 5.4 真机分阶段验收

1. **observe 模式**：LocalSTA 与 Remote 各完成静止、20°、60°、120° 旋转测试；验证新 trace 完整、无控制周期退化。
2. **enforce 模式，仅旋转**：人工制造正常网络和弱网场景；旧 Odom 时必须先零速度，且不得继续积累旧 yaw。
3. **停止确认**：每次旋转结束后检查日志中至少有 `ZERO_SENT -> post-stop fresh odom -> SETTLED`；不能只有 `move(zero)`。
4. **房间标记回归**：完整全景返回 complete；人为制造第 K 次旋转失败时返回 partial、保留已有数据且不再继续转。
5. **空间记忆寻物回归**：到历史位置、stored yaw、逐步扫描、VLM 转向、二次确认；任何 `UNCONFIRMED_STOP` 或 `CONTROL_ERROR` 均不得打招呼或回复找到。
6. **性能 A/B**：diagnostics off / observe / enforce 分别比较控制周期、WebRTC heartbeat、Odom 接收率、TraceSink drop 数和旋转总耗时。

验收条件：

- 现有正常网络下，enforce 不应频繁误停；阈值和触发率必须有实测记录。
- 出现动态反馈异常时，日志可定位到 source、接收、TF、控制、零命令和静止判断的完整链路。
- 没有连续新且低角速度反馈时，不得返回旋转成功。
- 诊断打开后控制周期、WebRTC heartbeat 和相机/Odom 接收率不出现不可接受退化。

## 6. 上线顺序与回滚

1. 合入时间来源与 observe 日志，默认不改变控制行为。
2. 完成回放和 LocalSTA/Remote observe 真机基线，分别确定 `excess_delay` 阈值。
3. 只为 `rotate_in_place_degrees()` 打开 enforce 和静止确认。
4. 依次验证单次转向、标记房间全景、历史物体朝向、房间逐步扫描、二次纠偏，不一次开启全部业务路径。
5. 完成寻物二次确认回归后，再评估是否把 freshness 门禁接入路径跟随控制器。
6. 保留 `DIMOS_ODOM_FRESHNESS_MODE=observe` 作为即时回滚开关；回滚只关闭门禁，不回退原始时间保真和诊断证据。

## 7. 风险与决策点

| 风险 | 应对 |
|---|---|
| 原始 source 时间改变 TF/Rerun/回放消费者行为 | 先做全量消费者审计和回放测试；必要时为旧消费者提供显式主机接收时间适配器 |
| 跨设备时钟差导致错误 freshness 判定 | 只用运行内稳定基线的额外变化；预热不足或 source 异常时进入不确定状态，不声称网络延迟 |
| 严格门禁导致旋转常常超时 | 先 observe 标定；enforce 仅用于旋转；超时保持零速度并记录原因，不盲目放宽阈值 |
| 反馈恢复等待导致业务卡住 | 启动/单次恢复均限制 5s、最多恢复 2 次，并受单次旋转 60s 硬截止约束 |
| 标记房间中途失败却仍返回完整成功 | 返回 partial、实际图片数和旋转失败原因；保留已写数据，不继续剩余旋转 |
| 控制故障被误判为视觉未命中 | 结构化区分 `UNCONFIRMED` 与 `CONTROL_ERROR`，后者中止旋转搜索并向上传播 |
| 开环 timed fallback 绕过 freshness | enforce 首版禁止空间记忆业务静默使用 timed fallback |
| Odom 停止但物理机身仍有残余旋转 | 首版明确为 Odom 闭环；记录 LOW_STATE，后续确认 gyro 可用后加入第二证据 |
| 高频日志影响真机 | 复用有界异步 TraceSink，控制路径仅写小型标量，队列满时丢诊断而不阻塞控制 |

## 8. 完成定义

本计划完成不等于“网络延迟被消除”。完成定义是：

1. Odom 主机时间覆盖与图像/Odom 对齐逻辑保持不变；控制器可通过旁路元数据追溯每次使用的原始反馈来源。
2. 零速度后有明确的、基于连续新 Odom 的静止确认或未确认结果。
3. 反馈旧、缺失、异常时，旋转不会继续用旧 yaw 推进，也不会误报旋转成功。
4. 所有启动等待、异常恢复和静止确认都有明确超时，任何房间标记或物体转向路径都不会无限卡住。
5. 房间全景中途失败返回 partial；视觉未命中与控制故障在业务结果上明确分离。
6. 历史朝向、逐步扫描和视觉纠偏全部检查旋转结果，只有 `CONFIRMED` 才保存成功快照并打招呼。
7. 新行为仅在真机旋转验收通过后扩展到更广的导航控制。

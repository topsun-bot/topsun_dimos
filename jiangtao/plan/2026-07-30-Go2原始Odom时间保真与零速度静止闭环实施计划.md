# Go2 原始 Odom 时间保真与零速度静止闭环实施计划

创建日期：2026-07-30

适用分支：`jtlinux`

适用场景：Go2 真机通过 LocalSTA 或 Remote/4G WebRTC 执行原地转向、空间记忆寻物、房间扫描和导航控制。

## 1. 目标

解决当前控制链路中的两个问题：

1. Go2 原始 Odom 已带采样时间，但 `dimos/robot/unitree/connection.py` 会将 `odom.ts` 改写为主机当前时间。这个覆盖逻辑是图像与 Odom 按同一主机时间轴配对所必需的；问题在于原始采样时间没有作为下游可用元数据保留，控制器无法判断自己读到的是新采样，还是刚刚到达的旧采样。
2. `rotate_in_place_degrees()` 在发送零速度后只固定等待 `0.35s` 就返回。`move(zero)` 成功只说明本机提交发送未报错，不能说明 Go2 已停止转动。

本次改造的目标不是声称获得 Go2 的设备执行 ACK，而是建立一个可证伪的本地闭环：**只有收到停止命令之后采样的新姿态，且连续一段时间推算角速度足够小，才允许系统认为“已静止”并进入下一步视觉确认。**

## 2. 当前事实与设计约束

### 2.1 已确认的代码事实

当前 Odom/图像同步链路：

```text
Go2 ROBOTODOM header.stamp
  -> Odometry.from_msg() 写入 Pose.ts
  -> connection_raw_odom 记录 source_ts / host_rx_ts
  -> time_is_now() 覆盖 Pose.ts 为主机 time.time()
  -> world -> base_link TF
  -> 旋转控制器 / 路径控制器读取 TF

相机 VideoFrame
  -> Image.ts 也写为主机 time.time()
  -> NavigationSkillContainer 以 image.ts 与 Pose.ts 最近邻配对
```

`NavigationSkillContainer._build_search_snapshot()` 当前以 `abs(pose.ts - image.ts)` 选择拍照时最近的位姿。这条主机时间轴用于沿途寻物截图、VLM 延迟回退、图片保存和二次确认，必须保持不变。

当前旋转结束链路：

```text
remaining 进入容差
  -> move(zero_twist)
  -> sleep(0.35s)
  -> 返回 ok=True
```

日志已反复证明 `host_rx_ts - source_ts` 存在动态变化和突发到达，但 Go2 header 的时钟域仍是 `unitree_header_unverified`。因此：

- 不能将绝对 `host_rx_ts - source_ts` 直接命名为网络延迟。
- 不能用一个固定的跨设备秒数阈值判断“旧 Odom”。
- 可以利用同一条 source 时间序列的单调性、采样间隔，以及相对稳定基线之上的额外变化，判断动态滞后风险。
- `LOW_STATE` 的当前 Remote WebRTC 类型只明确包含 IMU `rpy`，没有可直接依赖的 gyro/yaw-rate 字段；首版静止判定不能假设它可用。

### 2.2 不改变的边界

- 不修改地图坐标系、重定位 TF、空间记忆地标坐标或 VLM 业务逻辑。
- 保留 Odom、图像和 TF 当前的主机时间同步语义；不改变 `Pose.ts` 的含义。
- 不以 WebRTC `send` 成功作为执行确认。
- 不在控制回调或 WebRTC 回调中同步写磁盘或等待日志。
- 不一次性把新的反馈门禁强制用于全部路径导航；先在原地旋转验证通过后再扩展。
- 任何“不确定”状态都保持或重复下发零速度，不继续旋转，不触发视觉“找到”或打招呼。

## 3. 目标状态机

### 3.1 Odom 状态模型

为每一条 Odom 建立不可覆盖的时间来源信息：

```text
OdomFeedback
  sequence                    # 主机收到原始 Odom 时递增
  source_ts                   # Go2 原始 header 时间，永不改写
  host_rx_wall_ts             # 主机原始回调墙钟，仅用于与 source 建立关系
  host_rx_monotonic_ns        # 主机收到数据的单调时间
  pose_ts                     # 现有 Pose.ts，主机时间轴，用于图像/Odom 对齐
  tf_published_monotonic_ns   # 写入 TF 缓存的单调时间
  pose / yaw
  baseline_delta_s            # 运行内稳定基线估计
  excess_delay_s              # host-source 相对基线的额外变化
  freshness_state             # FRESH / DELAYED / CLOCK_UNCERTAIN / INVALID
```

`Pose.ts` 继续保持当前的主机时间值，确保与 `Image.ts` 可直接比较。`source_ts` 仅保存在旁路 `OdomFeedback` 中。为避免给现有 LCM `PoseStamped` 临时挂 Python 属性，时间来源信息通过新的强类型缓存/RPC 接口传递给需要做安全判断的控制器；不能改变现有消息的图像/Odom 配对行为。

首版不要求全局规划器立刻消费该接口，但 TF、odom 发布和旋转控制必须能够追溯到同一条 `sequence`。

### 3.2 原地转向状态机

```text
ROTATING
  -> 达到角度容差或超时
ZERO_SENT
  -> 只下发零速度，不宣布停止
WAITING_FOR_FRESH_ODOM
  -> 丢弃零命令之前采样的历史 Odom
  -> 反馈异常暂停时：拿到新鲜 Odom 后重新计算 remaining，再决定是否继续旋转
  -> 正常转到目标时：拿到新鲜 Odom 后进入 SETTLING
SETTLING
  -> 连续采样计算 yaw 角速度与 yaw 波动
SETTLED
  -> 返回成功，允许后续视觉确认
UNCONFIRMED_STOP / TIMEOUT
  -> 保持零速度，返回失败，禁止后续到达动作
```

`SETTLED` 不是“机器人已收到设备 ACK”，而是“在可观测反馈内，机器人已出现连续的新低角速度状态”。日志必须保留这一语义。

### 3.3 Odom 不新鲜的精确判定与控制动作

旋转控制是 20 Hz，而真机 Odom 约 18 Hz。因此一个控制 tick 读到与上一 tick 相同的 `sequence` 是正常现象，**不能仅因 sequence 单次重复就发零速度**。判定必须以“最后一条合格 Odom 到控制器的本机单调时间间隔”作为宽限条件。

每个控制 tick 都为当前关联的 `OdomFeedback` 计算以下字段：

```text
local_feedback_age_s = controller_read_monotonic - host_rx_monotonic
source_interval_s     = source_ts_i - source_ts_(i-1)
D_i                   = host_rx_wall_ts_i - source_ts_i
excess_delay_s        = D_i - baseline
```

其中 `baseline` 是同一次连接、source 时间连续且接收节奏稳定样本的低分位稳定簇；它代表“固定时钟关系 + 最低链路耗时”的合量，不被命名为网络延迟。

| 状态 | 必须满足的判断条件 | 旋转控制动作 |
|---|---|---|
| `FRESH` | provenance 关联成功；source 严格递增；source 间隔在合理范围；预热完成；`excess_delay_s <= max_excess_delay`；`local_feedback_age_s <= max_local_age` | 使用该 yaw 更新累计角度并计算下一条转向指令 |
| `GRACE_HOLD` | 上次状态为 `FRESH`；当前 sequence 尚未推进，但距上一次 FRESH 接收仍不超过 `max_no_new_odom_s` | 允许短暂保持当前转向命令，不更新 accumulated，不根据重复 yaw 重新计算角度 |
| `DELAYED` | 新 sequence 已到达，但 `excess_delay_s > max_excess_delay`；或新样本的本机本地年龄超限 | 立即发零速度，进入 `WAITING_FOR_FRESH_ODOM`；旧 yaw 不计入 achieved |
| `NO_NEW_ODOM` | sequence 未推进持续超过 `max_no_new_odom_s` | 立即发零速度，等待新 Odom；不能持续盲转 |
| `INVALID` | source 时间重复/倒退/异常跳变，或 source 间隔无法用于速度计算 | 立即发零速度，返回或等待失败；不能使用该样本 |
| `CLOCK_UNCERTAIN` | provenance 关联失败、预热未完成、基线不可用或 source 时钟语义异常 | observe 模式只记录；enforce 模式发零速度并等待，超时后返回未确认 |

初始候选配置如下，必须由 LocalSTA 和 Remote 分别标定后才能固化：

```bash
# 20 Hz 控制与约 18 Hz Odom 下，允许正常的一两次控制 tick 复用同一条 Odom。
DIMOS_ROTATE_MAX_NO_NEW_ODOM_S=0.20
DIMOS_ODOM_MAX_LOCAL_AGE_S=0.20

# 仅使用 source 的相对时间间隔，不依赖其与主机的绝对时钟同步。
DIMOS_ODOM_MIN_SOURCE_INTERVAL_S=0.02
DIMOS_ODOM_MAX_SOURCE_INTERVAL_S=0.20

# 由 observe 数据分别标定，不使用跨运行 host-source 的绝对秒数。
DIMOS_ODOM_MAX_EXCESS_DELAY_S=<待按连接方式标定>
```

`max_excess_delay` 的取值方法：先在同一连接方式的静止与正常旋转 observe 数据中统计 `excess_delay_s`，选取能够覆盖正常样本 P99、并留出有限裕量的阈值。若远程 4G 的正常 P99 已高于安全可接受控制反馈时限，则不应简单把阈值放大，而应保持零速度并将问题归类为“该连接条件不适合闭环旋转”。

### 3.4 本次运行稳定基线的精确计算

基线在连接建立后后台持续计算，不等到用户发出“转向”命令才开始。它只用于将同一次运行的固定时钟关系与动态额外滞后分开，**不修改 `Pose.ts`，不参与图像/Odom 配对。**

#### 启用时机

```text
连接 ready 且开始收到原始 Odom
  -> 收集至少 3.0 秒、且至少 40 条有效 Odom
  -> 计算首次 baseline
  -> freshness 状态从 CLOCK_UNCERTAIN 进入可判定状态
```

两项条件必须同时满足：

- `DIMOS_ODOM_FRESHNESS_WARMUP_S=3.0`
- `DIMOS_ODOM_FRESHNESS_MIN_SAMPLES=40`

按约 18 Hz Odom，通常约 3 秒即可达到 40 条；若网络差、回调慢或有效样本不足，则继续预热。`observe` 模式下只记录 `CLOCK_UNCERTAIN`；`enforce` 模式下，在基线尚未就绪时禁止开始新的闭环旋转，并保持零速度返回未确认，不能擅自把未知反馈当新反馈。

#### 有效样本筛选

只有同时满足下面条件的样本才进入基线窗口：

1. `source_ts`、`host_rx_wall_ts`、`host_rx_monotonic_ns` 均存在且有限。
2. `source_ts` 相比上一有效样本严格递增。
3. `source_interval_s` 位于 `[0.02, 0.20]` 秒；超出范围视为时间语义异常或采样不连续。
4. 当前 Odom provenance 与覆盖后的 `Pose.ts` 一一关联成功。

不要求机器人静止。基线描述的是通信/处理时间关系，正常直行或旋转期间的有效样本也可以参与；明显积压样本会通过低分位算法自然不影响基线。

#### 首次基线公式

对预热期间所有有效样本计算：

```text
D_i = host_rx_wall_ts_i - source_ts_i
baseline_0 = P10(D_i)
```

采用 P10 而不是最小值，避免偶发的过小异常值把基线拉低；也不采用中位数，避免积压样本把正常的动态余量吞进基线。`baseline_0` 的含义始终是“当前连接下接近最低的 host-source 差”，不是纯时钟偏移，也不是单向网络延迟。

#### 运行中的更新与重标定

首次基线生效后，维护最近 `60s`、最多 `2048` 条有效样本的滑动窗口，每 `1s` 更新一次：

```text
candidate_baseline = P10(D_window)
```

更新规则：

1. 若 `abs(candidate_baseline - baseline) <= 0.10s`，直接更新为 `candidate_baseline`。
2. 若差值大于 `0.10s`，不立刻把新值用于控制；记录 `BASELINE_SHIFT`，清空基线状态并重新执行 `3.0s + 40条有效样本` 预热。
3. 重连、source 时间倒退/跳变、连接方法从 LocalSTA 切换到 Remote 时同样强制重新预热，不能沿用旧基线。
4. 重标定期间状态为 `CLOCK_UNCERTAIN`；enforce 模式保持零速度，observe 模式只记录。

这样可以处理时钟/NTP 或连接状态突变，避免把旧连接条件的基线错误套到新的数据流。

#### 单样本新鲜度计算

在基线有效时，对每个新样本计算：

```text
excess_delay_s = max(0, D_i - baseline)
```

控制器不根据单个 `D_i` 的绝对大小作结论，只根据：

```text
source 是否连续
AND provenance 是否关联成功
AND local_feedback_age 是否在限值内
AND excess_delay 是否在该连接方式已标定阈值内
```

的组合结果判为 `FRESH` 或 `DELAYED`。

## 4. 实施方案

### 阶段 A：时间来源保真与旁路反馈缓存

涉及文件：

- `dimos/robot/unitree/connection.py`
- `dimos/robot/unitree/go2/connection.py`
- `dimos/robot/unitree/go2/connection_spec.py`
- 新增 Odom 时间来源类型与单元测试

实施内容：

1. 保留真机 `odom_stream()` 中现有 `time_is_now()` 覆盖逻辑；图像和 Odom 继续使用同一主机时间轴。
2. 在调用 `time_is_now()` **之前**生成单调递增的 `sequence`、`source_ts`、主机墙钟和主机单调接收时间；覆盖后保存对应的 `pose_ts`。解析完成、TF 发布完成时补齐对应的单调时间。
3. 在 `Go2Connection` 模块缓存最近一条 `OdomFeedback`，并以明确的 RPC/Spec 方法暴露给 `UnitreeSkillContainer`。返回值必须包含采样时间、接收时间、sequence、yaw 和 freshness 判断，不能只返回裸 TF。
4. 保留现有 `connection_raw_odom` trace，但增加 `sequence`、TF 发布 sequence、控制器消费 sequence 等关联字段。
5. 所有同主机时延使用 `time.monotonic_ns()`；`source_ts` 与主机墙钟仅用于建立运行内相对基线。

兼容性审计：

- 回归检查 `Pose.ts` 与 `Image.ts` 的最近邻配对，尤其是沿途寻物 `_build_search_snapshot()`、VLM 延迟回退、TF 缓存、Rerun、导航 trace 和回放代码。
- Replay、MuJoCo、DimSim 后端没有原始 Unitree source clock 时，构造明确的 `CLOCK_UNCERTAIN` 或模拟实现，不得伪造真机新鲜度。
- 原始 source 时间的旁路缓存必须在 Go2Connection 工作进程内与已覆盖时间的 Pose 一一关联；关联失败时 freshness 为 `CLOCK_UNCERTAIN`，不得猜测或错配到另一帧。

### 阶段 B：运行内新鲜度估计器

新增一个小型、无阻塞的 `OdomFreshnessEstimator`，仅维护有限窗口，不做文件 IO。

计算规则：

```text
D_i = host_rx_wall_ts_i - source_ts_i
baseline = 稳定、单调样本中 D_i 的低分位稳定簇
excess_delay_i = D_i - baseline
```

判定条件：

- `source_ts` 必须严格推进，且相邻间隔处于合理范围；重复、倒退、巨大跳变进入 `INVALID`。
- 在完成最小预热样本数前，仅报告 `CLOCK_UNCERTAIN`，不强制停车。
- `excess_delay_s` 超出配置阈值时标记 `DELAYED`；阈值以实际 LocalSTA/Remote 分开标定，不使用跨运行的绝对 `host-source` 秒数。
- 接收序号虽递增、但 source 时间明显落后于零命令前的时间水位时，该样本不能证明停止后的姿态。
- 控制频率高于 Odom 频率时，同一 sequence 在短宽限窗口内仅为 `GRACE_HOLD`；只有超过 `max_no_new_odom_s` 才判为 `NO_NEW_ODOM` 并发送零速度。

估计器应输出原因码，例如：`WARMUP`、`SOURCE_NON_MONOTONIC`、`EXCESS_DELAY`、`POST_STOP_SOURCE_NOT_REACHED`、`FRESH`，便于日志和测试判断。

### 阶段 C：零速度发送与静止确认

涉及文件：

- `dimos/robot/unitree/unitree_skill_container.py`
- `dimos/robot/unitree/go2/connection.py`
- 必要时 `dimos/robot/unitree/connection.py`

将当前旋转结束处的 `move(zero) + sleep(0.35)` 替换为统一的私有流程 `_send_zero_and_wait_for_settle()`：

1. 记录最后一个非零控制命令的 ID、值、生成时间、发送开始/完成单调时间。
2. 显式下发零 Twist，记录零命令 ID、`move()` 返回值、WebRTC send 事件关联 ID；发送异常立即进入失败路径。
3. 从零命令开始，以受限频率重复显式零 Twist，直到确认静止或超时，避免上一摇杆值被继续保持；不能依赖当前只取消 timer 的 `stop_movement()` watchdog 行为。
4. 记录零命令前的 `source_ts` 水位、sequence、主机单调时间和运行内 source-to-host 基线；只接受 sequence 增大、source 时间严格推进、且按该基线估计的采样时刻不早于零命令安全界限的新 Odom。
5. 对连续合格 Odom 用 source 时间差计算 yaw 角速度；若 source 时间间隔异常，不计算角速度，也不能进入 `SETTLED`。
6. 同时要求：
   - 至少 `N` 条停止后新 Odom；
   - 连续稳定窗口内 `abs(yaw_rate)` 小于阈值；
   - 同窗口 yaw 总波动小于阈值；
   - 每条样本 freshness 为 `FRESH`；
   - 稳定持续时间达到最小值。
7. 满足全部条件才返回 `SETTLED`；超时或反馈异常返回 `UNCONFIRMED_STOP`，保持零速度并使 `rotate_in_place_degrees()` 返回 `False`。

首版不把 `LOW_STATE.rpy` 作为静止成功条件。额外记录原始 LOW_STATE payload 和到达时间；若真机确认其中稳定提供 gyroscope/yaw-rate，再以独立、可选的第二证据接入，而不是替换 Odom 判据。

### 阶段 D：控制器接入与业务保护

1. `rotate_in_place_degrees()` 继续从 TF 读取当前姿态值，但同时读取同 sequence 的 `OdomFeedback`；TF 的 `Pose.ts` 继续服务于图像同步，不能单独作为新鲜度证据。
2. 反馈 `DELAYED`、`INVALID`，或 sequence 未推进超过 `max_no_new_odom_s` 时，立即进入 `ZERO_SENT`，不再根据旧 yaw 累积 `achieved` 或继续下发非零转向。短宽限内的正常 sequence 重复仅进入 `GRACE_HOLD`，不误停。
3. `rotate_in_place_degrees()` 只有在 `SETTLED` 后才可返回成功。
4. 调用旋转的视觉伺服、房间扫描、沿途命中、历史物体点确认自动继承该失败结果；不触发视觉确认成功、JPG 保存或打招呼。
5. 路径导航控制器第一期只记录 freshness，不改变运行行为；待原地旋转真机验收完成后，以独立开关接入相同门禁，避免一次修改影响现有导航链路。

### 阶段 E：配置、日志和故障降级

建议配置项：

```bash
# 默认 observe：只记录，不改变现有动作；真机验收后才明确启用 enforce。
DIMOS_ODOM_FRESHNESS_MODE=observe           # observe | enforce
DIMOS_ODOM_FRESHNESS_WARMUP_S=3.0
```

日志要求：

- 只写入有界 navigation trace，使用小型标量事件和后台 writer；控制线程不能被日志阻塞。
- 每个旋转周期关联 `rotation_session_id`、control tick、Odom sequence、freshness 原因、源/接收/控制单调时间。
- 每个停止阶段记录 `ZERO_SENT`、首个合格新 Odom、每个 yaw-rate 样本、最终结果和失败原因。
- 明确区分 `local_send_completed`、`fresh_feedback_observed`、`settled_by_odom`；禁止记录成不存在的 `robot_execution_ack`。

## 5. 测试计划

### 5.1 单元测试

1. Odom 经 `odom_stream -> TF -> odom publish` 后，`Pose.ts` 仍与同一时刻的 `Image.ts` 可最近邻配对；原始 `source_ts` 在旁路 `OdomFeedback` 中保持不变。
2. `OdomFeedback.sequence` 单调，source/接收/覆盖后的 `Pose.ts` 与 TF 发布时间可关联。
3. 固定时钟偏移但 source/host 节奏正常：判为 `FRESH`，不误触发停车。
4. source 时间正常、host 突发接收历史帧：判为 `DELAYED`。
5. 单次或短时间 sequence 重复但不超过宽限：判为 `GRACE_HOLD`，不发送零速度。
6. sequence 未推进超过宽限：判为 `NO_NEW_ODOM`，发送零速度。
7. source 时间倒退、重复、跳变：判为 `INVALID`，不能计算 yaw-rate。
8. 零命令后只有旧 source 时间的 Odom：不能进入 `SETTLED`。
9. 零命令后连续新 Odom 且 yaw-rate、yaw span 均合格：进入 `SETTLED`。
10. yaw-rate 长期高于阈值、反馈延迟、无新 Odom、发送异常：返回 `UNCONFIRMED_STOP` 并持续零速度。
11. observe 模式完全不改变当前旋转命令序列；enforce 模式在异常反馈时停止非零旋转。
12. TraceSink 满、写入失败或禁用时，不影响命令发送和控制频率。

### 5.2 回放与模拟测试

- 使用现有 `raw_odometry_rotate_walk` 回放，验证时间保真、yaw-rate 计算和状态机转换。
- 构造带固定时钟偏移、动态积压、burst、重复帧、无 Odom 的确定性输入。
- MuJoCo/DimSim 明确走模拟 freshness 适配，不因缺少 Unitree header 误报失败。

### 5.3 真机分阶段验收

1. **observe 模式**：LocalSTA 与 Remote 各完成静止、20°、60°、120° 旋转测试；验证新 trace 完整、无控制周期退化。
2. **enforce 模式，仅旋转**：人工制造正常网络和弱网场景；旧 Odom 时必须先零速度，且不得继续积累旧 yaw。
3. **停止确认**：每次旋转结束后检查日志中至少有 `ZERO_SENT -> post-stop fresh odom -> SETTLED`；不能只有 `move(zero)`。
4. **空间记忆寻物回归**：标记房间、到历史位置、VLM 转向、二次确认；任何 `UNCONFIRMED_STOP` 均不得打招呼或回复找到。
5. **性能 A/B**：diagnostics off / observe / enforce 分别比较控制周期、WebRTC heartbeat、Odom 接收率、TraceSink drop 数和旋转总耗时。

验收条件：

- 现有正常网络下，enforce 不应频繁误停；阈值和触发率必须有实测记录。
- 出现动态反馈异常时，日志可定位到 source、接收、TF、控制、零命令和静止判断的完整链路。
- 没有连续新且低角速度反馈时，不得返回旋转成功。
- 诊断打开后控制周期、WebRTC heartbeat 和相机/Odom 接收率不出现不可接受退化。

## 6. 上线顺序与回滚

1. 合入时间来源与 observe 日志，默认不改变控制行为。
2. 完成回放和 LocalSTA/Remote observe 真机基线，分别确定 `excess_delay` 阈值。
3. 只为 `rotate_in_place_degrees()` 打开 enforce 和静止确认。
4. 完成寻物二次确认回归后，再评估是否把 freshness 门禁接入路径跟随控制器。
5. 保留 `DIMOS_ODOM_FRESHNESS_MODE=observe` 作为即时回滚开关；回滚只关闭门禁，不回退原始时间保真和诊断证据。

## 7. 风险与决策点

| 风险 | 应对 |
|---|---|
| 原始 source 时间改变 TF/Rerun/回放消费者行为 | 先做全量消费者审计和回放测试；必要时为旧消费者提供显式主机接收时间适配器 |
| 跨设备时钟差导致错误 freshness 判定 | 只用运行内稳定基线的额外变化；预热不足或 source 异常时进入不确定状态，不声称网络延迟 |
| 严格门禁导致旋转常常超时 | 先 observe 标定；enforce 仅用于旋转；超时保持零速度并记录原因，不盲目放宽阈值 |
| Odom 停止但物理机身仍有残余旋转 | 首版明确为 Odom 闭环；记录 LOW_STATE，后续确认 gyro 可用后加入第二证据 |
| 高频日志影响真机 | 复用有界异步 TraceSink，控制路径仅写小型标量，队列满时丢诊断而不阻塞控制 |

## 8. 完成定义

本计划完成不等于“网络延迟被消除”。完成定义是：

1. Odom 主机时间覆盖与图像/Odom 对齐逻辑保持不变；控制器可通过旁路元数据追溯每次使用的原始反馈来源。
2. 零速度后有明确的、基于连续新 Odom 的静止确认或未确认结果。
3. 反馈旧、缺失、异常时，旋转不会继续用旧 yaw 推进，也不会误报旋转成功。
4. 新行为仅在真机旋转验收通过后扩展到更广的导航控制。

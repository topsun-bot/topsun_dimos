# Go2 单楼层地图绑定固定点巡航实施计划

创建日期：2026-07-15

目标：基于已有 Go2 / DimOS 导航、地图录制和重定位代码，完成一套可跨启动复用的单楼层固定点巡航 baseline。系统支持不少于 5 个固定巡航点，能够加载指定楼层地图并完成重定位，连续巡航 30 分钟不中断，同时输出逐点结果和失败原因记录。

## 1. 验收目标

本计划最终需要满足以下条件：

- 使用 `unitree-go2-memory` 完成一楼原始数据录制。
- 从录制数据库导出经过 PGO 优化的 `.pc2.lcm` 预地图。
- 5 个巡航点保存为最终预地图 `map` 坐标系下的位姿，而不是某一次启动的 `world`/`odom` 坐标。
- 地图文件和路线文件通过唯一 `map_key` 绑定，避免加载错误楼层或错误版本的路线。
- 下次启动时自动加载地图，等待重定位成功后再启动巡航。
- 支持 `P1 -> P2 -> P3 -> P4 -> P5 -> P4 -> P3 -> P2 -> P1` 往返模式。
- 单点失败、目标超时或短时路径阻挡不会让整个巡航永久卡住。
- 连续运行不少于 30 分钟，无进程重启、无人工接管。
- 每个目标点均记录开始、到达、失败、重试、跳过及耗时。
- 失败事件必须包含机器可统计的原因字段，并输出本次巡航 summary。

## 2. 当前已有能力

### 2.1 地图录制

`unitree-go2-memory` 已组合 Go2 导航栈和 `Go2Memory`，默认把以下数据写入 `recording_go2.db`：

- `lidar`
- `odom`
- `color_image`
- TF

数据库路径可以通过以下参数指定：

```bash
-o go2memory.db_path=<path>
```

### 2.2 地图导出

项目已有离线地图导出命令：

```bash
dimos map global <database> --export
```

`--export` 会执行 PGO，并生成 `<database>.pc2.lcm`。由于 PGO 会校正建图轨迹，第一次建图过程中直接读取的原始 `/odom` 坐标不能直接作为最终巡航点坐标。

### 2.3 地图加载与重定位

`unitree-go2-relocalization` 已支持：

- 加载 `.pc2.lcm` 预地图。
- 把预地图统一设置为 `map` 坐标系。
- 使用实时局部点云计算 `map <- world` 配准结果。
- 发布并缓存当前有效的 `world <- map` 变换。
- 提供 `get_current_map_key()`、`get_current_map_file()`、`get_world_to_map()` 和 `is_relocalized()` RPC。

### 2.4 地图坐标转换

`NavigationSkillContainer._map_metadata_for_pose()` 已实现以下转换：

```text
当前机器人 world 位姿
  -> 使用重定位得到的 world <- map 变换取逆
  -> 转换为最终预地图中的 map 位姿
```

该逻辑可以复用到巡航点录制，不需要重新设计坐标变换。

### 2.5 当前固定巡航缺口

当前项目还缺少：

1. 保存当前位置为固定巡航点的接口。
2. 地图文件和固定路线文件的绑定格式。
3. 固定点顺序或往返巡航 router。
4. 重启后将 `map` 点转换到本次 `world` 坐标并下发的流程。
5. 单点 timeout、retry、skip 和失败原因日志。
6. 5 点跨启动复现和 30 分钟真机验收。

## 3. 地图包设计

每层楼保存为一个独立目录：

```text
data/floor_maps/floor_1/
├── floor_1.db
├── floor_1.pc2.lcm
├── patrol.yaml
└── patrol_runs/
```

文件职责：

- `floor_1.db`：原始建图录制，主要用于重新导图和问题复现。
- `floor_1.pc2.lcm`：运行时加载的最终 PGO 预地图。
- `patrol.yaml`：该地图对应的固定巡航点和路线参数。
- `patrol_runs/`：真机巡航日志和 summary，默认不提交仓库。

建议的 `patrol.yaml`：

```yaml
version: 1
map_key: floor_1
map_file: floor_1.pc2.lcm
frame_id: map
route_name: floor_1_baseline
mode: ping_pong

settings:
  goal_timeout_sec: 90
  max_retries: 2
  continue_on_failure: true

waypoints:
  - name: P1
    position: [0.0, 0.0, 0.0]
    orientation: [0.0, 0.0, 0.0, 1.0]

  - name: P2
    position: [0.0, 0.0, 0.0]
    orientation: [0.0, 0.0, 0.0, 1.0]

  - name: P3
    position: [0.0, 0.0, 0.0]
    orientation: [0.0, 0.0, 0.0, 1.0]

  - name: P4
    position: [0.0, 0.0, 0.0]
    orientation: [0.0, 0.0, 0.0, 1.0]

  - name: P5
    position: [0.0, 0.0, 0.0]
    orientation: [0.0, 0.0, 0.0, 1.0]
```

约束：

- `frame_id` 第一版只接受 `map`。
- `orientation` 使用四元数 `[x, y, z, w]`。
- `map_key` 必须与 `RelocalizationModule.get_current_map_key()` 一致。
- YAML 采用临时文件加原子替换方式写入，避免录点过程中断导致文件损坏。
- 大型 `.db` 和 `.pc2.lcm` 是否提交仓库，需要先确认项目 LFS 规则；路线 YAML 可以正常提交。

## 4. 正确的建图和录点流程

### 4.1 第一次运行：录制一楼

```bash
mkdir -p data/floor_maps/floor_1

dimos --robot-ip 192.168.12.1 run unitree-go2-memory \
  -o go2memory.db_path=data/floor_maps/floor_1/floor_1.db
```

真机操作要求：

- 从容易重复到达、几何特征明显的位置开始。
- 遥控覆盖完整巡航区域。
- 走廊、拐角、门口和开阔区域都要有足够点云。
- 尽量形成闭环，给 PGO 提供回环机会。
- 建图过程中先不把原始 `/odom` 数值当成最终巡航点。

### 4.2 导出最终 PGO 地图

```bash
cd data/floor_maps/floor_1
dimos map global floor_1.db --export --no-gui
```

检查：

- 生成 `floor_1.pc2.lcm`。
- 地图无明显重影、断层或楼层错位。
- 目标巡航区域在地图中完整可见。
- PGO 后轨迹与主要墙面、走廊方向一致。

### 4.3 第二次运行：加载最终地图并示教录点

先加载地图：

```bash
dimos --robot-ip 192.168.12.1 run unitree-go2-relocalization \
  -o relocalizationmodule.map_file=data/floor_maps/floor_1/floor_1
```

录点前必须满足：

- 日志出现成功的 `relocalize` 结果。
- `is_relocalized()` 返回 `true`。
- Rerun 中实时局部点云和预地图基本重合。

然后用遥控器依次到达 P1 至 P5，每次停稳后调用计划新增的接口：

```bash
dimos mcp call save_patrol_waypoint --arg route=floor_1 --arg name=P1
dimos mcp call save_patrol_waypoint --arg route=floor_1 --arg name=P2
dimos mcp call save_patrol_waypoint --arg route=floor_1 --arg name=P3
dimos mcp call save_patrol_waypoint --arg route=floor_1 --arg name=P4
dimos mcp call save_patrol_waypoint --arg route=floor_1 --arg name=P5
```

这些命令是本计划需要新增的目标接口，当前尚未实现。

## 5. 代码设计

### 5.1 路线数据模型和存储

建议新增：

```text
dimos/navigation/patrolling/route.py
dimos/navigation/patrolling/waypoint_store.py
```

主要类型：

- `PatrolWaypoint`
- `PatrolRouteSettings`
- `PatrolRoute`
- `WaypointStore`

职责：

- 使用结构化模型解析 YAML。
- 校验版本、`map_key`、坐标有限性、四元数和点位名称唯一性。
- 保存、覆盖、删除和列出 waypoint。
- 保留 YAML 中稳定的点位顺序。
- 原子写文件。

### 5.2 录点接口

在 `PatrollingModule` 中复用已有 `_latest_pose`，并注入可选的 `RelocalizationStateSpec`。

新增接口：

```python
save_patrol_waypoint(route: str, name: str) -> str
list_patrol_waypoints(route: str) -> str
delete_patrol_waypoint(route: str, name: str) -> str
clear_patrol_waypoints(route: str) -> str
```

`save_patrol_waypoint()` 执行顺序：

1. 确认收到最新 `odom`。
2. 确认当前存在 `RelocalizationModule`。
3. 确认 `is_relocalized()` 为真。
4. 读取 `map_key` 和 `world <- map`。
5. 把当前 `world` 位姿转换为 `map` 位姿。
6. 校验路线文件中的 `map_key`。
7. 新增或显式覆盖同名点位。
8. 写入 `patrol.yaml`。
9. 返回点名、map 坐标和路线文件路径。

拒绝保存的情况：

- 尚未收到 odom。
- 尚未成功重定位。
- 变换矩阵不存在或包含非法值。
- 路线绑定了其他 `map_key`。
- 同名点已经存在且调用方没有确认覆盖。

### 5.3 固定点 router

建议新增：

```text
dimos/navigation/patrolling/routers/fixed_patrol_router.py
```

支持两种顺序：

```text
loop:
P1 -> P2 -> P3 -> P4 -> P5 -> P1 -> ...

ping_pong:
P1 -> P2 -> P3 -> P4 -> P5 -> P4 -> P3 -> P2 -> P1 -> ...
```

router 只维护路线顺序和当前索引，不直接负责导航、重定位或日志。

### 5.4 下发目标前的坐标转换

路线文件永久保存 `map` 坐标，但当前规划器运行在本次启动的 `world` 坐标中。

每次下发目标时都执行：

```text
T_world_goal = T_world_map_current * T_map_goal
```

要求：

- 不在启动时一次性转换全部点位。
- 每次下发目标前读取最新的已验证重定位变换。
- `map_key` 不一致时停止巡航并记录 `map_mismatch`。
- 重定位暂时不可用时进入等待或恢复状态，不直接使用旧的原始 odom 坐标。

### 5.5 固定巡航生命周期

新增接口：

```python
start_fixed_patrol(route: str, mode: str = "ping_pong") -> str
stop_fixed_patrol() -> str
get_fixed_patrol_status() -> str
```

启动顺序：

```text
加载 patrol.yaml
  -> 校验至少 5 个点
  -> 校验当前 map_key
  -> 等待重定位成功
  -> 选择第一个目标
  -> map 点转换为当前 world 点
  -> 下发目标并启动 watchdog
```

到点后选择下一个目标。停止时取消当前目标、关闭 watchdog、恢复规划器设置并输出 summary。

### 5.6 目标结果、timeout 和恢复

当前 `PatrollingModule.handle_goal_reached()` 不能忽略 `Bool.data`。计划调整为：

- `Bool(data=True)`：当前点成功到达，进入下一点。
- `Bool(data=False)`：当前点失败或取消，不算到达。

每个目标增加：

- `goal_timeout_sec`
- `max_retries`
- `continue_on_failure`

默认策略：

```text
目标成功
  -> 记录 reached
  -> 下一个点

目标失败或超时
  -> 取消当前 goal
  -> 记录失败原因
  -> 当前点重试，最多 2 次
  -> 仍失败则记录 skipped
  -> 继续下一个点
```

阻挡恢复需要保持 A* 重规划可用。固定点巡航不应沿用当前 coverage patrol 中无条件关闭 replanning 的行为。

### 5.7 巡航日志

建议每次巡航生成一个 JSONL 和一个 summary JSON：

```text
data/floor_maps/floor_1/patrol_runs/<run_id>.jsonl
data/floor_maps/floor_1/patrol_runs/<run_id>-summary.json
```

JSONL 每条事件至少包含：

```json
{
  "ts": 0.0,
  "run_id": "...",
  "route": "floor_1_baseline",
  "map_key": "floor_1",
  "event": "goal_started",
  "waypoint": "P1",
  "attempt": 1,
  "elapsed_sec": 0.0,
  "result": null,
  "reason": null
}
```

建议事件：

- `patrol_started`
- `relocalization_waiting`
- `relocalization_ready`
- `goal_started`
- `goal_reached`
- `goal_failed`
- `goal_timeout`
- `goal_retry`
- `goal_skipped`
- `patrol_stopped`
- `patrol_completed`

失败原因枚举：

- `no_odom`
- `relocalization_unavailable`
- `map_mismatch`
- `route_invalid`
- `planner_rejected`
- `navigation_failed`
- `goal_timeout`
- `path_blocked`
- `robot_stuck`
- `cancelled`
- `internal_error`

summary 至少输出：

- 运行开始、结束和总时长。
- 成功到达次数。
- 失败次数。
- 重试次数。
- 跳过点数量。
- 每个 waypoint 的成功率和平均耗时。
- 按失败原因分类的计数。
- 是否满足 30 分钟验收条件。

## 9. 关键风险

### 9.1 把原始 odom 当成最终地图坐标

风险：PGO 后地图发生校正，点位与地图不一致。

处理：只允许在最终预地图加载且重定位成功后，把当前位置转换成 `map` 坐标保存。

### 9.2 重定位未成功就开始巡航

风险：同一个坐标落到错误物理位置。

处理：`start_fixed_patrol()` 必须硬检查 `is_relocalized()` 和 `map_key`。

### 9.3 使用启动时的一次变换转换全部点位

风险：后续重定位更新后，目标仍使用旧变换。

处理：每次下发 waypoint 前读取最新有效变换。

### 9.4 目标失败事件被当成到达

风险：当前 `handle_goal_reached()` 忽略 `Bool.data`，可能错误切换到下一点。

处理：显式区分成功、失败和取消，并由 watchdog 统一管理目标生命周期。

### 9.5 固定巡航关闭 replanning

风险：临时阻挡或偏航后无法恢复。

处理：固定点巡航保留 replanning；coverage patrol 的配置不直接套用到 fixed patrol。

### 9.6 地图质量不足

风险：重定位长期达不到 fitness 阈值，后续所有点位功能都无法稳定验证。

处理：先把“地图可重复加载并完成重定位”作为 P1 录点前置验收，不把地图问题混入巡航逻辑调试。

## 11. 完成定义

只有同时满足以下条件，才能认为本目标完成：

- 一楼地图能够从指定目录加载。
- 系统能够在新启动中完成对该地图的重定位。
- 5 个点均保存为该地图的 `map` 坐标。
- 路线文件与地图通过 `map_key` 正确绑定。
- 机器人能够自动按 5 点持续往返。
- 单点失败不会让巡航永久卡死。
- 连续运行不少于 30 分钟。
- 有完整 JSONL、summary 和复现步骤。

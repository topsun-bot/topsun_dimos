## 1. 问题结论

`20260731-111330` 中，到达灭火器标记点后的计划命令净和约为 `308.9°`，但：

- 原始 odom 净转约 `947.3°`，约 `2.63` 圈；
- LOW_STATE IMU 净转约 `932.4°`，约 `2.59` 圈；
- 考虑正反向修正后，累计绝对转动路径约 `1371.7°`，约 `3.81` 圈。

问题由以下行为叠加：

1. 房间搜索设计上会执行 `40° × 9 = 360°` 的完整扫描。
2. Remote 运行未设置限速时，`rotate_in_place_degrees()` 默认允许 `0.8` 的摇杆比例，反馈滞后时会继续高速下发。
3. 达到内部角度容差后只发送一次零 Twist，固定等待 `0.35s`，没有确认姿态已经停止变化。
4. `achieved` 在发送零速度前就冻结，停止后的尾部转角不计入结果。
5. 房间扫描调用方忽略部分旋转失败结果，会继续执行下一次 `40°`。
6. 本次 Remote 反馈存在最高约 `2.93s` 的动态积压；但当前 TF 时间已经被改写为主机接收时间，第一版无法严格识别原始采样新鲜度。

## 2. 本计划的目标

以最小改动实现四个结果：

1. Remote 真机未显式配置时，原地旋转不再使用 `0.8` 的激进默认值。
2. 每次原地旋转结束后持续下发零速度，直到观察到连续的新 TF 样本已经稳定，或明确失败。
3. 日志里的最终 `achieved` 包含发送零速度后的尾部转角。
4. 单步旋转未确认停稳或最终角度超差时，房间扫描立即中止，不再把误差传递给下一步。

安全目标优先于“勉强完成整圈扫描”：如果反馈或停转状态不可信，允许本次寻物失败，但不允许继续盲转。

## 4. 最小实现设计

### 4.1 Remote 真机使用保守默认最大转向比例

实施前核对当前分支，默认值已经是：

```python
max_omega = float(os.getenv("DIMOS_ROTATE_MAX_RAD_S", "0.25"))
```

因此本次不再修改最大转向比例逻辑，避免无意义地改变 LocalSTA 或 simulation
分支。Remote 仍建议在运行环境中显式设置 `DIMOS_ROTATE_MAX_RAD_S=0.25`，
防止部署配置漂移。

约束：

- `DIMOS_ROTATE_MIN_RAD_S` 默认值继续保持 `0.2`。
- `run-self.md` 中已显式设置 `DIMOS_ROTATE_MAX_RAD_S=0.25`，行为不变。
- 当前分支未设置环境变量时也不会回退到 `0.8`。
- 本次不修改变量名、默认值和外部配置接口。

### 4.2 在 `UnitreeSkillContainer` 内增加私有停转闭环

在同一个文件中新增私有方法，例如：

```python
def _stop_rotation_and_wait_for_settle(
    self,
    stop_twist: Twist,
    accumulated: float,
    last_yaw: float,
    last_tf_ts: float,
) -> tuple[bool, float, str]:
    ...
```

不新增 RPC、不修改 `GO2ConnectionSpec`、不改变公开方法签名。

建议默认参数：

```bash
DIMOS_ROTATE_SETTLE_ENABLED=true
DIMOS_ROTATE_ZERO_RESEND_HZ=10
DIMOS_ROTATE_SETTLE_MIN_SAMPLES=5
DIMOS_ROTATE_SETTLE_MIN_DURATION_S=0.35
DIMOS_ROTATE_SETTLE_MAX_YAW_RATE_DEG_S=3.0
DIMOS_ROTATE_SETTLE_MAX_YAW_SPAN_DEG=1.5
DIMOS_ROTATE_SETTLE_TIMEOUT_S=4.0
```

启用范围：

- 默认只对 Remote 真机启用。
- LocalSTA 和 simulation 第一版继续执行现有的单次零速度加 `0.35s` 等待。
- 可通过 `DIMOS_ROTATE_SETTLE_ENABLED=false` 快速关闭新逻辑。

停转流程：

```text
控制器进入角度容差
  -> 记录最后一次非零命令后的 TF ts、yaw 和 accumulated
  -> 立即发送零 Twist
  -> 在等待期间以 10 Hz 重复发送零 Twist
  -> 以 20 Hz 读取 world -> base_link TF
  -> 只处理 tf.ts 严格推进的新样本
  -> 对 yaw 做 unwrap，继续更新 accumulated
  -> 在最近稳定窗口计算 yaw span 和 yaw rate
  -> 满足样本数、持续时间、角速度和波动阈值后判为 SETTLED
  -> 超时、无新 TF 或 TF 持续变化时判为 UNCONFIRMED_STOP
```

关键规则：

1. 等待静止期间不再发送任何非零命令。
2. 重复读到同一个 `tf.ts` 不计为新样本，防止反馈停更时误判静止。
3. 发送零速度后的每个新 yaw 仍计入 `accumulated`。
4. `achieved_deg` 必须使用停稳后的最终 `accumulated`。
5. 只有同时满足以下条件才返回 `True`：
   - 状态为 `SETTLED`；
   - `abs(final_accumulated - target_rad) < tolerance_rad * 2`。
6. 若已停稳但最终角度超差，第一版直接返回 `False`，不自动反向修正，避免延迟反馈下发生振荡。
7. 超时和异常路径至少再尝试发送一小段零速度，然后返回 `False`。

这里使用 `tf.ts` 只能证明“主机收到了一条新的 TF”，不能证明 Go2 原始采样时间一定晚于零命令。因此日志名称必须使用 `new_host_tf`、`settled_by_tf`，不能写成 `device_ack` 或 `fresh_source_odom`。

#### 4.2.1 停稳判定的精确定义

每次读取 TF 时记录：

```text
sample = (tf.ts, host_monotonic, unwrapped_yaw)
```

一条样本只有满足以下条件才进入稳定窗口：

1. `tf.ts` 严格大于上一条已接受样本的 `tf.ts`；
2. yaw、时间戳均为有限值；
3. 相邻 yaw 使用 `angle_diff()` 解缠，不能直接相减跨越 `±180°`；
4. 同一 `tf.ts` 被控制循环重复读取时只算一条。

最近稳定窗口必须同时满足：

```text
accepted_samples >= 5
window_duration >= 0.35s
max(abs(pairwise_yaw_rate)) <= 3.0 deg/s
max(unwrapped_yaw) - min(unwrapped_yaw) <= 1.5 deg
```

其中：

```text
pairwise_yaw_rate =
    angle_diff(yaw_i, yaw_(i-1)) / (tf.ts_i - tf.ts_(i-1))
```

以下情况都不能判为停稳：

- 一直读取到同一个 TF；
- 没有新 TF；
- TF 时间推进但 yaw 仍持续变化；
- TF 追帧突发导致相邻样本角速度仍很大；
- 只经过固定时间，但没有满足样本和稳定窗口条件。

#### 4.2.2 停止、恢复和失败状态机

```text
ROTATING
  -> 内部累计角度进入容差
ZEROING_AND_SETTLING
  -> 立即发零速度
  -> 10 Hz 重复发零速度
  -> 最长等待 4.0s

  -> 满足稳定窗口
       -> SETTLED
       -> 复算 final_achieved / final_error
          -> abs(final_error) <= 10°
               -> ROTATION_OK
               -> 再等现有相机稳定时间 0.5s
               -> 才允许识别或下一扫描步
          -> abs(final_error) > 10°
               -> ANGLE_ERROR
               -> 中止当前扫描，不自动反向修正

  -> 4.0s 内仍未满足稳定窗口
       -> UNCONFIRMED_STOP
       -> 中止当前扫描，不自动恢复非零命令
```

时间含义：

- 正常情况下，发送零速度后最早约 `0.35s` 才可能判为停稳。
- 判为成功后仍保留当前扫描已有的 `0.5s` 相机稳定等待。
- 因此从第一次零命令到下一次识别或下一步旋转，理论最短约 `0.85s`。
- 若反馈有积压，会继续保持零速度并等待，最长 `4.0s`。
- 超过 `4.0s` 仍不稳定时，没有“再等固定几秒就盲目恢复”的逻辑。

恢复规则：

1. **当前扫描内自动恢复**：只发生在 `SETTLED` 且最终角度误差不超过 `10°` 时；恢复的是拍照/识别或下一扫描步，不是恢复上一条速度。
2. **已停稳但角度超差**：当前扫描失败，不做自动反向补偿。用户或上层以后重新发起一次寻物时，从当前真实朝向重新执行初始视角识别。
3. **未确认停稳**：当前扫描以安全错误结束。下一次任何原地旋转开始前，先复用同一个停稳判定做零速度 preflight；只有 preflight 成功才允许新的非零命令。
4. 记录一个模块内私有状态，例如 `_rotation_stop_unconfirmed`。失败时置为 `True`，下一次 preflight 成功后清除。它不进入公共消息或 RPC。
5. 不在当前失败的扫描循环里自动重试同一个角度，防止反馈积压时形成“超转—反转—再超转”的振荡。

### 4.3 房间扫描严格处理旋转失败

只修改 `_scan_room_for_object()` 中当前忽略返回值的两处调用。

保存方向修正：

```python
if not self._rotate_in_place_degrees(diff_deg):
    logger.warning(...)
    return _VisualLockResult(
        status=_VisualLockStatus.ERROR,
        message="Room scan aborted: stored-yaw rotation did not settle.",
        reason="rotation_failed",
    )
```

逐步扫描：

```python
if not self._rotate_in_place_degrees(step_deg):
    logger.warning(
        "[room_scan] aborting '%s' at step %d/%d: rotation did not settle",
        ...
    )
    return _VisualLockResult(
        status=_VisualLockStatus.ERROR,
        message="Room scan aborted: scan-step rotation did not settle.",
        reason="rotation_failed",
    )
```

这样可以保证：

- 第一步实际转成 `78°` 而不是 `40°` 时，最终角度检查失败，后续8步不会继续。
- 停止反馈不确定时，不拍运动中的图，不继续调用 VLM。
- `tag_location()` 已经检查旋转返回值，无需改变。
- 现有视觉居中链路大部分已经检查旋转返回值，不做额外重构。

控制失败不得降级成普通的“没有识别到物体”：

1. `_scan_room_for_object()` 使用已有 `_VisualLockStatus.ERROR` 返回安全错误。
2. `_visual_acquire_object()` 必须保留并向上返回该 `ERROR`，不能转成 `None`。
3. 房间遍历、历史图片回退和地标到达后的调用方遇到 `reason="rotation_failed"` 时，结束当前寻物任务，不继续下一个房间、tracking fallback 或新的移动。
4. 普通 VLM miss 仍返回 `UNCONFIRMED/None`，保持现有搜索回退行为。

这样区分的是：

```text
没看见目标 -> 可以继续安全搜索
运动控制状态不可信 -> 保持停止并结束本次任务
```

### 4.4 第一版不增加全局 360° 扫描预算

全局实际角度预算是正确的长期保护，但第一版暂不加入，原因是：

1. `NavigationSkillContainer._latest_odom` 与旋转控制使用的 TF 可能存在更新时间差。
2. 如果同时在两层维护 yaw unwrap，会增加状态一致性和测试复杂度。
3. 每步必须停稳、最终角度必须合格、失败立即中止后，已经能阻止本次日志中的误差逐步放大。

只有满足以下任一条件，才进入第二阶段增加全局预算：

- 单步全部通过，但9步扫描的最终净转仍超过 `400°`；
- 每步误差均在当前容差内，但累计偏差持续同向增长；
- 现场仍观察到扫描超过约1.1圈。

第二阶段也应优先放在 `rotate_in_place_degrees()` 返回最终角度结果之后实现；第一版不为此修改现有 `bool` RPC 签名。

### 4.5 第一版不修改全局 watchdog

本次停转重复发送由 `UnitreeSkillContainer` 局部完成，不依赖 `_on_command_timeout()`。

这是刻意的兼容策略：

- `connection.py` 的 watchdog 同时服务直行、导航和其他 Twist 调用。
- 将 watchdog 从“取消 timer”改为“发送零速度”需要独立评估竞态：旧 timer 可能在新命令后触发并错误停车。
- 在没有 command generation/token 的情况下，不应把这个全局修改混入原地旋转修复。

后续若要修 watchdog，必须单独增加命令序号并确保旧 timer 不能覆盖新命令。

## 7. 分阶段实施顺序

### 阶段 A：只实现局部停止闭环

1. 确认当前默认限速已为 `0.25`，不重复修改。
2. 增加 `_stop_rotation_and_wait_for_settle()`。

## 8. 真机验收标准

### 8.1 单次旋转

每次 `rotate_in_place_degrees()`：

- 零速度重复发送次数不少于稳定窗口所需次数；
- 下一条非零命令只能出现在上一轮 `settled_by_tf` 之后；
- `tail_after_zero_deg` 可观测并计入最终 achieved；
- 返回 `True` 时最终误差不超过 `10°`；
- 无新 TF、持续转动或最终误差超限时必须返回 `False`。

### 8.2 房间标记

`60° × 5`：

- 五次旋转均出现独立的停稳事件；
- odom实际总角度目标为 `300°`；
- 验收上限先设为 `330°`；
- 不再出现此前约 `437°` 的结果。

### 8.3 到达后的房间扫描

排除保存方向修正和视觉居中后，单纯9步扫描：

- 目标角度为 `360°`；
- 实际净转不超过 `400°`；
- 不出现未停稳就开始下一步；
- 任一步失败后不再继续下发剩余扫描命令；
- 完整寻物流程不超过约1.1圈扫描，再加必要的有限视觉居中。

### 8.4 回归

- LocalSTA 行为与修改前一致。
- Simulation 行为与修改前一致。
- 正常直行、路径导航、避障和到达判定不发生变化。
- VLM识别失败仍可继续下一扫描视角，但前提是该次旋转已经确认成功。
- `tag_location()` 仍能在旋转失败时停止后续全景拍摄。

## 9. 回滚与降级

## 10. 升级到完整方案的触发条件

最小方案验收后，如果仍发生以下任一现象，则停止继续堆局部阈值，转入
`2026-07-30-Go2原始Odom时间保真与零速度静止闭环实施计划.md`：

4. 反馈积压期间 TF 的主机时间持续推进，导致第一版无法区分历史反馈和实时反馈。
5. 需要把同样的新鲜度门禁扩展到路径导航或其他运动控制。

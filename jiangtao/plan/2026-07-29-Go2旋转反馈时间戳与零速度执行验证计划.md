# Go2 旋转反馈时间戳与零速度执行验证计划

创建日期：2026-07-29

适用分支：`jtlinux`

适用场景：Go2 真机通过 LocalSTA 或 Remote/4G WebRTC 执行空间记忆寻物、视觉对准和原地旋转。

## 1. 目标与边界

本计划不是直接修改旋转控制器，而是先验证下面三个判断是否成立：

1. `host_rx_ts - source_ts` 的变化究竟来自传输/处理积压、Go2 与 主机 的时钟偏移，还是两者共同作用。
2. Go2 原始 odom header 时间戳是否真的不可靠，以及当前把 `odom.ts` 改写为 主机 当前时间是否合理。
3. 发出速度命令以后，如何判断命令是否送出、Go2 是否执行、机身是否真正旋转。

第一阶段只增加旁路诊断，不修改以下行为：

- 不改变 `rotate_in_place_degrees()` 的控制频率、比例系数、最小角速度、停止阈值和超时。
- 不改变 odom、TF、Twist 的消息结构和现有下游时间戳。
- 不改变 WebRTC 发送顺序、DataChannel 配置或运动模式。
- 不把“发送成功”当作“机器人已经执行”。
- 不在证据不足时启用“反馈过旧就停转”的新规则。

最终解决方案必须等验证结果出来后再决定。本计划末尾只给出条件化的初步方向。

## 2. 当前代码已经确认的事实

### 2.1 odom 时间戳链路

当前链路为：

```text
Go2 rt/utlidar/robot_pose
  -> data.header.stamp
  -> Odometry.from_msg() 写入 odom.ts
  -> connection_raw_odom 旁路记录原始 source_ts
  -> time_is_now() 把 odom.ts 改为 Mac 的 time.time()
  -> Transform.from_pose()
  -> world -> base_link TF
  -> rotate_in_place_degrees() 读取 yaw
```

因此以下结论已经由代码确认：

- Go2 原始消息包含 `{sec, nanosec}`。
- `Odometry.from_msg()` 确实先把这个值写入 `odom.ts`。
- `odom_stream()` 随后确实用 `time.time()` 覆盖该值。
- 旋转控制器通过 TF 只能看到覆盖后的时间，当前无法直接判断姿态的原始采样时间和新鲜度。

但以下结论尚未确认：

- Go2 的 header 时间一定代表传感器采样时间。
- Go2 与 Mac 的 Unix 时钟已经同步。
- `host_rx_ts - source_ts=3.8s` 就等于 3.8 秒网络延迟。
- 时间差下降就一定是 WebRTC 队列积压，也可能是源时钟跳变、时间同步、消息来源变化或本机调度积压。

### 2.2 旋转控制链路

当前 `rotate_in_place_degrees()` 是一个 20 Hz 速度闭环，不是向 Go2 下发“旋转 12°”：

```text
读取当前 TF yaw
  -> 与上一帧 yaw 做差
  -> 累加 achieved angle
  -> remaining = target - achieved
  -> 根据 remaining 计算 angular.z
  -> 映射为 joystick.rx
  -> 50 ms 后再次读取 TF
```

当前真机最小角速度指令默认是 `0.2 rad/s`，最大角速度指令默认是 `0.8 rad/s`。控制器停止后显式下发一次零 Twist，并固定等待 `0.35s`。

### 2.3 零速度与执行确认

当前代码能确认的仅有：

1. 本机调用了 `move(zero_twist)`。
2. WebRTC 协程没有抛异常。
3. `publish_without_callback()` 已被调用。

这些都不是机器人执行 ACK。当前 `WIRELESS_CONTROLLER` 发送路径没有设备侧回执，代码也没有在零速度后检查机身角速度是否稳定。

另外，当前 watchdog 超时只取消 timer，明确不会自动发送零速度。它与 `rotate_in_place_degrees()` 结束时主动发送零 Twist 是两条不同路径，必须分开验证。

当前 Remote WebRTC 的 `LOW_STATE` 类型只声明了 IMU `rpy`，未声明 `gyroscope`。DDS 消息虽然有 `gyroscope` 和 `yaw_speed`，但不能据此假设 Remote WebRTC 实际也能提供，必须先检查真机原始 payload。

## 3. 待验证假设

| 编号 | 假设 | 当前状态 | 可观察特征 |
|---|---|---|---|
| H1 | Go2 与 Mac 存在近似固定时钟偏移，实际传输正常 | 未验证 | `host-source` 长期近似常数，收发间隔基本一致，无追帧突发 |
| H2 | WebRTC、SDK 或本机回调队列发生动态积压 | 未验证 | `host-source` 动态增减，随后短时间密集收到旧样本，source 时间推进快于 host 接收时间 |
| H3 | 固定时钟偏移和动态积压同时存在 | 未验证 | 时间差存在稳定基线，同时叠加可恢复的动态峰值 |
| H4 | Go2 header 的时钟来源、语义或单位不稳定 | 未验证 | 时间戳倒退、重复、跳变、重连后换原点，或与物理运动事件不对应 |
| H5 | 主要积压发生在 Mac 的 WebRTC event loop、解码或 DimOS 回调 | 未验证 | DataChannel 回调前正常、回调后到 TF/控制器读取之间耗时异常 |
| H6 | 零命令已发送且执行，但机身存在制动惯性 | 未验证 | 零命令后角速度平滑衰减，停止延迟和多转角稳定可重复 |
| H7 | 零命令没有被 Go2 接收或应用，上一摇杆值被保持 | 未验证 | 零命令后持续保持近似原角速度，直到后续命令或模式变化 |
| H8 | 机身已经停止，但 odom/TF 仍在追历史数据或自身漂移 | 未验证 | 外部视频/IMU 显示已停，odom yaw 仍继续变化 |

## 4. 验证所需的统一时间线

### 4.1 必须记录的时间点

每个 odom 样本至少记录：

- `raw_callback_seq`：连接进程内收到原始消息时递增的序号。
- `source_sec`、`source_nanosec`、`source_ts`：Go2 原始 header。
- `raw_callback_wall_ts`：进入 Mac 原始消息回调时的 `time.time()`。
- `raw_callback_monotonic_ns`：进入回调时的本机单调时间。
- `decoded_monotonic_ns`：完成 odom 解析的时间。
- `odom_publish_monotonic_ns`：覆盖时间戳并进入下游流的时间。
- `tf_update_monotonic_ns`：TF 缓存接受该姿态的时间。
- `controller_read_monotonic_ns`：旋转控制器读取该 TF 的时间。
- `yaw_rad`、位置和 frame。

每个 20 Hz 旋转周期至少记录：

- `rotation_session_id`、`control_tick`。
- `target_deg`、`current_yaw_deg`、`delta_deg`。
- `accumulated_deg`、`remaining_deg`。
- 比例计算结果、限幅前后 `omega_rad_s`。
- 本周期实际关联的 `raw_callback_seq` 和 `source_ts`。
- 同一个 TF 是否被连续多个控制周期重复读取。
- 指令生成、进入 WebRTC event loop、调用 DataChannel send 前后的单调时间。
- joystick 的 `lx/ly/rx/ry` 和是否为零命令。
- DataChannel 的 `readyState`、`bufferedAmount` 和本地发送异常。

每个停止阶段至少记录：

- 最后一个非零命令的 ID、值和发送时间。
- 第一个零命令的 ID、值和发送时间。
- 零命令以后每个新 odom/IMU 样本的 yaw、yaw 变化率和时间。
- 判断“已经停止”所依据的传感器、阈值、持续时间和样本数。

### 4.2 不能只用墙上时间

`time.time()` 可能被 NTP 校时，因此：

- 同一台 Mac 内部的耗时一律用 `time.monotonic_ns()`。
- Go2 `source_ts` 与 Mac 墙上时间只有在确认同一时钟域后才能直接相减并称为“单向延迟”。
- 未确认时钟域前，字段只能命名为 `host_source_delta`，不能命名为 `network_latency` 或 `feedback_age`。

### 4.3 诊断实现不得改变控制行为

复用现有有界、非阻塞 `TraceSink`，高频记录写独立 navigation trace：

- 仅在 `navigation_trace_level=full` 时启用。
- 控制线程和 WebRTC 回调只构造小型标量记录并 `put_nowait()`。
- JSON 序列化和磁盘写入由后台 writer 完成。
- 队列满时丢弃诊断事件并累计 drop 数，不允许阻塞控制。
- 不在主 `main.jsonl` 中以 `logger.info` 输出 20 Hz 全量数据。
- 诊断异常只能关闭 TraceSink，不得影响 odom、TF、旋转或零命令发送。
- 使用 diagnostics off/full 做 A/B，对比事件循环延迟、控制周期和丢帧率。

## 5. 验证一：区分时钟偏移与动态积压

### 5.1 静止基线

在 Go2 静止、无导航和无 VLM 请求时分别执行：

1. LocalSTA 连接记录 10 分钟。
2. Remote/4G 连接记录 10 分钟。
3. 每种连接至少执行一次断开重连。
4. 条件允许时重启 Go2，再重复 3 分钟。
5. 同时保存 Mac 的 NTP/系统时钟状态；如果能够合法读取 Go2 系统时间，也记录 Go2 的时钟状态，但不能把“SSH 能登录”作为计划前提。

每个样本计算：

```text
D_i = host_rx_wall_ts_i - source_ts_i
source_interval_i = source_ts_i - source_ts_(i-1)
host_interval_i = host_rx_monotonic_i - host_rx_monotonic_(i-1)
```

### 5.2 动态积压判据

仅凭 `D_i` 很大不能证明网络延迟。需要同时满足以下证据：

- `D_i` 在短时间显著上升或下降，而不是保持固定基线。
- `source_ts` 单调递增且采样周期合理。
- 恢复阶段出现接收突发：多个历史样本以远短于源采样周期的 host 间隔到达。
- `source_interval` 累计推进明显快于同段 `host_interval`，表现为追帧。
- event-loop heartbeat、DataChannel 回调或下游 TF 更新时间能定位积压发生在哪一层。

如果 `D_i` 长期近似常数，并且 `source_interval` 与 `host_interval` 一致，则更符合固定时钟偏移。

如果 `source_ts` 跳变、倒退、重复或重连后改变时间原点，则先判为源时间语义异常，不能继续使用 `D_i` 推断网络。

### 5.3 分析方法

使用稳健基线分离固定偏移和动态部分：

```text
baseline = 一段稳定窗口内 D_i 的低分位数或最小稳定簇
excess_delay_i = D_i - baseline
```

`baseline` 只是时钟偏移与最低链路延迟的合量，不声称是纯时钟偏移。`excess_delay` 也只有在 source 时钟连续稳定时才可解释为动态链路/处理延迟。

输出以下图表：

- `host_source_delta` 随时间变化。
- source 采样间隔与 host 接收间隔对比。
- 每秒回调数量和追帧突发。
- WebRTC event-loop delay。
- raw callback、decode、TF update、controller read 的分段耗时。

### 5.4 验收结论

本实验必须给出以下四种结论之一：

- `CLOCK_OFFSET_DOMINANT`
- `DYNAMIC_BACKLOG_CONFIRMED`
- `CLOCK_OFFSET_AND_BACKLOG`
- `SOURCE_TIMESTAMP_UNUSABLE_OR_INCONCLUSIVE`

没有达到证据条件时必须选择最后一项，不能凭趋势直接断言“网络积压”。

## 6. 验证二：确认 Go2 原始 odom 时间戳是否可信

### 6.1 验证内容

原始时间戳需要回答四个问题：

1. 是否单调递增，有无重复、倒退和跳变。
2. 采样周期是否与实际约 18 Hz 的 odom 更新匹配。
3. 重连和重启后属于 Unix 时间、开机时间还是其他时钟域。
4. 时间戳标记的是测量时刻、发布时刻，还是无法解释的 SDK 时刻。

### 6.2 静止和重连实验

记录：

- 10 分钟静止样本的单调性、重复率、跳变次数和频率分布。
- LocalSTA 与 Remote/4G 是否使用相同的 source clock 语义。
- WebRTC 重连前后 source 时间是否连续。
- Go2 重启后 source 时间是否回零或跳到新的 Unix 时间。

### 6.3 物理事件对时实验

在空旷区域执行低速、短时、可重复的左右旋转脉冲，并同时保存：

- Go2 原始 odom yaw 与 `source_ts`。
- Mac 接收时间和控制命令时间。
- Remote WebRTC 原始 `LOW_STATE` payload，核实是否实际含有 gyro/角速度但当前 TypedDict 未声明。
- 若 Remote payload 没有角速度，则使用外部 60 fps 视频、AprilTag/视觉航向或其他独立测量作为物理基准。

对每次脉冲比较：

```text
命令发出时刻
物理机身开始转动时刻
原始 odom yaw 首次变化的 source_ts
该 odom 到达 Mac 的时刻
TF 被旋转控制器读到的时刻
```

如果原始时间戳对应测量时刻，odom 的运动开始/停止事件应在 source 时间轴上与独立物理基准稳定对齐；如果只对应发布时刻或发生不稳定偏移，需要明确记录其语义和误差范围。

### 6.4 可信判据

原始时间戳满足以下条件后，才可用于 freshness gate：

- 无无法解释的倒退和大幅跳变。
- 采样周期与 odom 更新频率一致。
- 重连、连接模式切换和短时运动中语义一致。
- 与独立运动事件的偏差稳定且可量化。
- source clock 与 host clock 的关系能够校准，或 freshness 算法完全不依赖跨设备绝对时间差。

若不满足，则不能简单把原始时间戳删除或继续伪装成当前主机时间。应分别保留：

- `measurement_ts`：只有确认有效时使用。
- `host_received_wall_ts`：用于跨日志人工对齐。
- `host_received_monotonic_ns`：用于本机处理时延。
- `producer_seq`：用于确认是否获得新反馈。

## 7. 验证三：确认发零以后 Go2 是否真正停止

### 7.1 将“成功”拆成四层

每次零速度必须分别记录：

1. `ZERO_REQUESTED`：控制器生成了零 Twist。
2. `ZERO_LOCAL_SEND_OK`：本机调用 DataChannel send 未抛异常。
3. `ZERO_DEVICE_ACKED`：设备明确返回执行 ACK。当前链路不存在这一层，不能伪造。
4. `ZERO_MOTION_STOPPED`：新鲜的物理运动反馈证明机身已经停止。

当前只能证明前两层。第三层需要确认 Unitree 是否存在可用的回执接口；如果没有，就用第四层建立执行闭环。

### 7.2 停止判断的独立反馈

优先级如下：

1. 真机 raw lowstate 中可用的 `gyroscope.z` 或 `yaw_speed`。
2. 与命令独立的机身 IMU 角速度流。
3. 外部固定相机的 AprilTag/视觉航向。
4. 原始 lidar odom yaw 差分。

odom 只能作为估计，不能单独充当物理真值。若外部视频显示已停止而 odom 仍变化，应判为 odom/队列问题，不应判为机器人仍在转。

### 7.3 实验步骤

1. 在静止状态记录至少 30 秒角速度/视觉航向噪声，建立零速基线。
2. 在空旷区域、人工持有遥控器和急停能力的情况下，从低速短脉冲开始。
3. 左右方向分别发送固定持续时间的非零摇杆命令。
4. 记录最后一个非零命令，并立即显式发送零命令。
5. 零命令后继续采集至少 2 秒的新鲜 odom、IMU 和外部视觉数据。
6. 计算停止延迟、零命令后的额外旋转角和反馈链各段时延。
7. 每个方向、每个速度至少重复 10 次；先测试当前默认最小值 `0.2 rad/s`，确认安全后再扩展到 `0.3 rad/s`、`0.4 rad/s`。
8. 将“显式零命令”与“watchdog 超时”分开测试。当前 watchdog 不发零，测试时不得假设它能停止机器人。

初始停止判据不直接写死，先由静止噪声确定。建议候选规则：

```text
abs(yaw_rate) < max(静止噪声的 3σ, 0.03 rad/s)
并持续至少 300 ms
并跨过至少 5 个新的反馈样本
```

同时要求 300 ms 窗口内视觉/odom 航向变化不超过经基线验证的阈值。正式阈值由实验数据决定。

### 7.4 需要区分的结果

| 现象 | 判断 |
|---|---|
| 零命令后 IMU、视觉和 odom 同时逐渐停下 | 命令执行，存在可量化制动延迟 |
| 视觉/IMU 已停，odom 仍继续变化 | odom 陈旧、追帧或估计漂移 |
| odom 显示已停，视觉/IMU 仍在转 | odom 不能代表当前机身状态 |
| 所有反馈均持续转动 | 零命令可能未应用、运动模式保持上一指令或发送链路异常 |
| 只有本机 send 成功，没有新反馈 | 结果不可确认，禁止报告“已停止” |

## 8. 测试矩阵与安全门禁

### Gate 0：静态与单元测试

- 构造固定偏移、动态积压、时间跳变和乱序的合成 odom 序列。
- 验证分类器不会把固定时钟偏移误判成网络延迟。
- 验证 20 Hz trace 字段完整、序号连续、丢弃可统计。
- 验证 tracing off 时不创建队列、线程和文件。
- 验证诊断异常不会中断零命令。

### Gate 1：Replay/Simulation

- 完整记录每个 50 ms 控制周期。
- 对比 tracing off/full 的控制输出逐样本一致性。
- 模拟旧 TF、重复 TF 和新 odom 超时。
- 验证报告只描述证据，不自动改变控制器行为。

### Gate 2：静止真机

- LocalSTA 与 Remote/4G 各记录 10 分钟。
- 不发送运动命令，只验证时间戳、回调频率、event-loop delay 和 trace 开销。
- full tracing 开启后，odom 接收频率和 WebRTC heartbeat 不得显著劣化。

### Gate 3：低速短脉冲

- 空旷区域、人工安全监控，从当前默认最小值 `0.2 rad/s` 开始，再逐级测试更高速度。
- 左右方向重复测试。
- 每次必须显式发送零命令，并继续记录 2 秒。
- 未取得独立运动反馈前，不得把 odom 单独称为“实际转角”。

### Gate 4：复现视觉对准

- 使用固定目标，记录 bbox 计算角度、每个控制周期、完整命令序列和最终新鲜画面。
- 将预计转角、odom 估算转角、IMU/外部视觉转角分开报告。
- 二次视觉确认必须继续作为“找到目标”的最终门禁。

### 性能门禁

每个 Gate 均比较 tracing off/full：

- WebRTC event-loop delay 的 p50/p95/p99。
- odom 回调频率、最大间隔和重复/丢弃数量。
- 20 Hz 控制周期实际间隔。
- TraceSink 队列峰值、drop 数和写盘吞吐。
- CPU、内存和日志体积。

若 full tracing 使控制周期 p95 增加超过 5 ms、出现新的连续 odom 空窗，或改变 Twist 序列，则停止真机移动测试，先降低记录量或修复诊断开销。

## 9. 初步解决方向

以下不是最终方案，只在相应证据成立时采用：

### 情况 A：原始时间戳可信，动态积压成立

- 下游同时保留 source measurement time 和 host receive time，禁止无痕覆盖。
- 控制器只使用满足 freshness 条件的新 odom。
- 反馈过旧时显式发送零速度，等待新样本；只有新鲜反馈证明停止后才允许再次旋转。
- 小角度改为“短脉冲 -> 显式零 -> 等新反馈稳定 -> 重算剩余角”的闭环。

### 情况 B：主要是固定时钟偏移

- 不把绝对 `host-source` 直接当网络延迟。
- 校准稳定 offset，或用 source 序号/间隔和 host monotonic 判断新鲜度。
- 保留原始时间戳，不再用 host 当前时间冒充测量时间。

### 情况 C：原始 source 时间戳不可信

- 使用连接回调处的 host monotonic 时间和递增序号判断“是否为新反馈”。
- `source_ts` 仍旁路保存供诊断，但不参与实时 freshness 决策。
- 必须将“接收时间”和“测量时间未知”明确区分。

### 情况 D：零命令执行存在不确定性

- 修复 watchdog，使超时真正发送显式零命令。
- 增加 `STOPPING -> STOP_CONFIRMED` 状态，使用新鲜 IMU/视觉/odom 稳定窗口确认。
- 超时未确认时返回失败并禁止继续报“旋转完成”或“找到目标”。
- 若 Unitree 提供设备侧命令 ACK，记录 ACK；即便有 ACK，仍保留物理停止反馈。

### 情况 E：机身已停但 odom 继续追帧

- 停止状态优先使用独立角速度/视觉反馈。
- 暂停基于陈旧 odom 的角度累加。
- 清晰区分“机器人实际继续转”和“控制器正在消费历史姿态”。

## 10. 最终交付物

完成验证后应交付：

1. 原始 connection、TF、rotation、command 和 stop trace。
2. 一份自动分析报告，包含时间差、回调间隔、追帧、控制周期、命令和机身运动叠加图。
3. LocalSTA 与 Remote/4G 对比结果。
4. Go2 原始 odom 时间戳语义和可信度结论。
5. 零命令停止延迟和额外旋转角的统计结果。
6. 对 H1 至 H8 的 `CONFIRMED / REJECTED / INCONCLUSIVE` 结论与证据。
7. 基于实验结果确定的最终控制方案和配置值。

最终报告必须使用下面的表述边界：

- `source_ts` 未完成时钟域验证前，只能称“Go2 header 时间”。
- `host-source` 未完成时钟验证前，只能称“时间差”，不能称“网络延迟”。
- WebRTC send 返回成功只能称“本机发送调用成功”。
- odom yaw 只能称“里程计估算转角”。
- 只有独立的新鲜运动反馈稳定后，才能称“机器人已经停止”。

# Go2 沿途 VLM 寻物与延迟回退实施计划

创建日期：2026-07-14
基线分支：`relocalization-change-local-vlm`
基线提交：`c7434223`
主要改动范围：`dimos/agents/skills/navigation.py` 及其测试
目标物体：任意自然语言目标，不对灭火器、饮水机等具体类别做硬编码

## 1. 本次需求边界

本次只调整“已有记忆寻物如何搜索和中断导航”，保留现有 Agent、空间记忆、重定位地图和导航规划主链路。

用户显式启用沿途寻物并发出“去找 xxx”后，执行顺序为：

```text
解析目标并查询历史物体记忆
  ↓
前往该物体的历史位置，同时沿途做目标 VLM 检测
  ├─ 沿途命中：取消当前导航 → 回到拍照时的观察位姿 → 面向目标 → Hello → 结束
  └─ 沿途未命中：到达历史位置并执行现有视觉扫描
       ├─ 命中：面向目标 → Hello → 结束
       └─ 未命中：依次前往其他已知房间，同时沿途做目标 VLM 检测
            ├─ 沿途命中：取消当前导航 → 回到观察位姿 → 面向目标 → Hello → 结束
            ├─ 房间内扫描命中：面向目标 → Hello → 结束
            └─ 所有已知房间均未命中：返回“未找到”
```

明确约束：

- 沿途寻物是 opt-in 新功能，由 `DIMOS_ENROUTE_OBJECT_SEARCH_ENABLED=true` 显式启用；默认 `false` 时完整保留原来的“到历史位置后再检测”流程。
- 不在任务刚开始时对“当前位置”单独执行 VLM 检测，移除或绕过 `in_frame` 前置步骤。
- 沿途检测只在导航目标已下发、机器人进入该段路线后启用。
- 历史位置搜索失败后，只搜索“其他已知房间”；历史物体所属房间不重复搜索。
- 沿途 VLM 命中只触发停车和回到观察位姿；回到位姿后必须用新相机帧二次确认，确认成功才判定找到。
- 找到后的动作复用当前逻辑：面向物体并执行 `Hello`，随后结束寻物任务。
- 本期不加入未知区域 frontier exploration；已知房间全部失败后明确返回未找到。



## 2. 当前代码与缺口

当前 `NavigationSkillContainer` 已具备：

- `navigate_with_text()`：解析自然语言目标并启动 fallback。
- `_nav_fallback_step_landmark()`：导航到历史物体地标。
- `_room_anchor_sweep_for_object()`：遍历已记录的 `ROOM` 地标。
- `_navigate_to_landmark()`：把地图记忆转换成当前 `world` 目标并执行导航。
- `_wait_goal_with_relocalize()`：等待导航完成并处理重定位状态。
- `_visual_acquire_object()` / `_get_bbox_for_current_frame()`：到点后的 VLM 视觉确认。
- `_run_arrival_action("point", ...)`：停止导航并执行 `Hello`。

当前缺口是：

1. VLM 只在到达地标或房间扫描时使用，导航途中不识别目标。
2. `_latest_image` 和 `_latest_odom` 是两个独立“最新值”，没有按时间绑定。
3. VLM 是高延迟调用，结果返回时机器人可能已经离开图片拍摄位置。
4. 当前导航等待流程没有统一的“目标命中”中断信号，无法同时取消旧 goal、停止后续房间遍历。
5. 如果多帧 VLM 请求排队，旧图片的迟到结果可能错误打断新的导航段。

因此不能在导航循环中直接调用 `_get_bbox_for_current_frame()`；必须增加带任务标识、采集位姿和取消语义的异步沿途检测层。

## 3. 核心设计



### 3.1 单一寻物任务上下文

一次 `navigate_with_text("去找 xxx")` 创建一个 `ObjectSearchContext`，贯穿历史位置和所有房间路线：

```python
@dataclass
class ObjectSearchContext:
    search_id: str
    query: str
    state: SearchState
    hit_event: threading.Event
    cancel_event: threading.Event
    hit: SearchHit | None
    active_leg_id: int
    vlm_in_flight: bool
```

建议状态：

```text
CREATED
  -> NAVIGATING_TO_HISTORY
  -> SCANNING_HISTORY
  -> NAVIGATING_TO_ROOM
  -> SCANNING_ROOM
  -> RETURNING_TO_CAPTURE_POSE
  -> FOUND / NOT_FOUND / FAILED / CANCELLED
```

设计要求：

- 一个寻物任务只允许一个最终命中，首个有效命中原子写入 `context.hit`。
- `search_id` 防止上一轮任务的迟到结果污染新任务。
- `active_leg_id` 防止上一段路线的迟到结果打断下一段路线。
- 历史点路线和房间路线复用同一个 context，因此任意一段命中都能终止整个 fallback。



### 3.2 图像与采集位姿绑定

为 odom 增加一个有界时间缓冲区，而不是只保存 `_latest_odom`：

```text
deque[(odom.ts, pose_world)]
```

每次准备提交 VLM 时，生成不可变的 `SearchFrameSnapshot`：

```python
@dataclass(frozen=True)
class SearchFrameSnapshot:
    search_id: str
    leg_id: int
    image: Image
    image_ts: float
    capture_pose_world: PoseStamped
    capture_pose_map: PoseStamped | None
    map_key: str | None
    world_from_map_at_capture: Transform | None
```

位姿选择规则：

1. 使用 `image.ts` 查找时间上最近的 odom。
2. 图像与 odom 时间差超过阈值时丢弃该帧，不把不匹配的“最新位姿”硬绑给图片。
3. 重定位可用时，同时保存 `capture_pose_map` 和 `map_key`。
4. `capture_pose_world` 仅用于当前 session fallback；长期和重定位场景以 `capture_pose_map` 为准。

这是处理 VLM 延迟的基础：结果晚到时，系统仍知道“这张图是在什么位置拍的”。

### 3.3 沿途 VLM 调度

沿途检测采用 single-flight 模式：同一任务最多只有一个 VLM 请求在途。

```text
导航段进入 ACTIVE
  -> 等待机器人产生最小位移，避免把任务起点当作当前位置检测
  -> 按配置间隔取最新清晰帧
  -> 绑定采集位姿后异步提交 VLM
  -> 请求未返回期间不排队新图片
  -> 未命中后再对最新帧发起下一次请求
```

这么做的原因：

- 避免低速网络或云端回退时积压多张旧图。
- 避免已经走到下一房间后才收到几段路线以前的识别结果。
- 控制 VLM 请求频率和费用。
- 首个请求返回后立即使用最新画面，而不是清空历史队列。

建议首期配置：


| 配置 | 初始值 | 作用 |
| --- | --- | --- |
| `DIMOS_ENROUTE_OBJECT_SEARCH_ENABLED` | `false` | 沿途寻物总开关；只有 `true` 才启用新逻辑 |
| `DIMOS_SEARCH_VLM_INTERVAL_S` | `0.8` 秒 | 两次请求的最短间隔 |
| `DIMOS_SEARCH_START_DISPLACEMENT_M` | `0.20` 米 | 导航后移动到该距离才启用沿途检测 |
| `DIMOS_SEARCH_POSE_SYNC_TOLERANCE_S` | `0.20` 秒 | 图像和 odom 最大允许时间差 |
| `DIMOS_SEARCH_MAX_RESULT_AGE_S` | `8.0` 秒 | 超龄结果不再中断导航 |
| `DIMOS_SEARCH_REWIND_THRESHOLD_M` | `0.40` 米 | 超过该距离才需要回到拍照位姿 |
| `DIMOS_SEARCH_ODOM_BUFFER_S` | `15.0` 秒 | 位姿历史长度，应覆盖最大 VLM 延迟 |
| `DIMOS_SEARCH_CONFIRM_FRAME_TIMEOUT_S` | `3.0` 秒 | 回到观察位姿后等待新相机帧的最长时间 |
| `DIMOS_SEARCH_CONFIRM_MAX_CHECKS` | `2` 次 | 二次确认最多检查的帧数；偏离中心时先转向再复核 |
| `DIMOS_SEARCH_CONFIRM_CENTER_TOLERANCE_DEG` | `5.0` 度 | 最终 bbox 中心允许偏离相机中心的角度 |


这些参数应通过现有配置模式暴露，不写死在业务分支判断里；真机日志稳定后再调优。

### 3.4 沿途初次命中与二次确认规则

沿途初次命中只用于确定观察位姿并中断当前导航，该次结果必须满足基本时序约束：

- 返回结果属于当前 `search_id`。
- 返回结果属于当前或仍允许中断的 `leg_id`。
- 任务尚未结束或取消。
- 图片有匹配成功的采集位姿。
- 结果返回年龄没有超过 `search_max_result_age_s`。
- VLM 返回目标 bbox，且类别与当前 query 的语义匹配。

机器人返回观察位姿并恢复目标朝向后，必须等待时间戳更新的相机帧重新识别：

- 新画面未识别到目标时，不写入物体记忆、不执行 Hello、不回复找到，并继续原历史地点搜索。
- 新画面识别到目标但 bbox 未居中时，按 bbox 偏差原地转向，再等待下一帧复核。
- 只有新画面再次识别到目标且 bbox 已居中，才写入记忆、保存最终确认帧 JPG、执行 Hello 并结束任务。
- 最终确认帧按 `YYYYMMDD-HHMMSS_<record_id>.jpg` 保存到 `landmark_memory/snapshots/`；再次找到同名物体时保留新文件，并让地标记录指向最新确认画面。

满足后设置 `hit_event`，用于停车并回到观察位姿；返回后再按上面的新帧规则执行最终确认。

## 4. VLM 延迟后的停止与回退



### 4.1 为什么不能使用结果返回时的当前位置

假设图片在 `t0` 拍摄，VLM 在 `t1` 返回：

```text
t0: 机器人在 P_capture，图片中看到目标
    ↓ VLM 处理 2~5 秒，机器人继续导航
t1: 机器人已经到 P_now
```

如果在 `t1` 直接面向 bbox 或把 `P_now` 记成目标位置，会发生两类错误：

- bbox 方位属于 `P_capture` 的相机视角，在 `P_now` 使用已经失效。
- 新物体记忆被写到走过头之后的位置，下次导航仍会偏离目标。

因此回退目标是**图片拍摄时的观察位姿**，不是 VLM 返回时的当前位置，也不是仅靠单目 bbox 猜测出的物体三维位置。

### 4.2 命中后的动作顺序

VLM 线程只发布命中事件，不直接控制机器人。导航线程在等待循环中读取 `hit_event`，按以下顺序处理：

```text
1. 原子锁定首个 SearchHit，停止继续提交 VLM。
2. cancel 当前 planner goal。
3. 发布停止命令并等待导航进入 CANCELLED/IDLE，避免旧 goal 和回退 goal 同时生效。
4. 读取当前位姿，计算与 capture pose 的距离。
5. 如果距离 <= rewind threshold：留在原地，直接转向目标方向。
6. 如果距离 > rewind threshold：通过同一导航栈规划回 capture pose。
7. 到达 capture pose 后，旋转到图片中目标对应的方位。
8. 一次命中直接判定 FOUND，调用现有 point/Hello 行为。
9. 用本次观察更新目标记忆，终止历史点或房间搜索循环。
```

回退必须继续使用现有 planner 和 `merged_map`，不能盲目倒车。走廊里可能有人或障碍物已经变化，重新规划返回观察点更安全。

### 4.3 重定位下如何解算回退点

拍照时已经保存：

```text
P_capture_map
T_world_map_at_capture
```

真正开始回退时重新读取当前重定位变换：

```text
P_capture_world_now = T_world_map_now * P_capture_map
```

然后把 `P_capture_world_now` 下发给当前导航模块。这样即使 VLM 等待期间发生重定位修正，也不会继续使用旧 `world` 坐标。

只有在拍照时无法获得有效 map 绑定时，才使用同 session 的 `P_capture_world`。如果 map key 已变化或重定位不可用，应停止并返回明确错误，不跨地图盲目回退。

### 4.4 如何面向图片中的目标

VLM 返回 bbox 后，复用当前图像水平视场角换算逻辑：

```text
bbox_center_offset_yaw = bbox 中心水平偏移对应的相机角度
object_yaw_at_capture = capture_robot_yaw + bbox_center_offset_yaw
```

重定位模式下同时把目标朝向保存为 `object_yaw_map`；回到观察位姿时，使用当前 `world <- map` 转为 `object_yaw_world_now`。

回退 goal 的最终 orientation 可直接设为该朝向；到点后再执行一次原地旋转收敛。根据本期“一次命中即可”的要求，旋转完成后不再调用 VLM 复核，直接执行 `Hello`。

### 4.5 回退失败时的语义

识别命中但无法回到观察位姿时，不应：

- 静默恢复旧历史点导航。
- 继续搜索其他房间。
- 在错误位置执行“找到并打招呼”。

应返回独立结果：

```text
已在沿途识别到目标，但返回观察位置失败：<navigation reason>
```

任务状态设为 `FAILED_RETURN_TO_HIT`，日志保留 capture/current pose、距离、map key 和导航失败原因，便于现场区分“没识别到”和“识别到但回不去”。

## 5. 与现有导航流程的接入点



### 5.1 `navigate_with_text()`

- 对寻物 query 创建 `ObjectSearchContext`。
- 不执行 `in_frame` 当前画面检测。
- 查询目标历史 `LANDMARK`；没有历史物体记录时，可直接从已知房间序列开始。
- 使用 `try/finally` 确保任务结束时取消 VLM worker、清理事件和停止残留 goal。



### 5.2 `_nav_fallback_step_landmark()`

- 将 context 传给 `_navigate_to_landmark()`。
- 历史物体所属房间加入 room sweep 的 skip 集合。
- 沿途命中并完成回退后直接返回 FOUND，不再进入历史点扫描或房间搜索。
- 到历史点未命中时保留现有 360 度视觉扫描。



### 5.3 `_navigate_to_landmark()` / `_wait_goal_with_relocalize()`

- 增加可选的 `search_context`，普通导航调用不受影响。
- 每个 waypoint/goal 等待周期检查 `hit_event`。
- 命中时返回结构化中断原因，例如 `OBJECT_HIT`，而不是把主动取消误报成导航失败。
- 沿途 VLM 只监控物体搜索导航，不影响一般的“去会议室 A”等位置导航。



### 5.4 `_room_anchor_sweep_for_object()`

- 过滤历史物体所属房间，并对其他 ROOM 记录按现有排序依次访问。
- 前往每个房间的路线都传入同一 search context，沿途均可中断。
- 到房间后执行现有全景扫描；房间扫描中的首个 VLM 命中同样直接 FOUND。
- 一个房间失败后才进入下一个房间。



### 5.5 `_run_arrival_action()`

- 沿途命中回退完成后，复用现有 `point` 分支执行停止、`Hello` 和恢复站立。
- 保证动作只执行一次；room/history scan 的迟到回调不得再次触发。



## 6. 物体记忆更新

沿途命中完成回退后，应把本次观察写回 `SpatialLandmarkMemory`：

```json
{
  "query": "用户目标原文",
  "observation_source": "enroute_vlm",
  "map_key": "当前地图",
  "capture_pose_map": "拍照时观察位姿",
  "capture_pose_world": "拍照时 world 位姿，仅作诊断",
  "object_yaw_map": "目标朝向",
  "image_ts": "采集时间",
  "vlm_result_ts": "结果时间",
  "vlm_latency_s": "识别延迟",
  "search_id": "本次任务"
}
```

MVP 无可靠深度时，不把观察位姿伪装成精确物体三维坐标。现有系统若必须使用 landmark position，则继续把安全观察位姿作为导航锚点，并通过 metadata 标明 `position_semantics=observation_viewpoint`。

如果目标从旧房间移动到新房间：

- 新命中记录成为首选记录。
- 旧位置保留为历史或标记 stale，不能继续排在新记录之前。
- 若本次命中发生在前往某房间的途中，可根据拓扑/最近 ROOM 关联新房间；无法可靠判断时不强行写错 room name。



## 7. 并发、取消与异常规则

- single-flight：同一时刻最多一个 VLM 请求。
- first-hit-wins：首个有效命中获得写权限，后续结果全部忽略。
- generation guard：`search_id + leg_id` 不匹配的结果丢弃。
- task cancellation：用户发出新导航、停止命令或模块 stop 时，设置 `cancel_event` 并取消导航 goal。
- relocalization guard：回退前重新确认 map key 和 `world <- map` 可用。
- image copy：提交异步 VLM 前冻结图片数据，避免 `_latest_image` 被下一帧覆盖。
- no stale hello：任务已经结束后，迟到回调只能记日志，不能控制运动或执行动作。

## 8. 日志与现场可观测性

每个搜索任务使用统一 `search_id`，至少记录：

```text
search_started(query, search_id, historical_record, room_count)
search_leg_started(leg_id, type, target_name, target_pose)
enroute_monitor_armed(displacement, interval)
vlm_request(image_ts, capture_pose_map, leg_id)
vlm_result(hit, latency_s, result_age_s, leg_id)
object_hit(capture_pose, current_pose, rewind_distance, bbox)
navigation_cancelled_for_hit(old_goal_id)
rewind_started(goal_pose, map_key)
rewind_finished(status, duration_s)
object_faced(target_yaw)
hello_executed
memory_updated(record_id, old_record_status)
search_finished(status, total_duration_s)
```

这样现场可以直接区分：VLM 慢、事件迟到、取消 goal 慢、回退规划慢、旋转慢，还是 Hello 动作未执行。

## 9. 测试计划



### 9.1 单元测试

新增/扩展 `NavigationSkillContainer` 测试，覆盖：

1. 有历史物体时不调用当前位置 `in_frame` 检测，直接开始历史点导航。
2. 沿途第一帧 VLM 命中后取消当前 goal，只执行一次回退和一次 Hello。
3. 图片与最近 odom 正确绑定；超过同步阈值的帧不提交。
4. VLM 返回时机器人已前进，回退 goal 使用 capture pose 而不是 current pose。
5. 重定位变换更新后，用 `capture_pose_map + T_world_map_now` 解算回退目标。
6. 机器人离 capture pose 小于阈值时不额外导航，只转向并 Hello。
7. 迟到的旧 `search_id` / `leg_id` 结果不能中断当前路线。
8. 多次并发命中只接受第一个，Hello 只触发一次。
9. 历史位置未找到后，跳过原房间并依次搜索其他 ROOM。
10. 前往任意后续房间途中命中后，不再访问剩余房间。
11. 回退导航失败返回 `FAILED_RETURN_TO_HIT`，不继续 room sweep。
12. 普通位置导航不创建 VLM monitor，行为保持不变。



### 9.2 模拟延迟集成测试

用可控 fake VLM 注入 `0.1 / 2 / 5 / 9` 秒延迟：

- `0.1` 秒：通常原地转向，无明显回退。
- `2 / 5` 秒：取消当前 goal，规划返回拍照位姿。
- `9` 秒：超过 max age 后丢弃，不用旧图打断新路线。

验证事件时序：

```text
VLM hit
  < cancel old goal
  < start rewind goal
  < rewind success
  < face target
  < Hello
```



### 9.3 Go2 真机验收

场景 A：目标仍在历史位置

- 从其他位置发出“去找目标”。
- 不在任务起点检测。
- 沿途无命中时到历史点扫描并找到，面向目标执行 Hello。

场景 B：目标移动到去往历史点的途中

- VLM 命中后机器人可能继续走一小段。
- 机器人取消旧目标，通过 merged map 回到拍照观察点。
- 面向目标并执行一次 Hello，不再前往历史点。

场景 C：目标从房间 A 移到房间 B

- 先到历史位置 A，未找到。
- 不重复搜索 A，依次前往其他已知房间。
- 前往 B 途中或 B 内扫描命中后，回到观察点、面向目标并 Hello。
- 新观察更新为目标的首选记忆。

场景 D：目标不存在

- 历史位置和其他已知房间全部搜索完。
- 不做未知区域探索，返回明确未找到，不无限循环。



## 10. 分阶段实施顺序



### 阶段 1：搜索任务和时序基础

- 给历史点导航和每个房间导航传入同一 search context。

## 11. 完成标准

以下条件全部满足才算本功能完成：

- [ ] 总开关默认关闭时完全保留旧的到点寻物逻辑，显式开启后才创建沿途搜索任务。
- [ ] 寻物任务开始时不会单独检测当前位置。
- [ ] 前往历史物体位置的整段路线可持续进行目标 VLM 检测。
- [ ] 历史位置失败后会跳过原房间，依次访问其他已知房间，并在每段路线沿途检测。
- [ ] 沿途命中后必须返回观察位姿并使用新相机帧二次确认，不能仅凭旧 bbox 终止搜索。
- [ ] VLM 延迟期间走过目标后，机器人能取消旧 goal 并回到图片拍摄观察位姿。
- [ ] 回退位姿优先绑定预加载 map，并通过当前重定位结果转换到 world。
- [ ] 二次确认成功后能面向 bbox 对应方向，并且只执行一次 Hello。
- [ ] 二次确认成功后将最终居中画面保存为独立 JPG，并把路径写入物体地标记录。
- [ ] 二次确认失败时不记忆、不打招呼、不报找到，并继续原历史地点及后续房间搜索。
- [ ] 新命中会更新通用物体记忆，不硬编码具体目标类别。
- [ ] 迟到 VLM、任务取消和回退失败不会触发错误动作或继续搜索。
- [ ] 普通导航、房间标记和现有重定位导航行为无回归。



## 12. 实施结论

这个需求可以在当前蓝图上实现，不需要改 Agent 的自然语言决策主逻辑，也不需要替换重定位后的 merged-map 导航栈。核心改动集中在 `NavigationSkillContainer`：通过默认关闭的总开关，把寻物从“到点后识别”可选扩展为“导航段可被视觉命中中断”，并为每次 VLM 请求冻结拍照时的地图位姿。

对于 VLM 延迟，首期最可靠的策略不是估算单目图片中物体的精确三维坐标，而是返回图片拍摄时的安全观察位姿，再根据 bbox 方位面向目标。这样既能补偿机器人已经走过目标的问题，也能直接复用当前规划、重定位和 Hello 动作链路。

# Mid-360 数据接收调试经验教训

> 2026-05-22 记录，供后续遇到类似问题时回顾。

---

## 问题描述

`mid360_native` 进程启动后，`tcpdump` 能看到 UDP 数据到达网卡，但进程 `/proc/<PID>/io` 的 `rchar` 不增长 — 进程收不到数据。

## 排查走过的弯路

### 错误猜想：组播 bind 问题

**猜想**：SDK 用 `bind(224.1.1.5, 56301)` 方式绑定组播地址，Linux 内核不转发数据给进程。

**为什么会错**：
1. 没有第一时间确认 `tcpdump` 看到的源 IP（`192.168.123.20`）到底是哪台设备
2. 用户说 Mid-360 IP 是 `192.168.123.161`，直接信了没验证
3. 把注意力全放在 socket 编程细节（组播 vs 单播），忽略了更基本的问题

### 花费的时间

在错误方向上浪费了约 2 小时：分析 SDK 源码的 `CreateSocket()`、对比 Python 和 C++ 的组播接收差异、尝试二进制补丁去掉 multicast。

## 真正的原因

| 问题 | 说明 |
|------|------|
| `lidar_ip` 配错 | Mid-360 实际 IP 是 `192.168.123.20`（被改过），不是 `192.168.123.161`（那是 Go2 内部处理器） |
| `multicast_ip` 硬编码 | `livox_sdk_config.hpp` 写死了 `"multicast_ip": "224.1.1.5"`，改为空即走单播（次要原因） |

## 解决方法

1. 用正确的 `lidar_ip=192.168.123.20` 启动
2. 去掉 `livox_sdk_config.hpp` 中 `multicast_ip` 硬编码（改为 unicast 更可靠）

## 核心教训

### 排查网络问题的正确顺序

```
1. 确认身份  → tcpdump 看到的 IP 分别对应哪台物理设备？用 ARP 表 / MAC 地址确认
2. 确认连通  → 目标设备能 ping 通吗？端口有回应吗？
3. 确认协议  → 数据格式、端口号是否匹配预期？
4. 确认绑定  → 进程的 socket 绑在哪个地址/端口？ss -aunp 确认
5. 最后才看代码细节 → bind 方式、组播/单播、buffer 大小等
```

### 具体经验

- **永远先验证 IP 身份**：`arp -a` 或 `ip neigh show` 看 MAC 地址，确认每个 IP 对应的物理设备
- **不要假设 IP 没被改过**：Livox 出厂默认 `192.168.1.155`，但可能被用户/工具改到任意地址
- **`tcpdump` 能抓到 ≠ 进程能收到**：tcpdump 工作在内核层（raw socket），应用层 socket 的 bind 地址/端口必须和数据包的目的地址精确匹配
- **SDK 设备发现是前提**：Livox SDK2 必须先通过广播发现设备，才会创建数据通道。`lidar_ip` 错了 → 发现失败 → 数据通道没建立 → 即使 socket 绑对了也收不到

### 快速定位 Mid-360 IP 的方法

```bash
# 方法 1：tcpdump 看谁在发 Livox 协议端口的数据
sudo tcpdump -i go2eth 'udp and (port 56300 or port 56400)' -c 5

# 方法 2：直接运行 mid360_native 看 "Device connected" 输出
timeout 10 ./mid360_native --lidar /test --host_ip 192.168.123.18 --lidar_ip 0.0.0.0

# 方法 3：ARP 表 + 排除法
ip neigh show dev go2eth
# 排除已知设备（dock .18、Go2 主板 .161），剩下的大概率是 Mid-360
```

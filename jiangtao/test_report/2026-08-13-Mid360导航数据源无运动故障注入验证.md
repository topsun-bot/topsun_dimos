### 时间戳复核与结论修正

上述 `28.511 Hz` 只是旧实现的消息发布频率，不是 PointLIO 产生新定位状态的频率。
原因是原生包装层每次主循环都用当前主机时间发布 `get_odometry()`，即使 PointLIO
并没有处理新的激光状态。这会产生“时间戳一直变新，但 pose 仍是旧值”的伪新鲜 odom。

修复后：

1. 用首个 Mid360 包建立固定的传感器时钟到主机 epoch 的偏移。
2. 发布时保留 PointLIO 源状态的时间间隔，不再每循环重写为当前时间。
3. 只有源状态时间戳变化时才发布新 lidar/odom；重复状态不能延长导航健康时间。
4. 时间戳回退仍发送一次，交给下游锁存故障，不会被去重逻辑隐藏。

修复后无运动录制 `source-time-gate-20260813/navigation.db` 实测：

- lidar：`291` 帧，`30.738 s`，`9.435 Hz`；时间戳倒退 `0`，重复 `0`。
- odom：`304` 帧，`30.738 s`，`9.857 Hz`；时间戳倒退 `0`，重复 `0`。
- `291/291` 帧导航点云都能找到时间差不超过 `1 us` 的 odom，实测最大时间差为 `0 s`。
- odom 最终位移 `0.0135 m`，最大偏离 `0.0182 m`，最大单帧变化 `0.0110 m`。
- 净 yaw 变化 `-0.059 deg`，yaw 全程范围 `0.164 deg`，四元数范数正常。
- TF 消息 `928` 条，解析出 `5` 条预期父子边，没有任何 child 同时拥有两个父节点。
- `world -> base_link -> mid360_imu_link -> mid360_link` 和相机静态边均存在。
- 录制中 `base_link -> mid360_imu_link` 与 `mid360_imu_link -> mid360_link`
  和 Orin Navigation 外参在 `1e-6` 容差内一致。

PointLIO 当前封装的对外校正状态随激光帧更新，因此真实新 odom 约为 `10 Hz`。
原配置的 `odom_freq=30 Hz` 只会重复发布旧状态，已将 Mid360 导航配置和地图 profile
调整为 `10 Hz`，使配置频率与真实状态频率一致。

## 故障注入与结果

通过 `SIGSTOP` 暂停当前 PointLIO 原生进程，模拟 LIO 不再输出，而不是断开整机网络。

```text
08:10:26.405  Mid360 navigation source fault latched: ODOM_STALE: age=0.501s
08:10:26.406  cached costmap replaced with 1x1 unknown grid
08:10:26.407  run-local voxel map cleared: frames=365, voxels=22144
```

结论：

1. Odom 超过 `0.5 s` 未更新后，导航源进入永久故障锁存。
2. costmap 在下一毫秒被替换为 `1x1 unknown`，旧可通行区域不能继续被下游使用。
3. 同一故障事件清空本次运行累计的 `365` 帧、`22144` 个体素。
4. 后续健康消息不会自动恢复地图，必须重启导航栈并重新建立坐标状态。

### 真实 UDP 断流复测

仅暂停 PointLIO 进程不能证明“Mid360 UDP 断流”也会被发现。进一步通过
`iptables` 丢弃来自 `192.168.123.20` 的 UDP，但保持 PointLIO 进程正常运行。

修复前，规则已丢弃 `6910` 个包、`8922490` 字节，但预处理样本仍每 `5 s`
增加约 `50`，且没有故障。这直接证明旧代码在重新发布缓存状态。

修复后运行 `20260813-162132-unitree-go2-mid360-navigation-source-validation`：

```text
08:22:12.535  开始丢弃 Mid360 UDP
08:22:13.084  ODOM_STALE: age=0.516s
08:22:13.084  清空 216 帧 / 21524 个体素
08:22:13.085  costmap 替换为 1x1 unknown
```

测试期间累计丢弃 `9178` 个包、`11848208` 字节。移除丢包规则后，导航源仍然
保持故障锁存，没有自动恢复。测试结束后已确认没有残留的 `iptables` 规则。

## 无控制 Viewer 与资源短时基线

使用不含 `GO2Connection`、规划器和 `MovementManager` 的
`unitree-go2-mid360-navigation-source-validation` 蓝图做了一次带 Mac Viewer
连接的短时资源采样：

```text
run_id=20260813-165612-unitree-go2-mid360-navigation-source-validation
artifact=jiangtao/artifacts/mid360/performance/no-control-20260813-165608/
```

该运行不具备运动指令输出。Mac `192.168.110.129` 已连接 Orin Rerun 服务，
PointLIO、导航源、VoxelGrid 和 costmap 均处于工作状态。运行结果如下：

- VoxelGrid 实际使用 `CPU:0 (packed-numpy)`，本次没有使用 Open3D CUDA。
- 导航源处理约 `10 Hz`；输入点数均值约 `5098`，输出约 `3886`。
- 预处理总耗时 p95 在稳定阶段约 `10.86-11.43 ms`，其中体素化 p95
  约 `7.77-8.64 ms`，变换和发布 p95 约 `0.70-0.72 ms`。
- `latest_wins_replaced=10` 只发生在启动阶段，之后保持不变；
  `dropped_no_odom=0`，没有运行期处理追不上输入的证据。
- PointLIO 原生进程最后约 `27-28%` 单核等价 CPU，RSS 稳定在约
  `59.6 MiB`。
- 最后约 15 秒内，导航源、VoxelGrid 和 costmap Python worker 的 RSS
  分别稳定在约 `159.3 MiB`、`335.5 MiB` 和 `305.9-306.2 MiB`。
- 主进程在启动完成后的约 45 秒窗口由 `655.0 MiB` 降至 `652.5 MiB`，
  没有继续增长。
- RerunBridge 在最后约 15 秒仍由约 `410 MiB` 增至 `442 MiB`。代码已通过
  `server_memory_limit=2GB` 对 Rerun 时间序列缓存设定硬上限，因此该现象不是
  “无限增长”的直接证据；但当前 44 秒有效运行窗口也不足以证明一小时稳定，
  长稳测试必须确认达到缓存上限后发生淘汰且不会触发 swap 抖动或影响定位。

这些 RSS 不能直接相加：Python worker 由 forkserver 创建，`ps` 的 RSS 会对
共享页重复计数；`ps %CPU` 也是进程自启动以来的平均值，不是每秒瞬时占用。
因此本轮可以确认 Mid360 导航处理周期有充足余量、核心处理 worker 短时稳定，
但不能据此宣称整栈一小时资源验收通过。

超时工具以 `124` 退出属于预期停止条件。DimOS 完成顺序关闭，PointLIO 原生
进程返回 `0`；结束后 `dimos status` 为 `No running DimOS instance`，所谓残留
命中只有采样脚本自身，没有残留 DimOS 或 PointLIO 进程。

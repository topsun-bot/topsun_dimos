# AI 写代码 → 真机验收闭环：架构分析与改进方案

> 目标：把「AI 写机器狗控制代码 → 人工上机调试 → 口头反馈 → AI 再改」的低效循环，
> 换成一个可重复、可审计、可安全停止的自动化闭环，并把 AI 生成功能在真机上"一次
> 就能正确运行"的比例，从当前的 **2/100** 提升到 **98/100** 量级。

## 1. 现状与瓶颈

当前流程（人工描述）：

1. AI（Claude）写控制代码；
2. 人把代码部署到真实 Unitree 机器狗上调试；
3. 代码即使编译通过、仿真通过，上真机也经常跑不起来；
4. 每次失败都要人观察机器狗、口头描述现象，再让 AI 继续改；
5. 反馈慢、不标准，调试效率低。

结合仓库现状（见下方"仓库已有能力盘点"），可以看到这个瓶颈**不是缺一个摄像头**，
而是整条流水线里几乎没有任何自动化的中间关卡：

- `ai_longrun_harness/run_to_main.sh` 会调用 `run_multi_agent_loop.sh`，但**这个脚本在
  仓库里根本不存在**——整个"AI 开发循环"目前是一个未实现的占位符，直接跳到
  `run_pr_pipeline.sh` 做 `git push` + `gh pr create`。也就是说，现在从 AI 写完代码到
  开 PR 之间，**没有任何自动检查**，无论是编译检查、单元测试，还是仿真测试。
- Go2（实际在用的机器狗型号）**没有物理仿真**，`--replay` 模式只是回放录制好的传感器
  日志，没有闭环动力学，无法验证一个新动作在物理上是否可行。G1 有 MuJoCo 物理仿真
  （`unitree_g1_basic_sim.py` → `unitree_g1_sim.py` → `unitree_g1_agentic_sim.py`），
  但仓库自己的测试文档也承认 `mujoco` 标记的测试"很慢，目前在 CI 里跑不起来"，CI 里
  全程排除 mujoco 测试。
- 仓库里**没有任何物理安全机制**：搜索 `dimos/` 和 `docs/` 全文，找不到 e-stop、跌倒
  检测、关节限位保护、超时自动停止这类东西。现有的"停止"能力（`dimos stop`、
  watchdog）都是进程级的（杀掉进程），不是物理层面的（让机器狗回到安全姿态）。
- 感知栈里已经有可以复用的部件：`dimos/perception/fiducial/`（AprilTag 等标记物的位姿
  识别，可给出确定性的、亚厘米级的位姿真值）、`dimos/agents/vlm_agent.py`
  （基于 GPT-4o 的开放式视觉问答）、无人机的视觉伺服模式
  （`drone_tracking_module.py` + `drone_visual_servoing_controller.py`，第三人称摄像头
  跟踪 + 反馈控制的现成范式）。但**没有"第三方外部摄像头"模块**（现有摄像头都是机器人
  本体第一人称视角），也**没有"动作是否完成"的判定器**。

结论：单独加一台外部相机 + 视觉判断，只是在这条几乎没有关卡的流水线**最末端、最贵**
的位置加了一个信号源。它能告诉你"失败了"，但：

- 信号太稀疏、太晚——每次迭代都要走完整条真机部署流程才能拿到一次反馈，迭代慢；
- 它不减少失败发生的概率，只是把失败"看见"而已；
- 单摄像头 + 纯视觉判断本身就不稳（遮挡、光照、相机与机器人坐标系未标定），存在
  误判风险，而误判比"没有判断"更危险——它会把能用的代码判成不能用（拖慢迭代），或
  把有问题的代码判成能用（放真的坏代码合并）；
- 它给 AI 的反馈只有一段视频，AI 无法从中定位是感知问题、规划问题还是执行层的时序/
  关节问题，本质上还是在靠"看视频猜"，只是从人猜变成了 AI 猜。

## 2. 更好的方案：分层过滤漏斗（Failure Funnel），而不是单一终点判官

核心思路：**不要用一个又晚又贵又噪声大的裁判去挡所有失败**。把现在"AI 写完直接上
真机"这一步，拆成一串越来越贵、但也越来越准的关卡（漏斗），让绝大多数会失败的代码
在便宜的关卡就被挡下来，只有真正大概率能成功的代码才会消耗真机时间和电池寿命去做
最终的物理验收。外部相机仍然是这个漏斗的重要一环，但只是最后一环，而且要和机载
遥测、确定性标记物一起做**多信号融合判断**，不能只靠 VLM 看视频。

```
0. 静态检查      mypy / lint（已有，未接入 harness）
1. 快速单测      pytest 默认套件（已有，未接入 harness）
2. 仿真闭环测试   MuJoCo（G1 已有；Go2 需要新建）+ 程序化断言（用仿真真值，不用视觉）
3. 真机安全预检   受限动作类别 + 物理安全网（超时停止/跌倒检测/关节限位）——目前完全缺失
4. 真机验收       外部相机（建议 ≥2 台或相机+标记物）+ 机载遥测 + VLM 语义判断，多数表决
5. 结构化失败证据回传 AI（不是一段视频，而是分层定位到底哪一步不对）
6. 熔断与安全停止  连续失败/跌倒/碰撞类故障 → 立刻停并叫人，不是无限重试
7. 合并门槛       N 次真机连续通过才可合并（真实世界有随机性，1 次通过不代表稳定）
```

### 为什么这样能把 2/100 提到接近 98/100

现在的 98% 失败，很多其实是"根本不该走到真机这一步"的失败——参数错误、API 用错、
明显不满足运动学约束、逻辑漏洞——这些在关卡 0/1/2 就该被挡住，而现在这些关卡**根本
没接进 AI 开发循环**（`run_multi_agent_loop.sh` 缺失）。先把这几层免费/低成本的关卡
接上，预期就能吃掉相当大一部分失败，而且完全不占用真机时间。

真正走到真机的候选代码，用"多信号融合 + N 次连续通过"代替"单摄像头单次判断"，可以
同时降低两类错误：假阴性（正确代码被误判失败，导致有效改动被浪费掉）和假阳性
（有缺陷代码被误判通过，混进主干后在生产环境才暴露，比现在更难查）。

### 关卡细节

**关卡 2：仿真闭环测试（新建 Go2 物理仿真是关键缺口）**
G1 已经有 MuJoCo 物理仿真链路可以参考。Go2 目前只有"回放录制日志"，没有真实动力学，
建议照 G1 的模式（`mujoco_sim.py` → sim blueprint → agentic sim blueprint）给 Go2 建一条
同样的仿真通道。仿真阶段的判定**不用视觉**，直接读仿真环境里的真值状态（关节轨迹、
接触事件、末端位姿是否到达目标）——便宜、确定性强、可大批量并行跑，能在几秒内验证
一个动作在物理上是否合理，不需要消耗任何真机资源。

**关卡 3：真机安全预检（目前完全空白，需要新建）**
仓库里现在没有任何物理安全网。建议新建一个"安全看门狗"模块，作为 Module 插入所有
真机 blueprint（复用现有的 Module/`In[T]`/`Out[T]`/blueprint 组合机制，不需要特殊
hook）：
- 基于 IMU 的跌倒/侧翻检测 → 立即触发安全姿态或急停；
- 关节限位/力矩越界 → 立即停止；
- 动作超时未完成 → 自动停止并回到安全位姿；
- 首次真机验收前，先跑一个"受限动作类别"预检（比如离地悬空测试台，或限定小幅度
  运动），确认基本不会摔倒/撞人，再放到自由场地做完整验收。

**关卡 4：真机验收——多信号融合，而不是单摄像头纯视觉**
- 外部相机建议用 **AprilTag/Fiducial 标记物**（仓库已有 `dimos/perception/fiducial/`）
  贴在机器狗身上，给出确定性、可复现、亚厘米级的位姿真值，用来判断"位移/朝向/高度"
  这类量化指标——不依赖 VLM，噪声远小于纯视觉语言模型判断。
- VLM（复用现有 `dimos/agents/vlm_agent.py`）负责语义性判断（"是不是完成了挥手/坐下
  这个动作"），处理标记物判断不了的定性问题。
- 同时把机载遥测（关节角度、IMU、足端接触，这些数据本来就在流里）和外部相机的判断
  做交叉验证：机载说"走了 2 米"，外部标记物追踪也确认位移 2 米，两者一致才算通过；
  不一致则升级为人工复核，而不是简单地判定失败——避免把"传感器一次性抖动"误判成
  "代码失败"。
- 建议不少于 2 个外部机位（或 1 相机 + 标记物）应对遮挡，单摄像头的遮挡/光照失败是
  常见的误判来源。

**关卡 5：结构化失败证据，而不是"一段视频甩给 AI"**
证据包应包含：视频片段、外部追踪与机载遥测的对比曲线、期望轨迹 vs 实际轨迹的差异、
VLM 判官给出的失败原因描述、仿真阶段是否通过（能区分"仿真过真机不过"=sim-to-real
差距问题，和"仿真也过不了"=逻辑问题，这两类问题 AI 需要用完全不同的方式去修）。
这比现在"人看着描述现象"精确得多，也是让 AI 能真正定位问题、而不是盲改的关键。

**关卡 6：熔断与安全停止**
同一任务连续失败达到阈值（比如连续 3 次）应暂停自动重试并通知人，而不是无限循环
消耗电池和硬件寿命；跌倒/碰撞/关节故障这类安全相关的失败，应该硬停止并要求人工
确认后才能继续自动化流程——这类判定不能只靠视觉判官，要和关卡 3 的安全网联动。

**关卡 7：合并门槛用"多次连续通过"而不是"单次通过"**
真实世界有随机性，摄像头判一次过，不代表这个功能稳定。建议要求同一任务连续 N 次
（比如 3/3）真机验收通过才把 PR 标记为可合并，这样能显著降低"看起来能跑，合并后又
不能跑"的情况，这也是把"稳定在 98/100"作为目标时必须要有的门槛，而不是"98 次中有
一次蒙对"。

## 3. 分阶段落地建议

1. **先把关卡 0/1/2 接进 `ai_longrun_harness`**：实现目前缺失的
   `run_multi_agent_loop.sh`，让它在开 PR 之前先跑 lint + 默认 pytest 套件（+ G1 已有
   的 mujoco 仿真测试）。这是当前性价比最高的一步——现在这条流水线上完全没有关卡，
   补上免费的静态/单测/仿真关卡，预期就能拦掉相当一部分失败，且不需要任何硬件。
2. **补 Go2 的物理仿真**：照 G1 的 MuJoCo 链路给 Go2 建一条对应的仿真 blueprint，这样
   实际在用的机型也能有仿真闭环测试，不再只能"回放日志"。
3. **建物理安全看门狗模块**：跌倒检测、关节限位、超时自动停止、安全姿态回退，作为
   标准 Module 插入所有真机 blueprint。这是目前完全空白、且是启用"无人值守自动重试"
   前必须先有的前提条件。
4. **建外部验收判官模块**：基于现有 `dimos/perception/fiducial/` 做位姿量化判断，
   基于现有 `dimos/agents/vlm_agent.py` 做语义判断，两者融合 + 与机载遥测交叉验证，
   输出结构化的通过/失败 + 置信度 + 证据包。作为 Module 订阅外部相机的 `Out[Image]`
   流和机器人遥测流即可，复用现有按类型匹配自动布线的 blueprint 组合机制。
5. **把 harness 串成完整闭环**：开发循环 → 关卡 0-2（静态/单测/仿真）→ 通过则部署
   真机 → 关卡 3 安全预检 → 关卡 4 外部验收（N 次）→ 失败则把结构化证据回传 AI 重试
   （有重试次数上限和熔断）→ 全部通过则标记可合并。
6. **打点度量**：记录每个功能在漏斗每一层的通过率，才能真正衡量是否在向 98/100 前进，
   并定位漏斗当前最漏的地方在哪一层，持续针对性改进。

## 4. 一句话总结

单台外部相机 + 视觉判断只是给了系统一双"事后的眼睛"，但现在的问题是整条流水线里
**几乎没有其他任何关卡**，且这双眼睛本身（单摄像头纯 VLM）也不够准。更好的方案是把
现有仓库里已经存在但没有串起来的能力（仿真、感知、blueprint 组合机制）先接成一个
分层过滤漏斗，让大部分失败在便宜的阶段就被挡住，真机阶段用多信号融合代替单一视觉
判官，并用"连续多次通过"代替"单次通过"作为合并门槛，同时补上目前完全空白的物理
安全网，让这套流程能安全地无人值守运行。

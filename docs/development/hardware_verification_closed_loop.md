# AI 写代码 → 真机验收闭环：现状诊断与改进方案

> 状态：设计提案（RFC），非最终实现。目标读者：负责 `ai_longrun_harness` 自动化闭环、以及 Go2/G1 真机联调的团队成员。
>
> 一句话结论：**只加一台外部相机、靠它单独判定成功/失败，解决不了准确率问题**——它只是把"人看机器狗描述现象"换成了"AI 看视频猜现象"，判断方式的主观性、单次试验的偶然性、以及"失败了但不知道为什么"这三个根本问题都还在。真正要把 2/100 提到 98/100，需要的是一个**分层验收漏斗 + 客观地面真值 + 结构化可回放的失败证据**，外部相机只是这套系统里的一个传感器，不是整个系统。

---

## 1. 现状诊断：为什么现在是 2/100

当前闭环是：

```
AI 写代码 → 人把代码部署到真机 → 人观察机器狗 → 人用自然语言描述失败现象 → AI 猜测原因并修改 → 重复
```

这个流程低成功率、慢反馈的根因不是"没有自动判断成功与否的手段"，而是三个更深层的问题，单独加一台相机都解决不了：

1. **没有分层过滤，每一次失败都要用最贵的资源（真机 + 人）来发现。** 仓库里已经有可用的仿真后端（见第 3 节），但 `pyproject.toml` 的 pytest 配置里 `mujoco`、`dimsim` 标记的测试被显式排除在 CI 之外（`-m 'not (tool or self_hosted or mujoco or dimsim)'`），也没有任何 CI job 会在仿真里跑一遍新代码再放行。也就是说，**再明显的低级 bug（坐标系错误、单位换算错、API 调用方式错）现在也是直接拿真机去试出来的**。这是 2/100 里绝大多数失败的真实来源，跟"要不要加相机"无关。
2. **失败反馈是非结构化的自然语言，AI 拿到的信息比人观察到的还少。** 人看到"狗摔倒了"或"没抓到球"，转述给 AI 的往往只是一句话总结，损失了时序细节（哪一步开始偏、当时的关节状态/朝向、命令下发的时间戳）。即使换成"外部相机判断成功/失败"，如果只产出一个 pass/fail 标签或一段视频，AI 依然要靠猜——只是从"猜人的转述"变成"看视频猜"，诊断效率提升有限。
3. **单次试验的信号噪声比很低，无法区分"代码错了"和"这次运气不好"。** 真机试验受地面摩擦、初始姿态、电量、网络延迟等因素影响，单次成功/失败不能证明代码的稳健性。100 次里 2 次成功，也可能是"平均成功率其实有 20%，但样本量太小、人力盯不了 100 次"。不上仿真批量试验、不做统计口径，无论判定手段是人眼还是相机，得到的都是一次性的、置信度很低的信号。

**结论：外部相机解决的是"判断这一次是否成功"，但真正卡住准确率的是"绝大多数失败根本不该走到需要判断这一次是否成功的阶段"，以及"知道失败了但不知道为什么"。方案必须先补这两块，相机才有意义。**

## 3. 为什么"外部相机 + 二元判定"这个方案本身不够好

在给出改进方案前，先说清楚原设想的三个具体缺陷，这样后面的架构选择才有依据：

### 3.1 单一裁判 = 单点故障，而且是主观的单点故障
如果只用一台相机 + 一个"是否达成"的判定，判定本身的错误率会直接叠加进最终准确率里。VLM 类判定对"部分完成""动作变形但勉强达标""被遮挡瞬间"这类边界情况有明显的幻觉/不一致问题。用它做**唯一**裁判，等于用一个新的不确定系统替换掉旧的不确定系统（人工判断），准确率提升有天花板。

### 3.2 只在"真机上跑一次"这个时间点判定，反馈还是慢
真机部署 + 人工/相机观察 + 报告现象，这个循环的**单次迭代成本**没有变。之前 100 次里只成功 2 次，说明大部分失败其实是能在仿真里几秒钟发现的低级错误（见第 1 节）。不管裁判是人还是相机，只要还是"真机试了才知道"，调试速度就快不起来。

### 3.3 只有视频，没有可回放、可诊断的结构化状态
相机能告诉你"没做到"，但不能直接告诉你"为什么没做到"（是坐标系反了、是力矩不够、是时序抢跑、还是感知误检）。AI 拿到一段视频依然要靠猜测——这跟拿到一句人工转述相比是量的提升（更客观、更少丢信息），但不是质的提升（依然缺状态级别的因果链）。

### 3.4 没有统计口径，单次通过就合并 = 引入新的偶然性
如果"相机判定通过 = 可以合并"，那 100 次里可能又出现"这次因为运气好没摔倒，其实动作本质上不稳定"的情况——只是把"人眼觉得还行就合并"换成了"相机觉得还行就合并"，稳健性没有真正提升。

## 4. 提出的架构：分层验收漏斗 + 多信号地面真值 + 结构化失败证据

### 4.1 总体结构

```
┌─ Stage 0  静态检查 ───────────────────────────────────────────┐
│  lint / mypy / 现有 CI（已存在，不用动）                        │
└──────────────────────────────┬────────────────────────────────┘
                                ▼
┌─ Stage 1  仿真回归（秒级~分钟级，全自动，零人工，零硬件风险）────┐
│  复用 dimsim/mujoco blueprint，扩展现有 e2e_tests 模式：         │
│  每个 skill 在随机化初始条件下跑 N 次（如 N=20）                 │
│  地面真值断言：里程计/关节状态/物体位姿（不是 VLM 猜的）          │
│  门槛：成功率 ≥ 阈值（如 90%）才能进入下一阶段                   │
└──────────────────────────────┬────────────────────────────────┘
                                ▼
┌─ Stage 2  半物理台架测试（真实电机/真实控制栈，机身固定/悬吊）───┐
│  验证仿真到真实执行器的动力学是否一致，不会摔机、不需要人值守场地 │
│  可以用现有 self-hosted-tests 的自建 runner 模式接一台带电机台架 │
└──────────────────────────────┬────────────────────────────────┘
                                ▼
┌─ Stage 3  受限真机试验（拴绳/护栏/限定场地 + 外部相机阵列）──────┐
│  这里外部相机才登场，且不是唯一裁判：                             │
│    - Fiducial marker 位姿（客观几何真值，复用 dimos/perception/fiducial）│
│    - VLM 语义判定（复用 dimos/agents/vlm_agent.py，判定"任务级"目标） │
│    - 机身遥测融合（关节力矩/IMU/足底力，判定"看着成功但其实不稳"）   │
│  独立安全层：跌倒检测/超限自动急停（现在完全没有，见 4.4）         │
│  多次试验（如 M=10）→ 二项分布置信区间，不是单次通过/失败          │
└──────────────────────────────┬────────────────────────────────┘
                                ▼
┌─ Stage 4  合并门禁 ──────────────────────────────────────────┐
│  接入 ai_longrun_harness/run_pr_pipeline.sh，作为 required check │
│  未达标 → 自动打包结构化失败证据（4.3）回传给 AI，继续迭代，       │
│           不进入人工 review 队列                                │
└──────────────────────────────────────────────────────────────┘
```

关键设计原则：**越往下的阶段越贵、越慢、越依赖真实硬件，所以流量应该指数级衰减**——大部分候选代码应该死在 Stage 1，只有已经在仿真里稳定的代码才配消耗真机时间和人的关注力。这才是把"发现问题"这件事从"真机+人"转移走、从而把调试速度提上来的关键，而不是相机本身。

### 4.2 视觉判定子系统设计（相机在这里，但不是全部）

外部相机进程应该是**独立于机器狗自身感知栈的第三方观测者**（这点原设想是对的，要保留）：单独的相机 + 单独的进程，不依赖机身上可能本身就有 bug 的感知代码，避免"用可能有问题的系统去验证自己"。具体建议：

- **不要只用一个 VLM 判定当唯一信号**。融合三路信号，两两互相校验，任一路异常都应该保守地判定为失败或标记为"不确定，转人工"：
  1. **几何地面真值**（权重最高，最不主观）：机身贴 fiducial marker，外部相机做 6-DoF 位姿解算，直接复用 `dimos/perception/fiducial/marker_tf_module.py` 和 `fixture_verification.py`。适合"移动到指定位置""转向指定角度""抓取物体是否位移"这类可几何化的任务。
  2. **语义判定**（复用 `dimos/agents/vlm_agent.py`）：适合几何无法穷举描述的任务（"像正常走路一样走""没有明显跛行"）。给它固定的评分 rubric，而不是开放式问答，减少幻觉。
  3. **机身遥测交叉验证**：关节力矩/角速度/足底力是否在正常范围内，即便相机判定"动作完成"，遥测异常（比如力矩持续接近限位）也应判为不合格——这是相机看不出来但真机长期可靠性最相关的信号。
- **裁判进程通过 LCM 发布结构化 verdict**（复用 `dimos/protocol/pubsub/impl/lcmpubsub.py`），和现有的 `lcm_spy` 测试基建保持同一套时间戳体系，方便和命令下发时间对齐。
- 判定结果三态而不是二元：`pass` / `fail` / `uncertain`（比如被遮挡、marker 丢失）。`uncertain` 不能自动判 pass，也不该直接判 fail 计入统计，要么重试要么转人工抽检——避免相机自己的失败模式污染判定准确率。

### 4.3 结构化失败证据包（这是提升"调试速度"的核心，而不是相机）

现在人工转述"机器狗摔倒了"这种反馈，本质上是在丢弃仓库里其实已经能采集到的信息。每次 Stage 3 试验（不管 pass/fail）都应自动产出一个**证据包**，失败时自动推给 AI：

- 复用 `dimos/memory2/store/sqlite.py` 的记录能力，把该次试验的完整传感器/命令历史落盘（和现有 `data/.lfs/*.db` 回放数据集同一格式）。
- 外部相机视频 + 逐帧的 verdict 时间线（哪一秒开始偏离预期）。
- 关键状态快照：命令下发时刻 vs. 实际关节响应时刻的时序差、最后一次已知正常状态。
- **可直接用 `ReplayConnection`（`dimos/robot/unitree/go2/connection.py`）在仿真里重放这次失败的确切轨迹**——AI 拿到失败证据后，第一步应该是在仿真里复现问题、验证修复假设，而不是必须再申请一次真机窗口。这一步直接解决"每次失败都要人重新观察、慢且不标准"的问题：证据是标准格式的文件，不是人的记忆和转述。

### 4.4 安全层（现在完全缺失，且这套方案会把真机试验频率提高，必须先补）

因为本方案意味着 Stage 3 的真机试验次数会比现在更频繁（要凑够统计样本），**必须先有一个不依赖 AI 写的代码是否规矩的独立安全层**，而不是继续只靠 system prompt 里那句话：

- 关节力矩/速度硬限位（执行器驱动层，不经过 LLM 决策路径）。
- 跌倒/异常姿态检测 → 自动切断当前 skill、回到安全姿态（可以用 IMU 阈值，简单可靠，不需要 AI 判断）。
- 物理/电子围栏：Stage 3 场地里出界即急停。
- 复用 `dimos/skills/kill_skill.py` 的手动急停通路，加一条自动急停触发源。

这一层的意义不止是保护设备，也是让"提高真机试验吞吐量"这件事本身是安全的，是把 2/100 提到 98/100 所必需的前提条件之一。

## 5. 用统计口径回答"98/100"到底怎么定义

"100 次功能里 98 次能正确运行"不应该理解成"新代码提交后跑一次真机、100 次里 98 次通过"，而应该拆成两层指标，且都要在 Stage 1/3 里分别度量：

1. **单个 skill 的稳健性**：同一段代码在随机化初始条件下重复试验的成功率（比如 Stage 1 仿真里跑 20 次、Stage 3 真机里跑 10 次），用二项分布下界估计真实成功率，而不是看单次结果。
2. **一批 skill/功能里，"达到可合并标准"的比例**：这才是"100 个功能里 98 个能跑起来"这句话真正对应的指标——即 100 次 AI 提交的功能变更里，有多少通过了上面的分层漏斗且没有回退安全事件。

Stage 1 仿真回归天然支持大样本重复试验（便宜、快），所以"稳健性"这个维度的置信度主要应该在仿真阶段建立；真机阶段只需要做**确认性**的少量重复（比如 10 次），验证仿真到真实世界没有明显 gap。这样既控制了真机资源消耗，又不会把"合并标准"退化成"一次运气好的真机演示"。

## 6. 落地路线图（建议的最小起步范围）

不建议一次性铺开全部四个 Stage，按下面顺序推进，每一步都是独立可交付、可验证收益的：

**P0（不需要买相机就能做，收益最大）**
- 把 `mujoco`/`dimsim` 标记的测试重新纳入 CI 必跑范围（或至少纳入 `self-hosted-tests` 同级别的 required check），先堵住"仿真里一眼能看出的 bug 也要拿真机试"这个最大漏洞。
- 补上 `ai_longrun_harness/run_multi_agent_loop.sh`（当前被 `run_to_main.sh` 引用但不存在），并在其后接一个仿真回归步骤，而不是直接进 PR pipeline。
- 把 `dimos/e2e_tests/test_dimsim_walk_forward.py` 这种"地面真值断言"模式，从目前只覆盖导航，扩展到更多 skill 类型（抓取、转身、手臂动作等），作为 Stage 1 的雏形。

**P1（引入外部相机，但作为多信号裁判之一，不是唯一裁判）**
- 搭建 Stage 3 场地：固定机位相机 + 机身 fiducial marker，跑通 `dimos/perception/fiducial` 的位姿解算链路。
- 用 `dimos/agents/vlm_agent.py` 搭一个独立于机身感知栈的裁判进程，只做语义判定，几何判定交给 marker。
- 定义结构化失败证据包的 schema（复用 memory2 SQLite），跑通"失败 → 自动打包 → AI 在仿真里回放复现"的链路。

**P2（安全层 + 统计门禁 + 全链路自动化）**
- 补最小可用的安全层（跌倒检测自动急停、关节限位）。
- 把 Stage 1/3 的多次重复试验 + 统计置信区间，接成 `run_pr_pipeline.sh` 的 required gate。
- 视情况扩展多相机/多角度覆盖遮挡问题，视情况引入台架测试（Stage 2）。

## 7. 一句话版本（给决策层）

不要把"加一台相机"当成解决方案本身，它只是分层验收漏斗里最后、最贵的那一级传感器。真正决定能不能从 2/100 走到 98/100 的是：**大部分错误在仿真里被免费拦住（复用仓库里已有但没接入 CI 的 mujoco/dimsim 能力）、真机判定用多路客观信号而不是单一主观判定（marker 位姿 + 遥测 + VLM，而不是只有 VLM 看视频）、失败反馈是可回放的结构化证据而不是人的转述、以及一个不依赖 AI 代码是否规矩的独立安全层，让高频真机试验本身是安全的**。这四件事里，相机只解决了其中一小部分（多路信号里的一路），其余部分现在都还是空白，且优先级都比"买相机"更高、更便宜。

# 真机验证闭环：从"人工看狗+单相机验收"到可信赖的自动化闭环

> 目标：把"AI 写代码 → 部署真机 → 人工观察描述现象 → AI 继续改"这个流程，改造成一个可
> 重复、可审计、可安全停止、并且**首次真机成功率能从约 2/100 提到约 98/100** 的闭环。
>
> 参照 Boris Cherny《Steps of AI Adoption》的成熟度阶梯（Gated → Assisted → Parallel →
> Supervised autonomy → AI-native），我们目前在"真机这一环"上还停留在 **Step 1
> Assisted**：一人一个 agent，人必须盯着每一次真机运行、用自然语言描述失败现象。阶梯文档
> 自己给出的"1→2 的路径"是——**造一个你真正信任的自验证闭环**（对代码而言是
> `tests + build + lint + e2e`）。这篇文档就是在回答：**对一台四足机器人而言，这个"自验证
> 闭环"应该长什么样**。结论不是"加一个外部相机做终验"，而是"用一整条从便宜到昂贵的漏斗
> 替换掉单点终验"，外部相机只是漏斗里最后、也是最贵的一级。

## 1. 现状方案为什么不够好

现状：额外加一台独立相机，机器狗跑完指定动作后，由这台相机判断"做到了没有"；做到了就
进入可合并状态，没做到就把"证据"甩给 AI 继续改。这个想法方向是对的（引入独立于机器人自身
的观察者），但作为**唯一**的验收机制，有七个结构性问题，合在一起解释了为什么现在 100 次
里只有 2 次能跑通：

1. **验收点太晚、太贵。** 唯一的信号来自"整段真机运行结束之后"。一次真机试跑的固定成本
   （摆好场地、充电、Wi-Fi/BLE 连接、人工值守、机器人复位）远高于一次仿真运行，但相机方案
   把所有 bug——包括跑仿真三十秒就能发现的低级错误（坐标系写反、API 调用参数错、越界指令
   直接被 Unitree 固件安全层拒绝）——都留到最贵的一级才暴露。这是当前循环慢的最大原因，
   不是相机判断不准，而是**根本不该让这么多次尝试走到相机这一步**。

2. **反馈信号维度太窄，"通过/不通过"不能定位原因。** 一段视频/几张图 + 一句"没做到"，既
   不能告诉 AI 是逻辑 bug、坐标系 bug、被机载安全限制截断、网络时延导致指令丢失、sim2real
   gap（真实摩擦力/电机限矩和仿真不一致），还是纯粹的硬件问题（低电量、意外触发急停）。
   现状里"翻译"这层差异的工作是人在做——人看着狗描述现象——这正是把吞吐量摁在"一人盯一次
   跑"的原因。

3. **没有把已有的仿真能力用起来做前置漏斗。** 仓库里其实已经有相当完整的仿真栈：
   `dimos/simulation/mujoco/`（主力后端，`dimos --simulation run unitree-go2` 可直接跑）、
   `dimos/simulation/dimsim/`（配合 `dimos/e2e_tests/` 的轻量仿真+回放，走 LCM）、以及
   Isaac Sim / Genesis / Unity 的薄封装。但 `docs/platforms/quadruped/go2/index.md` 描述
   的部署路径是"发现 → 连 Wi-Fi → 拿 IP → `dimos run unitree-go2` 直接上真机"，中间没有
   "先过仿真关"这一步。多数会在真机上炸的低级错误，仿真几秒钟就能复现。

4. **"指定动作"是自然语言，既没有机器可判定的验收标准，也没有可复现的任务定义。** 相机+
   人工/VLM 判断"看起来像不像做到了"，本质上是主观题。同一个任务，两次录像给不同的人看，
   结论可能都不一致（遮挡、机位、光线）。要做到 98/100 这种工程级可靠性指标，"通过"必须
   是可机器判定、可复现、有容差范围的谓词（例如"沿 +x 方向净位移 > 2m，过程中无摔倒事件，
   步态频率落在 1.5–2.5Hz，终止姿态直立"），而不是单一 VLM 一句"看起来对/不对"。

5. **没有安全包络（safety envelope），人不敢放手，闭环就自动化不起来。**
   `docs/platforms/quadruped/go2/index.md` 里能查到的唯一安全机制是 Unitree 固件自带的
   机载避障，DimOS 层面没有速度/力矩/工作空间的独立限幅，没有跌倒/关节超限/低电量/断连时
   的强制停止。没有这层"就算 AI 写的代码是错的，机器人也不会真出事"的保证，人就必须每次
   都守在现场，这正是 Cherny 阶梯里 Step 1（"你的注意力和逐条检查每个改动"）卡住不动的
   根本原因——不是不想放手，是没有敢放手的理由。

6. **失败证据不是结构化、可版本化、可回放的。** 仓库里已经有 `dimos/memory2/`
   （SQLite 记录）+ `dimos/utils/testing/replay.py`（`Memory2ReplayAdapter`，可以把记录
   的流按真实/加速时间重放），但目前没有在"真机试跑失败"这个事件上自动打包证据。现状是
   人重新回忆、口头转述"它往前走了两步然后往左倒了"，这种转述信息密度低、不可复现、也没法
   喂给下一次自动诊断。

7. **没有回归集，可靠性无法累积。** 每个新任务只针对自己验证一次，没有一个不断增长的
   "Go2 必须稳定做到的 N 件事"黄金测试集在每次改动后重新跑一遍。98/100 描述的是一个**统
   计意义上稳定**的可靠性，单次试跑的运气不构成这个统计量；没有回归集，今天修好的动作明天
   可能被下一次改动悄悄弄坏而没人发现。

## 2. 核心思路：把"单点终验"换成"漏斗 + 多信号仲裁 + 结构化证据闭环"

和软件里的 `lint → build → unit test → e2e test` 一样，把验证拆成一条从便宜、快、确定性
强，到昂贵、慢、涉及物理世界的漏斗，**每一级只放行足够便宜就能筛掉的错误**，外部相机只
承担漏斗里最后、且是"物理世界是否真的发生了预期变化"这一件事，不再是唯一的裁判。

```
Stage 0  静态检查      mypy / pre-commit                          （已有，CI 已跑）
Stage 1  单元/契约测试  robot API 调用是否合法                       （已有 pytest 体系）
Stage 2  仿真回归       MuJoCo（主力）/ dimsim（导航类）headless 跑
                        一遍，用和真机同一套「多信号验证器」判定
Stage 3  安全包络静态检查 命令的速度/力矩/工作空间是否越界，
                        与 AI 写的代码逻辑完全独立、不可被绕过
Stage 4  真机试跑 + 多信号验证（含外部相机）  独立看护进程实时监控，异常直接急停
Stage 5  失败证据自动打包  git SHA + 任务规格 + 全部信号录制 + 判据打分 + 失败假设
Stage 6  回归集累积       新通过的任务规格自动并入黄金测试集，防止越改越差
Stage 7  合并门禁         仿真回归全绿 + 真机重复试跑 N/N（不是 1 次）
                        + 黄金回归集全绿 + 安全包络检查全绿 → 才允许合并
```

失败越早暴露、修复成本越低——这条漏斗的意义不是"让相机更准"，而是让绝大多数尝试根本不需
要走到相机这一步就已经被挡下来，真正到真机、到相机面前的，是已经在仿真里跑对过一次的代码。

### 2.1 Stage 2：仿真回归 —— 用同一套判据在 MuJoCo 里先跑一遍

关键设计原则：**仿真和真机用同一套"多信号验证器"和同一份任务规格**，不是仿真一套标准、
真机再另一套。这样才能拿到一个可监控的指标——"仿真判定通过、真机判定失败"的比例，这就是
sim2real gap 的量化值，出现漂移时能第一时间发现，而不是笼统地怀疑"仿真不准"。

对接点：`dimos/simulation/mujoco/`、`dimos/robot/unitree/mujoco_connection.py`。

### 2.2 Stage 3：安全包络 —— 独立于 AI 代码的静态限幅

不信任 AI 写的代码会"自己注意安全"，而是在部署前对即将下发的指令序列做静态检查（速度/
加速度/力矩/工作空间边界），加上运行时看护进程实时订阅关节状态 + IMU + 外部相机，检测到
跌倒/关节超限/低电量/失联时立即触发独立于被测代码路径的急停。这一层不存在于当前文档
（`docs/platforms/quadruped/go2/index.md` 只提到 Unitree 自带机载避障），是新建能力，
但正是这一层让人可以放心让机器人在没人盯着的情况下自动重试——即 Cherny 阶梯里
"Step 1 → Step 2" 真正需要的信任基础。

### 2.3 Stage 4：多信号验证，相机是其中一路信号，不是唯一信号

单一外部相机 + "看起来对不对"这种判断方式误差率必然偏高（遮挡、机位、光照、VLM 幻觉）。
把验证拆成四路信号，取代"只问 VLM 一句话"：

- **本体感受信号**（已有数据源，通过 `dimos/memory2/` 可直接录制）：关节角度/速度、IMU、
  里程计、电量、急停状态。这是**主判据**——例如"净位移是否达标""是否发生跌倒""末态姿态
  是否直立"，这些用本体传感器判断，比看视频猜测精确得多，且不受相机角度影响。
- **机载相机**（已有感知栈：`dimos/perception/detection/detectors/`、`object_tracker.py`）
  提供粗粒度信号，例如"目标物体是否进入过视野""是否检测到跟踪对象"。
- **独立外部相机**（新增，1–2 个固定标定机位，减少单一视角遮挡问题）——负责回答本体传
  感器无法回答的问题："物理世界是否真的按预期发生了变化"（例如物体是否真的被移动到了
  指定位置，而不是本体里程计因打滑而漂移出的假象）。这一路的判据是**结构化的、可写成代
  码的**几何/位置判据（参考 `dimos/perception/fiducial/fixture_verification.py` 的
  "accept/reject + reject_reasons" 模式，而不是"发一张图问 VLM 对不对"）。
- **VLM 作为次要信号、且专职生成失败描述，不作主裁判**：VLM 擅长的是"这次失败大概是什么
  原因"这种开放式描述（这是它能显著提速反馈循环的地方），但不适合作为 accept/reject 的
  唯一依据——它没有稳定到能撑起 98/100 这种可靠性数字所需要的精度。任务规格里的机器可判
  定谓词才是主裁判，VLM 只在谓词判定为"临界/存疑"时作为仲裁，或者恒定用于生成人类可读的
  诊断摘要。

对接点：新建模块可以仿照 `dimos/agents/vlm_agent.py`（`VLMAgent`，已经能订阅图像流、调
用任意 LangChain 模型）扩展一个"独立外部相机流 + 结构化 judge"的变体。

### 2.4 Stage 5：失败证据自动打包 —— 把"人转述"变成"结构化回放包"

一次失败自动产出一个证据包，而不是靠人回忆转述：

- git commit SHA + 本次任务规格（YAML）
- 全部信号的时间对齐录制（复用 `dimos/memory2/` 存储 + `Memory2ReplayAdapter` 回放能力，
  加一路外部相机流进同一个数据集）
- 每路信号各自的判定结果和分数（复用 `fixture_verification.py` 式的
  `accepted / reject_reasons` 结构）
- 失败发生在漏斗的哪一级（本身就是强诊断信号：Stage 0/1 失败=代码错误；Stage 2 失败=
  逻辑/规划错误；Stage 2 通过但 Stage 4 失败=sim2real gap 或硬件/环境问题）
- 一段由 VLM 生成的自然语言"最可能原因"摘要，供 AI 下一轮诊断时直接读取，而不必重新猜测

这个证据包就是喂给下一轮 AI 修复循环的输入，替代当前"人观察机器狗、描述现象"这一步，也
是把调试节奏从"人力限速"变成"自动化限速"的关键。

### 2.5 Stage 6/7：回归集与合并门禁

每个通过 Stage 4 的任务规格都并入黄金回归集，之后每次改动都要在仿真里对整个回归集重跑
（真机层面可以定期抽样/夜间跑），防止可靠性只是"单次运气"而非"统计稳定"。合并门禁要求
**同一任务规格连续重复试跑 N 次全部通过**（例如 5/5），而不是 1 次——这是从"能跑通一次"
到"98/100 这种可靠性数字"之间必须补上的一步：任何物理系统都有噪声，单次通过对可靠性几乎
没有统计意义。

## 3. 这如何把成功率从 2/100 提到 98/100

先说清楚"2/100"和"98/100"实际上是两件不同的事，方案要同时覆盖两者：

- **(a) 首次尝试命中率**：AI 写出的 100 个不同动作里，有多少个不需要人工介入就能正确跑
  通。当前瓶颈主要是"仿真本可以筛掉的低级错误也要跑到真机才发现"——Stage 0–3 的漏斗直接
  处理这一项，预期能把绝大多数尝试挡在真机之前，省下的每一次真机机会都用在真正的 sim2real
  差异上。
- **(b) 单个动作的重复可靠性**：某个动作跑 100 次里有多少次成功。这靠 Stage 4 的多信号
  验证（减少误判）+ Stage 7 的重复试跑门禁（不让"蒙对一次"当作交付标准）+ Stage 6 的回归
  集（防止后续改动悄悄破坏已验证过的可靠性）来保证。

两者共同作用的机制：漏斗越靠前挡掉的问题越多，每一次真机尝试的"含金量"越高（真正在测试
sim2real gap，而不是在重新发现代码里的低级错误）；而 Stage 5 的结构化证据包让每一次真机
失败都能被精确归因，AI 下一轮修复的针对性显著提高，不再是"改了但不知道改没改对地方"。
这个飞轮转起来后，golden 回归集会越滚越大，sim2real gap 记录（Stage 2 判过、Stage 4 没
过的清单）会反过来指导仿真参数/物理模型的校准，形成"仿真越来越准 → 真机首发命中率越来越
高"的正反馈。

对照 Cherny 的阶梯：这套"仿真回归 + 多信号验证 + 安全包络"就是物理机器人版本的"你真正信
任的自验证闭环"（对代码是 tests+build+lint+e2e，对机器人是 sim regression + 多信号 judge
+ safety governor）。有了它，人的角色才能从"盯着每一次真机运行"（Step 1: Assisted）变成
"只看漏斗筛出来的候选、按例外监控"（Step 2/3: Parallel / Supervised autonomy）——这不是
锦上添花，是让"多次并发自动重试"这件事在物理世界里安全可行的前提条件。

## 4. 与现有代码的对接点（落地不是从零开始）

| 能力 | 现有代码 | 用途 |
|---|---|---|
| 仿真后端（主力） | `dimos/simulation/mujoco/`, `dimos/robot/unitree/mujoco_connection.py` | Stage 2 仿真回归 |
| 轻量仿真 + 回放 | `dimos/simulation/dimsim/`, `dimos/e2e_tests/` | 导航类任务的 Stage 2 |
| 视觉/VLM 基础设施 | `dimos/agents/vlm_agent.py`（`VLMAgent`） | 外部相机 judge 的次要信号、失败摘要生成 |
| 感知栈（机载相机） | `dimos/perception/detection/detectors/`, `object_tracker*.py` | Stage 4 的机载相机信号 |
| accept/reject + 原因 的判定模式 | `dimos/perception/fiducial/fixture_verification.py` | 外部相机结构化判据的实现范式 |
| 录制/回放 | `dimos/memory2/`, `dimos/utils/testing/replay.py`（`Memory2ReplayAdapter`） | Stage 5 证据包 |
| CI 骨架 | `.github/workflows/ci.yml`（lint / tests / self-hosted-tests） | Stage 0/1，可扩展 Stage 2 的仿真回归 job |
| AI 开发闭环外壳 | `ai_longrun_harness/run_to_main.sh`, `run_pr_pipeline.sh` | 需要在其中插入 Stage 2–7 的门禁（见下） |

`ai_longrun_harness/run_to_main.sh` 目前的流程是「多智能体开发循环 → 直接推 PR」，中间
完全没有验证门禁，而且它依赖的 `run_multi_agent_loop.sh` 在仓库里还不存在（脚本本身会在
运行时报错缺文件）。本次改动新增了 `run_sim_gate.sh` / `run_hw_verify.sh` 两个阶段脚本
的骨架，并在 `run_to_main.sh` 中把它们接到"开发循环"和"推 PR"之间，具体见
`ai_longrun_harness/README.md`。`run_multi_agent_loop.sh` 本身的实现不在本次范围内，需要
使用方按自己的多智能体编排方式补上。

## 5. 落地路线图（建议分四期，每期独立可用）

1. **Phase 1 — 仿真漏斗 + 证据包（不改真机流程，风险最低）**：把 Stage 0–2 和 Stage 5
   先跑通，任务规格（YAML）+ 判定器先在仿真里验证。这一步已经能显著减少真机尝试次数，
   且完全不涉及硬件安全问题，可以先落地。
2. **Phase 2 — 外部相机 + 多信号真机验证**：接入独立外部相机，实现结构化判据（参照
   `fixture_verification.py`），把本体感受信号也接入同一套判定器。
3. **Phase 3 — 安全包络 + 无人值守重复试跑**：静态限幅检查 + 运行时看护进程，只有这一步
   做完，才有理由让"重复试跑 N/N"在无人盯着的情况下自动进行。
4. **Phase 4 — 回归集 + 合并门禁自动化**：把 Stage 6/7 接入 CI/PR 流程，形成完整闭环。

## 6. 如何验证"这套验证方案本身"是可信的

方案自身也需要被监控，否则容易变成新的"看起来很科学但没人知道准不准"的黑箱：

- **核心 KPI**：跟踪"首次真机尝试命中率"随时间的变化趋势，这是唯一真正衡量目标是否达成
  的数字，不能只看"漏斗内部通过率"。
- **sim2real gap 台账**：记录"仿真判过、真机判不过"的任务清单和原因，定期用于校准仿真
  参数；这个清单本身如果持续增长而不收敛，说明漏斗前段（仿真）在给出错误的信心，需要优先
  处理。
- **判据误判率**：定期抽样让人复核外部相机+多信号 judge 的判定结果，跟踪 false
  accept（其实没做到但判过了，最危险）和 false reject（其实做到了但判定失败，影响效率）
  两类误判率，分别设置告警阈值。

## 7. 风险与限制

- MuJoCo 仿真对接触密集型动作（四足步态、打滑、地面材质）天然存在建模误差，Stage 2 不能
  完全替代真机验证，只能大幅减少走到真机的低质量尝试次数；sim2real gap 台账机制正是为了
  持续量化并收窄这个误差，而不是假装它不存在。
- 外部相机存在标定漂移、遮挡、光照变化等问题，判据设计上应该对"信号缺失/置信度低"显式建
  模为"不可判定"而不是强行给出 pass/fail，避免把噪声误当成信号。
- 真机重复试跑（Stage 7）会显著增加设备磨损和调试时长，N（重复次数）应该按任务风险分级，
  不是所有任务都需要同样高的重复验证次数。
- 安全包络的初始参数需要人工评审设定并留出足够裕度，不能完全依赖 AI 生成，这是防止"给
  AI 写的安全限制被 AI 自己的 bug 绕过"这一类问题的最后一道独立防线。

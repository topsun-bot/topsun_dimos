# 提高真机验证成功率：从"单一外接相机"到"分层验证漏斗"

> 目标问题：目前 100 次 AI 生成/修改的机器狗（Unitree G1/Go2）功能，只有约 2 次能在真机上正确跑起来；希望提升到 98/100。当前设想是在调试场地外加一台独立相机，自动判断动作是否完成，达标就合并、不达标就把失败证据交给 AI 继续修改。本文分析这个方案的局限，并给出一个更完整的方案。

## 1. 现状：验证只有"最后一关"，而且这一关是人工的

现有链路（依据 `AGENTS.md`、`docs/development/testing.md`、`.github/workflows/ci.yml`、`scripts/sync_g1_orin.sh`、`docs/platforms/humanoid/g1/greeter_onboard_opus_dev.md` 梳理）：

1. **本地/CI 只能做到"代码层"验证**：`uv run pytest`（默认套件）跑纯逻辑单测；`self-hosted-tests` job 在一个 `ros-dev` **容器**里跑重依赖测试，但这个容器不是接到真实机器狗的硬件在环环境（`.github/workflows/ci.yml:204`）。仓库里其实已经有仿真基建（MuJoCo、Isaac、Genesis、自研 `dimsim`，见 `dimos/simulation/`），并且 Go2 已经有一套基于 `dimsim` + LCM 断言的端到端测试模式（`dimos/e2e_tests/test_dimsim_*.py`，例如用 `lcm_spy.wait_until_odom_position(...)` 断言机器人真的走到了目标点）。但 G1 侧目前只有 MuJoCo 可视化仿真（`dimos/robot/unitree/g1/mujoco_sim.py`），**没有等价的、跑真实高层控制代码路径（`effectors/high_level/dds_sdk.py`、`webrtc.py`）的仿真在环回归测试**。
2. **部署是手工、非可复现的**：`scripts/sync_g1_orin.sh` 用 `rsync` 逐文件把一份"人工维护的文件清单"同步到 Orin 板载电脑，然后人工 SSH 上去手动执行 `orin_run_*.sh`，还要先手动把机器狗扳到 Sport 平衡模式（FSM）才能让代码生效（`docs/platforms/humanoid/g1/index.md`）。这意味着"笔记本上测过的代码"和"Orin 上实际跑的代码"之间没有强一致性保证——漏同步一个文件、忘了改文件清单，都会造成和逻辑对错无关的真机失败。
3. **失败反馈是人工转述**：真机跑挂之后，由人观察现象、口头/文字描述给 AI，AI 再猜测原因、改代码、再让人重新部署验证。这是目前唯一的"验收+反馈"环节。
4. **最有说服力的证据**是 `docs/platforms/humanoid/g1/greeter_onboard_opus_dev.md`：这份开发记录显示，AI 在本地只能做到 pytest/ruff/mypy 自测（因为 `unitree_sdk2py` 在开发机上根本装不上，硬件相关 blueprint 连 import 都跑不通），几乎所有硬件相关行为——手臂动作只在 FSM 状态 500/501/801 下生效、`corrected_odometry` 因 PGO 回环修正可能瞬间跳变导致"到站"判断被跳过（§7、§9.7）——都被列为"真机待验证"，只能等人上真机试。这些坑本质上是**已知的、可枚举的**，但目前没有任何自动化机制把它们变成回归用例，所以同类问题会反复出现在不同功能上。

结论：当前 2/100 的成功率，绝大部分损耗**发生在相机能看到"动作"之前**——代码根本没跑起来、部署漂移、FSM 前置状态不对、DDS/遥测异常。相机只能在"机器狗已经开始做动作"之后才有信号可判。

## 2. 为什么"只加一台外接相机做终审"不够好

把相机方案单独拿出来看，有三个结构性问题：

**(a) 它只覆盖漏斗的最后一环，而这一环之前已经损耗了大部分成功率。** 把失败原因粗分成几类：①语法/构建/import 错误、②纯逻辑错误（阈值、状态机判断）、③FSM/DDS 时序与硬件调用契约错误（如 §9.7 的 PGO 跳变类问题）、④部署产物与代码不一致、⑤真实物理动力学与仿真的偏差。目前①-④几乎不被任何自动化环节拦截，直接原样传导到真机测试这一步。相机只能在类别⑤（以及部分类别③）里产生有效信号；如果机器狗因为①-④直接"站在原地不动"或者进程崩溃，相机得到的信息量并不比现在人工观察多多少，只是把"人看"换成了"AI看"，没有解决大部分故障的根因。

**(b) 视觉判"过/不过"本身是个噪声很大的裁判。** 遮挡、光照、动作定义模糊（"这个后空翻算不算标准"）都会让视觉大模型的判定不稳定；而且每一次判定都要求真的让机器狗把动作物理执行一遍——成本高（几十秒到几分钟）、还有跌倒/碰撞的物理风险。用一个不够可靠的裁判去把关一个成本极高的验证环节，性价比很差。

**(c) 缺少安全约束的"失败→自动改→自动再部署→自动再跑"闭环，在实体机器狗上是有风险的。** 如果相机判"不通过"就自动触发下一轮无人值守的真机重试，一旦是新类别的动作、或者代码改坏了运动控制导致机器狗直接摔倒/撞人，没有人在现场，这是要出安全事故的。方案需要显式的止损和分级自治机制，而不是"相机说了算,一直循环"。

## 3. 更好的方案：分层验证漏斗（shift-left + 物理终审）

核心思路：**把能在真机之外验证的问题尽量往左移**，让机器狗真机测试只用来验证"仿真/静态分析验证不了的那部分"（主要是真实动力学、真实传感器噪声、真实环境）。相机+遥测融合裁判仍然是这个方案的一部分，但只是最后一层，而不是唯一一层。

```
Layer 0  静态 & 构建正确性     秒级   本地/CI
Layer 1  Mock 传输层单测       秒级   本地/CI
Layer 2  仿真在环回归（数字孪生）分钟级 CI（含已知坑回归用例）
Layer 3  历史真机数据影子回放   分钟级 CI（离线，零物理风险）
Layer 4  真机安全冒烟检查      数秒   真机，无需相机
Layer 5  相机+遥测融合任务终审  分钟级 真机，唯一需要真实执行动作的一层
```

### Layer 0 — 静态与构建正确性
让硬件相关代码在没有真实机器狗、甚至没有真实 `unitree_sdk2py` 的情况下也能被 import、类型检查、做 skill schema 校验（`dimos/agents/annotation.py` 里已有的 docstring/类型注解强制规则就是这一层的一部分，但目前止步于此）。做法：在 `uv sync --group tests-self-hosted` 覆盖的自托管 CI 环境里装上真实/兼容的 `unitree_sdk2py`（而不是只装在 Orin 上），让 G1/Go2 相关 blueprint 至少能在 CI 里完成 build（`autoconnect(...).build()`）而不报 import 错误。这直接解决 `greeter_onboard_opus_dev.md` 里提到的"本地完全没法测硬件相关代码"的问题。

### Layer 1 — Mock 传输层的单元测试
对 `dds_sdk.py`、`webrtc.py` 这类硬件调用点做 mock（`docs/development/testing.md` 已经在推荐用 `mocker` fixture），把 FSM 状态守卫、里程计到站阈值、PGO 跳变防御这类纯逻辑抽出来做确定性单测，不依赖仿真物理引擎，跑得快、可以每次 commit 都跑。

### Layer 2 — 仿真在环回归（这是杠杆最大的一步）
把 Go2 已经跑通的模式（`dimos/e2e_tests/test_dimsim_*.py`，通过 LCM 订阅真实话题断言机器人状态）**移植到 G1**，关键要求是：仿真必须驱动**和真机完全相同的代码路径**（`effectors/high_level/dds_sdk.py`/`webrtc.py` 不做 shortcut mock），只是把 DDS/WebRTC 的另一端换成仿真机器人而不是真实机器人。`dimos/robot/unitree/g1/mujoco_sim.py` 已经有 camera_info/tf 发布等基础设施，可以在此基础上补齐 FSM 状态模拟、里程计噪声模拟。

最重要的是：把 `greeter_onboard_opus_dev.md` §7/§9.7 里列出的**已知真机坑**（手臂动作仅在 FSM 500/501/801 下生效、PGO 回环跳变导致到站判断被跳过）固化成这一层的回归测试用例。这些坑目前是"每次真机测试都可能重新踩一遍"的隐性知识，写成用例之后就再也不会回归。

### Layer 3 — 历史真机数据"影子回放"
每次真机运行（不管成功失败）都保留 DDS/里程计/视频的原始记录。新代码上线前，先离线跑一遍历史记录里的传感器流，比较这次的决策输出（要发的指令、要触发的阈值判断）和历史已知正确的输出是否一致。零物理风险，而且数据集随真机运行次数增加会越来越大，回归覆盖越来越强——这是一个随时间自我增强的护栏，恰好也是相机+遥测记录（Layer 5）产生的副产品。

### Layer 4 — 真机安全冒烟检查（不需要相机）
在真正执行任务动作之前，先跑几秒钟的低风险检查：进程是否起来、DDS 心跳是否正常、是否成功进入 Sport 平衡模式、skill 调用是否抛异常。这一层完全可以用遥测数据（不需要视觉）判定，成本极低、没有跌倒风险，能挡掉"代码根本没跑起来"这一大类问题——这类问题目前很可能就是 2/100 里大部分损耗的来源。

### Layer 5 — 相机 + 遥测融合的任务终审（原方案的位置，但重新设计）
到这一层，前面四层已经把构建、逻辑、时序契约、部署漂移类问题基本挡掉了，只剩下"仿真和静态分析覆盖不到的真实物理动力学/环境不确定性"，这恰好是相机方案真正擅长、也真正值得投入真机时间的场景。相比原方案（单摄像头 + 视觉模型判过/不过），建议：

- **裁判以遥测为主、相机为辅**：摔倒用 IMU 姿态角阈值判定，到位用里程计误差判定，动作幅度/关节轨迹用关节状态判定——这些是确定性、低噪声的信号。相机只用来判定遥测覆盖不到的部分（动作姿态是否符合预期、场景中是否有人、朝向是否正确）。
- **多机位 + 与遥测同时间戳**，失败时自动打包"视频片段 + 遥测日志 + DDS trace + 对应 git commit diff"成结构化证据，直接回传给 AI，取代目前"人工口头描述现象"这一步——这是整个闭环里信息损耗最大的环节，值得优先自动化。
- **显式止损条件**：跌倒检测、关节力矩异常立即急停；同一任务连续 N 次失败自动升级人工介入，而不是无限循环重试。
- **分级自治**：全新动作类别第一次上真机必须有人在场；已经验证过安全边界的动作类别，允许在无人值守下自动重试，但重试次数和总时长要有硬上限。

## 4. 为什么这样比"单一相机关卡"更快达到 98/100

粗略估计（基于上面对失败原因的分类，具体比例需要用真实失败日志校准，但方向是可靠的）：如果构建错误、纯逻辑错误、FSM/DDS 时序契约错误、部署漂移这四类问题被 Layer 0-4 拦截，那么真正"必须靠一次真实机器狗物理执行才能发现"的问题比例会从接近 100%（现状）降到一个小得多的尾部，而这部分恰好是相机+遥测终审最擅长判定、最该用真机时间去验证的部分。换句话说：**不是相机不该用，而是相机不该是唯一一道关；把它放在漏斗最后一层，才能让它的判定准确率对最终"98/100"这个目标产生实质贡献**——因为它面对的不再是"平均分布的各种性质的 bug"，而是收敛到"值得用视觉+遥测判断的物理执行问题"。

## 5. 落地建议（分阶段，非一次到位）

1. **阶段一**：在自托管 CI 环境装上 `unitree_sdk2py`（或等价 stub），让 G1/Go2 硬件相关代码至少能在 CI 里 import/build（对应 `.github/workflows/ci.yml` 的 `self-hosted-tests` job、`docs/development/testing.md`）。
2. **阶段二**：把 `dimos/e2e_tests/test_dimsim_*.py` 的模式移植到 G1，把 `greeter_onboard_opus_dev.md` §7/§9.7 的已知坑写成回归用例。
3. **阶段三**：把 `scripts/sync_g1_orin.sh` 的手工文件清单换成"以 git commit SHA 为版本号的可复现部署产物"（打包/镜像/整仓同步二选一），并把 FSM/Sport 模式前置检查自动化或至少做成清晰报错，而不是静默无动作。
4. **阶段四**：把 Layer 4 的真机安全冒烟检查接入 `ai_longrun_harness/run_pr_pipeline.sh` 这条自动化流水线，作为真机测试前的门禁。
5. **阶段五**：搭建相机 + 遥测融合终审系统，以及结构化证据自动回传给 AI 的机制——这是原方案里"外接相机"真正该上场、也最值得投入的一层。

## 6. 一句话总结

单独加一台相机只是把"人看着判断"换成"AI 看着判断"，但没有解决真机测试之前就已经损耗掉的大部分成功率；真正把 2/100 提到 98/100 需要一个分层验证漏斗——把构建、逻辑、时序契约、部署一致性问题都在真机之外挡住，只把"仿真覆盖不到的真实物理不确定性"留给相机+遥测融合终审去判定，并配合结构化证据回传和分级自治的安全机制，形成一个真正可审计、可安全停止的闭环。

# 真机验证闭环：为什么"加一个相机"不够，以及更好的方案

> 背景：当前 AI 写的机器人技能代码，在 DimSim 仿真里能跑、也能编译，但部署到真实宇树（Unitree）机器狗上大约只有 **2/100** 能正确运行。目标是在不牺牲安全性的前提下，把这个数字提到 **98/100** 左右，同时把"人蹲在场地里看机器狗、口头描述现象、AI 再改代码"这种低带宽、不可复现的调试方式，改造成自动化、可审计、可安全停止的闭环。
>
> 依据：仓库内现有代码与文档（`ai_longrun_harness/`、`dimos/e2e_tests/`、`dimos/core/coordination/watchdog_main.py`、`docs/development/testing.md` 等），不含未实现设想。

---

## 1. 结论先行

**"外部相机 + 视觉判定通过/失败"这个想法方向是对的，但只解决了闭环里最后、也是最便宜的一环——"人工肉眼判定"的自动化。它不能把成功率从 2% 顶到 98%，因为 2→98 的差距根本不在"谁来判定成功/失败"，而在于：**

1. 现在**每一次**尝试都是在真实硬件上从零开始验证的——中间没有任何更便宜、更快、能提前拦截 bug 的关卡。
2. 失败反馈是**一段视频/一句人话描述**，AI 拿到的是"结果"而不是"原因"，只能靠猜来改代码，猜错了又要再等一次真机尝试（成本以分钟计，还要人在场）。
3. 单次真机运行是**随机变量的一次采样**，机器狗行为本身有噪声（地面摩擦、电量、初始姿态、来自遥控/网络的抖动），拿"这次成功了"就判定"代码没问题"在统计上不成立。
4. 没有**安全熔断**：如果 AI 生成的代码有系统性问题（比如某个方向的速度指令超限、跌倒后没有保护性动作),连续在真机上重复失败可能损坏硬件或造成人员风险，而现在没有机制在第 N 次失败后自动停下来。

单加一个相机，相当于只是把"人观察 + 人转述"换成了"AI 观察 + AI 转述给自己"，反馈变快了、变客观了一点，但每一次迭代仍然要付真机试验的全价，出的问题仍然是黑盒，出问题的原因仍然靠猜。这大概能把吞吐量提高（不用等人），但准确率很难从 2% 提到两位数以上，更别说 98%。

真正要做的是把"仿真通过 → 直接上真机"这个只有两级的验证链路，改造成**多级、可观测、带统计置信度、有自动熔断**的验证流水线——工程上就是把"给机器人跑软件"当成"给分布式系统跑 CI"来做,只是最后一级的 CI runner 是一条真实的狗。

## 2. 现状诊断：这个仓库里实际缺什么

看代码里已经有的东西，可以看到骨架其实已经搭了一半：

| 已有能力 | 位置 | 局限 |
|---|---|---|
| 仿真端到端测试 | `dimos/e2e_tests/test_dimsim_walk_forward.py` 等，用 `DimSimClient` + LCM 回放判定 | 判定标准是**里程计位置**（`lcm_spy.wait_until_odom_position`），状态量而非视觉；仿真物理与真机有差距，通过了不代表真机能走 |
| MuJoCo 更高保真仿真 | `pytest` 标记 `mujoco` | 文档明确写着"这些测试很慢，目前在 CI 里跑不起来"（`docs/development/testing.md`）——这是几乎零成本就能补上的一级验证，但现在被跳过了 |
| AI 自动改代码 → 提 PR 流水线 | `ai_longrun_harness/run_to_main.sh` 调用 `run_multi_agent_loop.sh` → `run_pr_pipeline.sh` | `run_multi_agent_loop.sh` 在仓库里**没有实际文件**（脚本引用了但目录里不存在），说明"多智能体开发循环"这一环本身还没有落地实现，更谈不上带着真机反馈闭环 |
| 进程级看门狗 | `dimos/core/coordination/watchdog_main.py` | 只负责"主进程挂了就杀掉子进程"，是进程生命周期管理，**不是**物理安全熔断（比如连续摔倒/连续任务失败后停止继续下发真机指令） |
| 单元/集成测试分层 | `docs/development/testing.md`：`default` vs `self_hosted` | 分层思路是对的（快测试挡在前面），但这套分层目前止步于"能不能装依赖"，没有延伸到"能不能上真机" |

也就是说，仓库里已经有"仿真验证"和"AI 改代码提 PR"两段闭环的雏形，唯独缺**中间这一大段**：仿真通过之后、真正在真机上放开跑之前，没有任何分级把关；而"外部相机"方案想做的，其实是想直接把验证挪到链路的最末端（真机整任务跑完之后），这恰恰是最贵、最慢、风险最高的地方。

## 3. 更好的方案：分级、可观测、统计置信的真机验证阶梯

把整个链路拆成 5 个成熟度阶段,借鉴的思路和你贴的那张"AI 应用成熟度阶梯"一致——**每一级要解决的是上一级暴露出的新瓶颈,而不是简单堆更多同类能力**。

| 阶段 | 名称 | 长什么样 | 当前瓶颈 | 关键组件（落到本仓库） | 护栏 |
|---|---|---|---|---|---|
| **0** | 人工肉眼判定（现状） | 人蹲场地看狗、口头描述给 AI | 反馈慢、主观、不可复现、人是唯一带宽 | 无 | 人在场，天然的安全兜底 |
| **1** | 单相机自动判定（你提的方案） | 外部相机 + 视觉模型给 pass/fail，喂给 AI | 只自动化了"判定"，没有根因信息；每次迭代仍是真机全价试验；无统计置信度；无自动熔断 | 一路相机 + 简单动作分类器 | 只有"看起来不对就停"，缺系统性熔断 |
| **2** | 多模态硬件在环记录 | 相机 + LCM 总线全量日志（关节电流/位置、IMU、足底接触、电量、指令流）按时间戳对齐，形成"黑匣子"记录；失败时自动生成**结构化**诊断（不是一段视频，而是"t=3.2s 关节 hip_L 电流饱和""t=5.1s 之后 60 次循环未收到 /cmd_vel"这类结论） | 把"哪里错了"从人工看视频猜,变成程序化归因,AI 拿到的是缩小后的定位而不是原始素材 | 新增 `HardwareTrialRecorder`：复用 `dim_sim_client.py`/`lcm_spy.py` 里已有的 LCM 订阅/回放模式,把订阅对象换成真机话题,外接相机流用时间戳对齐写入同一 trial 目录 | 记录本身不做决策,只是给下一级提供弹药 |
| **3** | 分级验证流水线（真正拦住大部分 bug 的地方） | 上真机前先过三关：① 现有 `dimsim`/`mujoco` 仿真测试（先把 `mujoco` 标记的测试接回 CI,这是当前唯一"写了但没跑"的免费仿真层）；② **日志回放**——把之前真机采集的传感器日志喂给新代码,不驱动电机,只检查下发的指令是否落在安全/合理范围内；③ **受限真机冒烟测试**——吊架/小范围场地、低速、只测试单一动作原语,而不是完整任务 | 现在只有"仿真"和"真机整任务"两级,中间空的这一段才是能以接近零成本拦掉大多数代码级 bug 的地方 | ① 修 CI 里的 `mujoco` 跳过问题；② 新增回放校验脚本,复用现有日志格式；③ 扩展 `ai_longrun_harness` 增加一个"冒烟测试"阶段,复用 `run_pr_pipeline.sh` 的分阶段脚本风格 | 每一关失败都直接挡住,不消耗真机整任务尝试的名额 |
| **4** | 统计置信 + 自动熔断 + 持续回归 | 通过前三关的代码,在真机上跑 N 次（比如 20~30 次,可以在无人值守时段批量跑,因为有相机+全量遥测,不需要人盯着）,统计成功率和置信区间；只有达到设定阈值（如 ≥95% @ N≥20）才允许合并；合并后仍纳入"夜间回归"定期重跑,因为真实世界会漂移（电量、地面、机械磨损）；连续失败或触发硬件安全信号（跌倒、急停、电流异常）自动中止后续真机尝试,需要人工复核才能继续 | 单次成功不能代表 98% 的可靠性——统计意义上必须多次采样；同时要防止"坏代码在无人值守时反复摔机器狗" | 合并门禁脚本（风格类似 `run_pr_pipeline.sh`,但改为"验证通过率达标才允许 push/PR"）；把 `watchdog_main.py` 的模式从"进程看门狗"扩展出一个"物理安全看门狗"——订阅遥测里的跌倒/急停/异常电流信号,达到失败计数阈值就切断继续下发指令的权限 | 这是唯一能把"人不用在场"和"不会把机器狗跑坏/跑失控"同时满足的机制 |

**关键判断**：2→98 这个跨度,主要工作量在**第 3 级**（分级拦截,把 90% 以上的 bug 挡在真机之前）和**第 4 级**（统计置信,把"一次成功"变成"可信赖的成功率"）,而不是第 1 级的相机本身。相机/多模态记录（第 1、2 级）是必要的**可观测性基础设施**,但如果没有第 3 级的分级拦截,相机只是让你更快地看到同一批 bug 反复失败;如果没有第 4 级的统计门禁和熔断,你会得到一个"看起来能跑但实际成功率没人验证过"的合并结果,以及一只可能被反复摔坏的机器狗。

## 4. 落到这个仓库的具体步骤（按性价比排序）

1. **先把免费的仿真层用起来**：修复 `mujoco` 标记测试在 CI 里跑不了的问题（`docs/development/testing.md` 里明确写了这个已知缺口）。这是零硬件成本、能拦住大量物理层 bug 的一步,应该排第一。
2. **把 `ai_longrun_harness/run_multi_agent_loop.sh` 补全**：目前 `run_to_main.sh` 引用了这个脚本但它不存在,是当前"AI 改代码"闭环里缺失的一环,需要先有它,后面的硬件反馈才有地方接入。
3. **新增 `HardwareTrialRecorder`**：仿照 `dimos/e2e_tests/lcm_spy.py`、`dim_sim_client.py` 的模式,把真机的 LCM 话题（关节状态、IMU、指令流）和外部相机帧按时间戳对齐落盘,每次真机尝试生成一个带 trial ID 的记录目录,而不是一段孤立视频。
4. **在真机记录基础上加结构化失败分类器**：不是"人/AI 看视频判断像不像成功",而是先用遥测数据做规则/模型化的根因归类（超时未收到指令、关节饱和、跌倒、路径规划无解等）,视觉判定只作为"任务级目标是否达成"的最终一环,两者互补而不是相机独扛全部判定职责。
5. **新增受限真机冒烟测试阶段**,插在"仿真通过"和"完整任务真机测试"之间,复用 `run_pr_pipeline.sh` 的分阶段脚本风格。
6. **加统计门禁**：合并前要求 N 次真机 trial 的成功率与置信区间达标,而不是一次通过就算数;合并后加入夜间回归重跑。
7. **把 `watchdog_main.py` 的模式扩展成物理安全熔断**：现在这个看门狗只管进程生命周期,需要新增一层订阅硬件安全信号（跌倒/急停/异常电流/连续失败计数)、达到阈值就阻止继续下发真机指令,这样才能真正做到"无人值守也敢跑"。

---

## 5. 为什么这样能到 98/100,而不是停在 20/100

如果只做"加一个相机做闭环",瓶颈从"人工判定慢"变成"每次迭代仍要真机全价试验 + 只有结果没有原因 + 没有统计置信度 + 没有熔断",大概能把吞吐量提上去（不用等人),但单次真机尝试的信息密度和安全边界没变,预期成功率提升有限,而且存在把机器狗跑坏的风险。

而分级流水线 + 结构化遥测 + 统计门禁 + 安全熔断的组合,是从三个独立维度同时发力：
- **在真机之前拦截大部分 bug**（第 3 级）——每次真到真机的代码,底子已经好得多；
- **每次真机失败给出可定位的原因**（第 2 级）——AI 每次迭代的信息量远大于"一段视频",收敛所需的真机尝试次数会显著下降；
- **用统计而不是单次结果定义"合格"**（第 4 级）——保证"98/100"是一个被验证过的数字,而不是"最近一次跑成功了"。

这三者叠加,才是能把成功率从个位数拉到 98% 这个量级的路径;单独的相机闭环最多是这套体系里的一个组件（第 1~2 级的输入源之一）,不是终点方案。

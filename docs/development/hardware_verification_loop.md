# 真机验证闭环：从"外部相机判分"到分层验证漏斗

> 背景：当前协作方式是 AI 写代码 → 人把代码部署到 Unitree 机器狗上 → 人观察现象、口头描述 → AI 继续改。
> 即使代码能编译、能过仿真，真机成功率也很低（当前约 2/100）。
> 本文档分析"加一台独立相机自动判断动作是否完成"这个方案本身的局限，并给出一个更完整的方案，
> 目标是把"AI 写的功能第一次上真机就能跑对"的比例从 2/100 提升到 98/100 量级。

## 1. 现有方案："外部相机 + 通过/不通过"

一句话定义（原方案）：用外部相机做独立的物理世界观察者，把"AI 写代码 → 真机运行 → 视觉验收 → 失败反馈 → 继续修改"连接成闭环，达标则合并，不达标则把证据交给 AI 继续改。

这个方向是对的——用机器代替人眼观察是自动化闭环的必要条件。但只做这一件事，解决的只是"谁来看"的问题，没有解决"为什么真机成功率只有 2%"背后的根本瓶颈。下面逐条分析。

## 2. 为什么"只加一台相机"不够

### 2.1 相机只给结论，不给病因

相机能回答"这次跳跃动作做完了没有"，回答不了"为什么没做完"。对照代码现状：

- `dimos/robot/unitree/unitree_skill_container.py` 里 `execute_sport_command`（覆盖 jump/flip/dance 等技能）是纯粹的"发指令就返回成功"——不读关节状态、不读 IMU、不确认物理上是否真的执行了。只有 `relative_move` 一个技能会轮询 `NavigationState` 并区分 timeout/cancelled/reached。
- 也就是说，在相机介入之前，技能本身就没有一个可核对的、量化的"完成"定义。相机拍到"狗摔倒了"，AI 收到的信息和人工口述"狗摔倒了"在信息量上几乎没有差别——闭环自动化了，但没有变得更聪明，调试速度不会因此显著提升。

**结论**：单一相机判分只是把"人观察"换成"机器观察"，观察的对象和信息颗粒度没变，仍然是"黑盒试错"，不是"可定位故障"。

### 2.2 单次试验不足以下结论

当前基线成功率约 2/100，说明系统本身噪声很大（电量、WiFi 时延、地面摩擦、Unitree 自带避障/安全策略随时可能接管 `cmd_vel`——`docs/development/orbit_object.md` 第 10 节已经记录过这类真机限制）。在这种噪声水平下：

- 一次真机试验"通过"不能证明改动是对的，可能只是蒙对了；
- 一次真机试验"失败"也不能证明改动是错的，可能是环境噪声。

只用单次相机判分做合并门槛，本质上是在高方差信号上做零样本决策，这也是当前 2/100 反馈本身可能都不完全可信的原因之一。

### 2.3 没有仿真前置过滤——大量本可以零成本拦截的 bug 被留到了真机上

仓库里其实已经有一套接近你想要的东西：`dimos/e2e_tests/`（`test_dimsim_walk_forward.py` 等）基于 `dimsim` 场景仿真器，会真的注入自然语言指令、跑完整 agentic blueprint、断言里程计结果——这正是"闭环验收"该有的形态，而且完全不需要真机。

但现状是 `.github/workflows/ci.yml` 里默认矩阵和 self-hosted 任务都用 `-m 'not (tool or self_hosted or mujoco or dimsim)'` 把 `dimsim` 标记的测试排除在外，也就是说**这套仿真验收从来没有在 CI 里自动跑过**。同样，`mujoco` 标记的物理仿真测试也被排除。

**结论**：在讨论"真机成功率"之前，应该先问"有多少失败其实在仿真里就能复现、根本不该浪费一次真机试验"。当前答案基本是"不知道，因为仿真闭环没接进流水线"。

### 2.4 `ai_longrun_harness` 名不副实，没有可复用的"多次试验"基础设施

这个目录名字听起来像"长时间/多次运行的测试脚手架"，实际内容只有三个文件，功能是 git push + `gh pr create` 的自动化包装，`run_to_main.sh` 甚至引用了一个不存在的 `run_multi_agent_loop.sh`。没有仿真、没有真机、没有重复试验、没有统计逻辑。**它不能作为"重复试验+统计判定"的基础，需要新建。**

### 2.5 没有安全/成本节流

"失败就继续改、改完就再上真机试"这个循环如果完全自动化且没有护栏，意味着：AI 可能在同一个假设上连续烧真机时间、电量、甚至因为同一个 bug 反复摔狗。原方案提到了"安全/失败停止条件"，但没有具体定义节流规则（连续失败几次自动暂停？谁来收到告警？）。

### 2.6 相机/视觉判官本身的可信度没有校准

如果最终是用视觉模型（哪怕只是简单的姿态/位置识别）来判断"动作是否完成"，这个判官本身也会犯错（遮挡、光照、视角）。原方案把它当作"独立且正确"的裁判直接用于合并门禁，但没有先验证它和人类判断的一致率。一个会犯错的自动裁判，如果被无条件信任，反而会让"合并标准"变得比人工判断更不可靠。

## 3. 更好的方案：分层验证漏斗 + 结构化失败证据链

核心思路：相机只是漏斗最顶端（最贵、最慢、真机相关）的一层；大多数迭代应该发生在更便宜、更快、不需要真机的层。每一层失败都要产出**结构化证据**，而不是一句"没通过"。

| 层级 | 内容 | 成本/耗时 | 是否碰真机 | 作用 |
|---|---|---|---|---|
| L0 静态/单测 | lint、mypy、现有单元测试（已有 CI） | 秒级 | 否 | 拦住纯代码 bug |
| L1 仿真回归门禁 | 把 `dimsim`（导航/场景类）+ `mujoco`（接触力学类，如跳跃/翻滚）测试接入 CI，作为技能改动的强制门禁 | 分钟级 | 否 | 拦住"编译通过但逻辑错"的问题，这是当前最大的漏洞 |
| L2 技能验收规范 | 给每个 `@skill`（如 `move`、`jump`、`follow_object`）定义结构化 `AcceptanceCriteria`：目标位姿容差、时长范围、必达终态、禁止事件（故障码、急停、避障接管） | 设计一次，长期复用 | 否 | 让"成功"从代码里的一句 `return "success"` 变成可核对的量化条件；仿真断言和真机验收使用同一份规范，消除语义不一致 |
| L3 受限真机冒烟测试 | 拴绳/软垫/限速的低风险试跑，只查"会不会摔/会不会失控/通信是否正常" | 真机，但风险小 | 是（受限） | 在放开自由试跑前先排除硬件层面的明显问题 |
| L4 多模态真机正式试验 | 外部相机（建议 ≥2 机位防遮挡）+ 与视频**时间对齐**的机载遥测（关节状态、IMU、电量、WiFi RTT、指令日志、故障码、cmd_vel vs 实际速度）打包成一份"黑匣子记录" | 真机 | 是 | 这才是"相机"该在的位置——作为多路证据之一，而不是唯一信号 |
| L5 统计合并门禁 | 不是"跑通一次就合并"，而是维护每个技能的历史试验记录，用 Wilson/Clopper-Pearson 区间之类的方法定义"至少 N 次里 M 次成功"才算达标，新技能要求更多次确认，历史稳定的技能可以降低确认次数 | 无额外真机成本，靠积累 | — | 把"看起来能用"变成"有统计意义地能用"，这是从 2/100 走向 98/100 的关键闸门 |
| L6 视觉判官校准 | 用一批人工标注过 pass/fail 的真机录像，测视觉判官和人的一致率，达到设定阈值（如 ≥99%）才允许它自动把关，之后仍按比例抽样人工复核 | 一次性 + 持续抽检 | — | 避免"自动裁判本身会犯错"被忽视 |
| L7 结构化失败回传 | 把 L1-L6 里任何一层失败，都整理成"哪一层失败 + 期望 vs 实测 + 关键时间窗视频片段 + 遥测曲线"回传给 AI，而不是一句话描述 | — | — | AI 拿到的是可定位的诊断包，而不是"没做到"三个字；修完之后从对应层级重新验证，通常先回 L1 而不是直接再上真机 |
| L8 安全/节流停止条件 | 连续真机失败达到阈值（如 3 次）自动暂停并通知人；跌倒/故障码触发立即急停；每日真机试验时长预算上限 | — | — | 防止在同一个错误假设上反复消耗真机和电量，也是原方案里提到但没有具体化的"安全停止条件" |

## 4. 与 "Steps of AI Adoption" 的对应关系

这次一并收到的 Boris Cherny《Steps of AI Adoption》讲的是纯软件场景下 agent 自主程度的成熟度台阶，其中 Step 1→2 的关键解锁条件是：

> "a self-verification loop you trust (tests + build + lint + e2e testing with a real dev environment)"

现在的真机调试流程本质上停留在软件世界的 **Step 1（Assisted）**：一人一 agent，同步盯着，每次改动都要人全程盯着看结果——只是把"看代码 diff"换成了"看机器狗有没有摔"。单纯加一台相机，只是把"人眼验证"换成"相机验证"，循环结构没变，依然是同步、单次、低信任度，本质上还是 Step 1，只是观察者换了。

要真正往 Step 2（Parallel，"Claude checks its own work before you see it"）甚至 Step 3（Supervised autonomy）走，解锁条件是上面 L0-L2（仿真门禁 + 量化验收规范）加上 L5-L6（统计门禁 + 判官校准）——这一组合就是机器人版的"你信得过的自验证闭环"。有了它，人不需要盯着每一次真机试跑，只需要在 L8 的安全阈值触发时才被叫回来，这才是"闭环、可审计、可安全停止"真正应该长成的样子。

## 5. 路线图：从 2/100 到 98/100

| 阶段 | 动作 | 直接依据 |
|---|---|---|
| Phase 1 | 把 `dimsim`（和条件允许下的 `mujoco`）测试接入 CI 作为强制门禁；给 `move`/`jump`/`follow_object` 等高频技能补上 `AcceptanceCriteria` 和真实的遥测回读（替换掉 `execute_sport_command` 的"发了就算成功"） | 2.3、2.1 节发现：仿真闭环已存在但未接入 CI；技能验收标准缺失 |
| Phase 2 | 建"真机运行记录器"：相机 + 遥测同步打包成黑匣子文件；先跑 L3 受限冒烟测试再放开 L4 正式试验 | 2.5 节：目前没有安全节流的中间层 |
| Phase 3 | 用人工标注的历史录像校准视觉判官，建立 Wilson 区间的多次试验统计门禁，只有过了统计门禁才允许合并 | 2.2、2.6 节：单次判分不可靠、判官本身未校准 |
| Phase 4 | 上线 L7 结构化失败回传 + L8 安全停止条件（连续失败自动暂停、故障码急停、每日真机预算） | 2.5 节 + 原方案里"安全/失败停止条件"尚未具体化 |

Phase 1 是性价比最高的第一步：`dimsim` 端到端测试和 `AcceptanceCriteria` 所需的技能容器代码都已经存在，只是没有被强制执行或没有量化标准，属于"补齐现有基础设施的开关"，不需要新造轮子，也不涉及真机风险。

## 6. 关键结论

1. 相机是必要的，但只是漏斗顶端最贵的一层，不应该独立作为唯一的验收信号。
2. 当前 2/100 的真机成功率，很大一部分原因可能是仿真闭环（`dimsim`/`mujoco`）建了却没接入 CI，导致本该在仿真里零成本拦下的 bug 被留到了真机上——这是投入产出比最高的修复点。
3. 从"能跑一次"到"98/100 稳定可信"，需要的不是更好的相机，而是量化的验收规范（L2）+ 多次试验的统计门禁（L5）+ 判官校准（L6），这三者共同决定了"通过"这个词到底有多可信。
4. 失败反馈的价值取决于信息颗粒度：结构化的"哪一层失败 + 期望 vs 实测 + 同步视频/遥测片段"比"相机说没做到"更能让 AI 定位问题、减少无效的真机往返。

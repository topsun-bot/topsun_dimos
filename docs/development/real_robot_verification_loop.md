# 真机验收闭环：从「2/100」到「98/100」的方案设计

> 背景：当前工作方式是 AI 写代码 → 人把代码部署到宇树机器狗上 → 人肉眼观察、口头描述失败现象 → AI 继续改。曾提出的改进方案是「在场地外加一台独立相机，自动判断动作是否完成，达标则可合并，不达标则把证据交给 AI 继续修」。本篇分析这个方案本身的不足，并给出一个更完整的架构，目标是把「AI 写的功能第一次上真机就能正确运行」的比例从约 2% 提升到 98% 量级。
>
> 结论先放在最前面：**外部相机能解决「谁来验收」，解决不了「样本效率」和「为什么失败」**。只加一个相机，闭环确实能转起来，但每一圈都要占用一次宝贵、有风险、分钟级的真机资源，且相机只给「过/不过」一个 bit，AI 拿不到失败根因，只能盲猜着改，收敛速度不会有质变。要把命中率提到 98%，需要的是一个**分层漏斗**：把绝大多数问题在真机之前的低成本环节里过滤掉，等真正上真机时，验收信号是结构化、可量化、可归因的，而不是一段视频。

## 1. 现状诊断：这个仓库里能看到的证据

在给方案打分之前，先说明诊断是基于代码库里的真实现状，不是泛泛而谈：

1. **仿真层的端到端测试已经存在，但从未在任何自动化流水线里跑过。** `dimos/e2e_tests/` 下有 `test_patrol_and_follow.py`、`test_person_follow.py`、`test_scan_and_follow_person.py` 等基于 MuJoCo + `DimSimClient` 的场景化测试，用 `lcm_spy` 订阅真实话题、用 `human_input()` 模拟自然语言指令。但 `.github/workflows/ci.yml` 里两处 pytest 调用都显式排除了 `mujoco`/`dimsim` marker（`-m 'not (tool or self_hosted or mujoco or dimsim)'`），`pyproject.toml` 的默认 `addopts` 同样排除。也就是说，**这批本可以在真机之前捕获大量问题的仿真测试，目前只能由工程师手动跑，等于没有跑**。这是当前「首发命中率 2%」里最容易补的一块——很多真机上才暴露的失败，其实在仿真里就能复现。

2. **视觉验收的雏形已经做过一次，但范围很窄、且是「自证」模式。** commit `569047b`（`feat(nav): visual re-verify flow with VLM presence check`）给 `navigation` skill 加了 `verify_object_in_view()`：让机器人自己转头、用机载相机 + VLM 问「看到了吗」来确认导航到位。这证明团队已经认识到「AI 说完成了不代表真完成」，但这套机制有两个局限，恰好是外部相机方案要解决又没解决的：
   - **自证问题**：验收传感器（机载相机）和被验收的系统（机器人自身控制/定位）绑在一起，如果定位本身错了，机载相机看到的「视角」也是错的，容易系统性地自己骗自己。这正是为什么需要**独立于机器人之外**的观察者——但独立相机只解决了「谁来看」，没解决「看到了不算数的时候，下一步该看哪」。
   - **只对单个 skill（导航找物体）生效**，没有抽象成通用的「验收标准即代码」框架，其他动作（走姿态、避障、follow、上下台阶等）没有对应的可编程验收逻辑。

3. **已经有可复用的精确视觉测量能力，但没有接到「验收」这条线上。** `dimos/perception/fiducial/`（`fixture_verification.py`、`marker_tf_module.py`）实现了 AprilTag 板的检测与几何校验，`dimos/robot/unitree/params/front_camera_720.yaml` 等有相机标定参数。这意味着「外部相机」不需要止步于「拍视频给人看」或「拍视频给 VLM 判断像不像」，而是可以直接**用 AprilTag/fiducial 做厘米级、可量化的位姿测量**——这是把验收从「主观判断」升级为「数值指标」的现成积木，目前没人把它接到真机测试流程上。

4. **「AI 写代码 → 自动跑测试 → 自动提 PR」的骨架已经搭了一半，但断在半路。** `ai_longrun_harness/run_to_main.sh` 会依次调用 `run_multi_agent_loop.sh` 和 `run_pr_pipeline.sh`，但仓库里**没有 `run_multi_agent_loop.sh` 这个文件**——`ai_longrun_harness/` 目录实际只有 `run_pr_pipeline.sh`、`run_to_main.sh`、`config.env.example` 三个文件。也就是说现有的"自动化闭环"脚手架，链路中间是断的，且完全没有涉及"部署到真机 / 采集证据 / 判定通过"这几步。这是本方案要补的位置，而不是另起炉灶。

5. **真机部署目前是人工 SSH + rsync。** `scripts/sync_g1_orin.sh`、`scripts/orin_dimos.sh`、`scripts/orin_run_nav.sh` 等脚本把改动同步到 Orin 板载电脑并手动启动，日志靠 `dimos log -f` 人工盯屏幕。这意味着即使加了相机，"部署 → 触发动作 → 采证据 → 回传给 AI"这一段目前也没有自动化，还是要人守在旁边。

综上，"加一台外部相机做验收"这个思路本身没错（独立观察者是对的方向），但它只解决了诊断出的 5 个问题里的第 3 点的一半（"有没有可量化的测量手段"），没有触及 1、2、4、5——而这几点合起来才是命中率上不去的主因。

## 2. 为什么「只加一台相机」不足以把 2% 提到 98%

把方案拆开看，能看出它隐含了几个不成立的假设：

| 隐含假设 | 现实 |
|---|---|
| 每次迭代都应该直接上真机验证 | 真机是最贵、最慢、最有风险的验证环节，应该是漏斗的**最后一级**，不是唯一一级。100 次改动次次上真机，样本效率天然低，98% 的目标在这个前提下几乎不可能靠"多试几次"达成 |
| 相机看到「没做到」这个结果，AI 就能诊断出「为什么没做到」 | 结果信号不等于原因信号。同样是"机器狗没走到目标点"，可能是控制增益问题、WebRTC 时延导致指令丢失、地图漂移、绊到台阶、还是触发了内部限幅——只给 pass/fail，AI 只能靠猜，等价于给一个没有堆栈信息的 crash 报告去 debug |
| 一台相机 + 单一判定，就能覆盖各种动作的"完成"定义 | "完成"对不同动作含义完全不同（到达某坐标 vs. 姿态稳定 vs. 抓取成功 vs. 语音应答），如果验收标准不能以代码/配置形式声明，就还是要靠人或 VLM 做主观判断，标准漂移、不可复现的问题并没有解决 |
| 失败之后，"继续修改、部署、测试"可以无限循环 | 没有提到停止条件和安全护栏。真机上无监督地反复试跑失败动作，存在摔倒、撞人、撞坏机器本体和硬件的风险，尤其步态类、接触类动作 |
| 通过/不通过是终点 | 没有提到"通过的证据要不要沉淀"。如果每次真机验证完就把视频丢掉，下次类似的改动还是要重新试一遍真机，样本效率永远上不去 |

一句话总结：**外部相机是漏斗最末端一个环节的正确升级，但被误用成了整个闭环。**

## 3. 更完整的架构：分层验证漏斗 + 结构化验收 + 根因分类

目标不是设计一个"更好的相机方案"，而是设计一个**让绝大多数候选改动在到达相机之前就被淘汰或修好**的系统，让真机 + 相机这一级只需要处理"看起来已经很可能对"的代码，同时在它判定失败时给出**可操作**的诊断信息。

### 3.0 总览

```
Stage 0  静态检查        lint / type check / 单测          秒级反馈，仓库里已有（CI）
Stage 1  仿真回归        MuJoCo/DimSim 场景化 e2e          分钟级，仓库里已有代码，只是没接进流水线
Stage 2  历史回放回归    真实遥测/视频录像的离线重放        分钟级，需要新建"证据库"
Stage 3  受限真机预检    绳保护/限速/围栏内做首次真机验证    需要人值守，但风险和时间成本最小化
Stage 4  开放场地真机验收 多相机 + AprilTag + 机载遥测融合判定 唯一真正"判成绩"的一级
```

每一级只有通过才进入下一级；任何一级失败，都要把**带时间戳、可对齐的多路证据**（不只是判定结果）连同结构化根因标签一起交回给 AI，作为下一次修改的输入，同时归档进 Stage 2 的回放库，避免同一个坑真机上摔第二次。

### 3.1 Stage 1：把已经写好的仿真 e2e 测试真正接入自动化

这是投入产出比最高、且成本几乎为零的一步——代码已经在仓库里了（`dimos/e2e_tests/*.py`），只是被 CI 显式排除。具体动作：

- 新增一条 nightly / on-demand 的 CI job（或者 `ai_longrun_harness` 里的一个 stage），专门跑 `-m mujoco or dimsim` 的用例，不再要求它们挤进主 CI 的秒级反馈里，但要求它们在合并前至少跑过一次。
- 把 AI 每次改动都先在这一层批量跑（可以并行开多个无头 MuJoCo 实例），凡是在仿真里就摔倒/卡死/达不到目标的，直接打回，**不占用真机名额**。
- 这一层能捕获的问题类型：逻辑错误、状态机死锁、坐标系搞反、参数越界、skill 调用顺序错误——这些恰恰是"代码能编译、能过单测，但真机跑不起来"里的相当一部分（另一部分是仿真覆盖不到的真实物理/硬件问题，见 3.3/3.4）。

### 3.2 Stage 2：把每一次真机验证都变成可复用资产（回放回归库）

现状是每次真机测试产生的视频和日志基本是一次性的——通过了就过了，没过就靠人转述几句话给 AI。这里的改进是把它变成沉淀资产：

- 每次 Stage 3/4 的真机运行，全量记录：机载 LCM/日志录像（repo 已有 LCM 录制能力）、外部相机视频、AprilTag 位姿轨迹、时间戳对齐后的一份"事件时间线"。
- 建一个轻量"回放库"：把历史真实场景（尤其是**曾经失败过**的场景）保存下来，之后新代码先在这些录制数据上做**离线重放校验**（例如：新的路径规划逻辑喂入历史里那次导致机器人卡在门框的传感器数据流，看新逻辑是否还会做出同样的错误决策）。这类似自动驾驶行业"回放真实路测数据做回归"的做法，不需要每次都重新占用真机。
- 效果：真正会重复出现的坑，只需要在真机上"交一次学费"，后续同类改动可以在 Stage 2 免费验证，这是从 2% 爬到两位数的第二个主要杠杆。

### 3.3 Stage 3：受限真机预检（绳保护 / 限速 / 围栏）

在开放场地全速测试之前，加一级低风险、低成本的真机验证：

- 室内小范围、挂保护绳或垫子、限速模式下，先跑一遍目标动作，只关注"会不会摔、会不会撞、指令能不能正常下发执行"这类高风险失败模式。
- 这一级仍然可以用同一套外部相机 + AprilTag，只是场地小、风险低，可以更激进地自动重试，不需要每次都升级给人。
- 通过 Stage 3 之后才允许进入开放场地全速测试，避免把明显有摔倒风险的候选代码直接放到 98% 验收要打分的正式场地里。

### 3.4 Stage 4：开放场地真机验收——多信号融合，而不是单相机单判定

这是原方案里"独立相机"的位置，但做几处关键强化：

1. **相机不止一台，且优先用可量化标记而不是纯粌像判断。** 复用仓库已有的 `dimos/perception/fiducial`（AprilTag 检测 + 几何校验）在场地里布置基准标记板，外部相机通过标定（已有 `front_camera_720.yaml` 之类的先例）直接解算机器人本体的位置、朝向、速度轨迹，输出的是**数值**（位置误差、姿态误差、完成用时、路径长度），不是"看起来像不像完成了"。需要主观判定的动作（比如"挥手动作是否自然"）才用 VLM 辅助，且 VLM 只作为**辅助信号**、不作为唯一裁判，避免把 3.1 节里提到的"自证"问题换个地方重演一遍。
2. **验收标准形式化为「任务规格」（TaskSpec / Acceptance-as-Code）。** 每个待验证的动作对应一份可读的判定逻辑，例如：
   ```yaml
   task: walk_to_point
   success:
     position_error_m: {max: 0.3}
     heading_error_deg: {max: 15}
     time_budget_s: {max: 10}
     max_roll_pitch_deg: {max: 25}      # 超过判定为接近跌倒
     estop_triggered: {equals: false}
     collision_detected: {equals: false}
   ```
   这样"完成没完成"不再依赖人或 VLM 的主观印象，而是外部相机测量值 + 机载遥测（IMU、关节力矩、急停状态、WebRTC 丢包率）联合判定的一次确定性计算，天然可复现、可审计、可回归（这份 YAML 本身也能喂给 Stage 2 的离线回放）。
3. **失败时输出结构化根因分类，而不是一个"没通过"。** 用一个规则/小模型对"外部相机轨迹 + 机载日志 + TaskSpec 里具体哪一项超标"做归类，例如：
   - `control_gain`（轨迹震荡但方向正确）
   - `perception_misjudge`（机载定位与外部真值系统性偏差）
   - `network_latency`（WebRTC 时延/丢包与指令执行的时间戳对不上）
   - `mechanical_limit`（关节力矩/限位触发）
   - `terrain`（外部相机可见明显地形障碍）
   - `safety_estop`（安全停止触发）
   这一步是把"2/100 → 98/100"里**质变**的那个杠杆：AI 拿到的不再是"再试一次"，而是"这次失败属于 control_gain 类，历史上这类问题改哪几个参数/哪几行代码有效"，诊断-修复的迭代效率会有数量级的提升，而不是线性提升。

### 3.5 安全停止条件（贯穿 Stage 3/4，必须先于自动化上线）

- **物理层**：受限测试阶段用保护绳/限速模式；开放场地用相机+围栏标记做电子围栏，越界立即降级为人工接管。
- **单次失败**触发即时停止该次尝试（跌倒姿态、力矩超限、越界、估计位置与视觉真值差过大导致失控风险）。
- **连续失败**（例如同一 TaskSpec 连续 N 次不通过，或出现新的、历史未见过的根因类别）自动暂停整条自动化链路，升级给人复核，而不是无限重试——这是对"直到满足任务要求或触发安全/失败停止条件"这句话里"失败停止条件"的具体化，原方案里没有把这条写实。

## 4. 如何接进现有代码库（具体落点）

不需要另起一套系统，建议的接入点：

1. **`ai_longrun_harness/`**：把现在缺失的 `run_multi_agent_loop.sh` 补上，并在 `run_to_main.sh` 的 `run_pr_pipeline.sh`（提 PR）之前插入两个新 stage 脚本：`run_sim_gate.sh`（对应 3.1，跑 mujoco/dimsim 标记的用例）、`run_replay_gate.sh`（对应 3.2，跑离线回放回归）。真机 Stage 3/4 作为单独的、非阻塞 PR 合并的"nightly 真机验收"流程（真机资源稀缺，不适合卡在每个 PR 的临界路径上；用 3.1/3.2 两级过滤后，真机只处理高置信度的候选）。
2. **`dimos/perception/fiducial/`**：`fixture_verification.py`、`marker_tf_module.py` 直接复用为外部相机的位姿测量后端，不用重新造 AprilTag pipeline。
3. **`dimos/navigation/visual/query.py` 的 `vlm_object_present_in_view()` 模式**：把它从"某个 skill 私有的机载验证"抽象成通用的 `TaskSpec` 判定器接口，允许每类动作插入自己的判定逻辑（数值型用 fiducial，主观型用 VLM），供 Stage 3/4 复用。
4. **`.github/workflows/ci.yml`**：新增一个不阻塞主 CI、定期触发的 job，专门跑当前被排除的 `mujoco`/`dimsim` 标记用例（对应 3.1）。
5. **`scripts/orin_*.sh`**：在部署脚本里加自动化的"部署 → 触发指定 skill → 开始录制机载日志"钩子，为 Stage 3/4 提供机载侧证据采集的自动化，替代现在"人工 SSH 盯屏幕"的方式。

## 5. 和 AI 应用成熟度模型的对照

对照文中贴的 Boris Cherny《Steps of AI Adoption》：文档明确指出从 Step 1（Assisted，一人一 agent，靠人逐条 review）迈向 Step 2（Parallel）的关键解锁条件是"a self-verification loop you trust (tests + build + lint + e2e testing with a real dev environment)"。当前团队在纯软件层面可能已经具备这个 loop（CI、lint、单测），但**在"物理世界"这一维上完全没有**——每次真机验证都要靠人守在场地边看、描述现象，这正是文档里 Step 1 "your attention... you sit and watch while Claude works" 的具体体现，只不过发生在机器人身上而不是屏幕上。

外部相机方案的价值判断可以重新表述为：它是在尝试给"物理世界"补一个 Step 1→2 所需的 self-verification loop，方向正确，但如果只做"相机 + pass/fail"，这个 loop 是"你信不过"的（噪声大、无归因、无法离线回归），达不到文档里"a self-verification loop you trust"的门槛，团队还是会因为不信任而继续人工介入，闭环转不快。3.1-3.4 提出的分层漏斗 + TaskSpec + 根因分类，本质上是把"物理验证"做到能达到软件 CI 同等级别的确定性、可回归、可解释性，这样才谈得上信任，也才谈得上把当前"人天天守在场地"的 Step ~1 workflow 升级为"批量真机验收跑夜间批次、人只看例外报告"的 Step 2/3 workflow。

## 6. 落地节奏建议（不是一步到 98%）

不建议把"98/100"当成单一相机系统要直接达成的指标，而是按漏斗分阶段设定中间目标，每个阶段目标达成再进入下一阶段：

| 阶段 | 主要动作 | 预期效果 |
|---|---|---|
| 1（1-2 周） | 把 `dimos/e2e_tests` 的 MuJoCo 用例接入 nightly CI（3.1） | 淘汰掉仿真里就能复现的逻辑错误，预计能过滤掉相当一部分"代码根本没法跑"的候选，减少无谓的真机尝试 |
| 2（并行进行） | 开始为每次真机测试录制多路证据，建回放库雏形（3.2） | 为后续离线回归打底，短期内主要是数据积累 |
| 3（2-4 周） | 部署 AprilTag 场地标记 + 复用 `fiducial` 模块做位姿测量，定义前 3-5 个高频动作的 TaskSpec（3.4.1/3.4.2） | 真机验收从"人看视频"变成"数值判定"，验收结果开始可复现 |
| 4 | 加根因分类（3.4.3）+ 安全停止条件（3.5） | 失败反馈从"没通过"变成"哪一类问题"，AI 迭代收敛速度显著提升，这是冲击两位数以上命中率的关键阶段 |
| 5 | 回放库积累到一定规模后，多数改动能在 Stage 1/2 就定型，真机基本只做"确认" | 逼近高命中率目标；98% 更现实的理解是"通过 Stage 1/2/3 的候选，在 Stage 4 的通过率"，而不是"AI 写完代码直接上真机的通过率" |

## 7. 一句话给到执行层的建议

不要把预算和精力集中在"买一台更好的相机、写一个更聪明的判定"上；相机应该是这条漏斗里**最后、也是相对最简单**的一环。真正决定能不能从 2% 冲到 98% 的，是前面三件事：（1）把已经写好但没人跑的仿真测试接进自动化；（2）把每次真机测试的证据变成可复用的离线回归资产；（3）把"通过/不通过"升级成"通过/不通过 + 结构化根因"，让 AI 拿到的反馈质量发生质变，而不是简单变快。

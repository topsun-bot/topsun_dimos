# 真机验证闭环：从"单相机人工判定"到分层硬件在环体系

> 背景问题：目前 AI 写的机器人功能，100 次里大约只有 2 次能在真机（Unitree
> 机器狗/人形）上正确跑起来；调试完全依赖人在场地里看、口述现象、AI 再改，
> 反馈慢且不可复现。有人提出"在场地外加一台独立相机，自动判断动作是否完
> 成"作为闭环的验收环节。本文分析这个方案的局限，并给出一个更系统的方案。

## 1. 问题拆解

"2/100 → 98/100"不是一个"验收更准"就能解决的问题，而是一个**漏斗**问题：

```
AI 写的功能（100）
   │ 有多少在语法/类型/接口层面就是错的？          ← 静态检查能挡住
   │ 有多少在确定性回放/仿真里就会失败？            ← 不需要真机就能挡住
   │ 有多少只在真实时序/真实执行器/真实网络下才暴露？← 需要"硬件在环"但不必真跑全场
   │ 有多少是真正的"仿真/真实差异"（sim2real gap）？← 需要真机数据反哺仿真
   └ 最终真正需要人到场地里看的，应该是极少数
```

只在漏斗最末端加一台相机，相当于在生产环境加了一个"上线后监控"，却没有单
元测试、集成测试、预发布环境。监控能告诉你"炸了"，但不能减少"炸"的次数，
也不能让 AI 更快定位"为什么炸"。这正是当前"两次成功"的原因：每一次尝试都
是从 Layer 0 直接跳到"全场真机测试"，中间没有任何更便宜、更快、更确定性
的过滤层。

## 2. 为什么"外部相机独立判定"本身也不够可靠

即使只看最后这一环，单一外部相机方案也有结构性弱点：

1. **只有"是否成功"的信号，没有"为什么失败"的信号。** 相机能看到狗摔倒了，
   看不到是关节力矩超限、IMU 姿态解算错误、LCM 消息时序错乱，还是 agent
   调用了错误的 skill 参数。AI 拿到"看起来动作没做完"这类描述，等于要重新
   从零开始诊断——这正是当前"人观察、口述、AI 再猜"慢的根本原因，换成相机
   +视觉模型描述，并没有解决"猜"的问题，只是把口述人换成了视觉模型。
2. **判定器本身需要被验证。** 用视觉模型/VLM 去判断"机器狗完成了指定动
   作"，本质上是又引入了一个会出错的 AI 模型。如果它的假阳性/假阴性率是
   10-20%（现实中很常见，尤其在遮挡、光照变化、狗的动作幅度小的场景下），
   那么整个闭环的上限就被这个判定器的准确率锁死了，无法达到 98%。
3. **单一视角，容易被遮挡/光照干扰**，且缺乏真值（ground truth）交叉验
   证——相机说"到位了"和里程计/关节编码器说"到位了"哪个可信，需要有第二
   通道去互相验证，而不是单一信号一锤定音。
4. **没有解决"何时不该让真机去试"的问题。** 相机只能在动作做完之后判断结
   果，不能在动作开始前拦截明显会失败/危险的代码——真机时间和真机磨损是
   最贵的资源，应该被最大化地保护在漏斗前端。
5. **一次真机试验的噪声很大。** 真实世界有随机性（电池电压、地面摩擦、初
   始姿态），单次"过"或"不过"不能代表这个功能的真实成功率。如果只做一次
   相机判定就决定"进入可合并状态"，很容易把一个实际成功率只有 30% 的功能
   误判为"能用"，这也是导致"看起来能过但真正稳定可用的极少"的原因之一。

这不是说相机没用——第 4 层里相机仍然是重要的信号源，但它应该是**多通道**
判定里的一路，而不是唯一裁判。

## 3. 核心原则：先建立"你信任的自验证闭环"，再谈自动化规模

这与团队在软件工程里从"逐行看 AI 代码"走向"多 agent 并行/自主运行"的路径
是同一个逻辑（对照 Boris Cherny 的 AI 应用成熟度阶梯：Step 1→2 的解锁条
件明确写的是"a self-verification loop you trust（tests + build + lint +
e2e）"，Step 2→3 才是"break work into loops/routines，让 Claude 自己触
发 Claude"）。软件工程里能做到"AI 写完直接合并"，前提从来不是"人看得更
快了"，而是"有一套自动化验证，团队真正信任它的判断"。

机器人闭环也一样：不能指望"用相机自动化人工验收"就跳过建立信任的过程。
正确顺序是：

1. 先在**仿真**里建立一个高置信度、可重复、能跑几百次的自验证层（Layer
   2），把它当成"tests + build + lint"；
2. 再在**受限硬件**（台架/绳索/护栏）上验证"仿真过了在真实执行器上是否
   也过"（Layer 3），把它当成"e2e in a real dev environment"；
3. 最后才是**全场自由测试**（Layer 4），这时候相机+人工巡场的介入频率应
   该已经从"每次改动都要看"降到"抽检/异常复核"。

跳过 1、2 直接做 4，就是"没有自验证闭环就想开自动模式"——软件工程里这样
做的后果是允许 AI 无监督乱跑，机器人场景里后果是摔坏硬件、调试更慢。

## 4. 方案：五层漏斗式硬件在环（HIL）验证管线

| 层级 | 内容 | 目的 | 本仓库现有基础 |
|---|---|---|---|
| L0 静态检查 | ruff/mypy、`@skill` schema 校验、blueprint 注册测试 | 挡住语法/接口错误，秒级反馈 | `pytest dimos/robot/test_all_blueprints_generation.py`、pre-commit |
| L1 确定性回放 | 用录制的 LCM bag（`dimos --replay`）跑一遍 | 挡住逻辑错误，无需硬件/仿真进程，最快 | `--replay` 模式、`~/.local/state/dimos/runs/<run-id>/main.jsonl` |
| L2 仿真 + 域随机化 + 多次试验 | MuJoCo/dimsim，随机化摩擦力、质量、延迟、传感器噪声，每个场景跑 N 次统计成功率 | 挡住绝大多数 sim2real 差异；把"能不能跑"变成"稳定成功率是多少" | `dimos/e2e_tests`（`test_dimsim_walk_forward.py` 等）、`DimSimClient`、`lcm_spy.wait_until_odom_position(...)`（已经是**遥测判定**，不是看图判定） |
| L3 受限硬件在环 | 真实执行器，但物理约束（吊架/低速/护栏），采集全量结构化遥测（关节力矩、电流、IMU、电量、LCM 全 topic dump、agent 工具调用轨迹） | 挡住"只有真实执行器/真实时序才暴露"的问题，同时把风险控制在可接受范围 | `dimos log --json`、run registry、Rerun 可视化桥 |
| L4 全场自由测试 | 真实场地，外部相机 + 车载感知 + 遥测，**双通道**自动判定 | 最终验收，覆盖真正需要开放环境的场景 | 用户提议的"外部相机" + `dimos/perception`（物体检测/跟踪）+ 已有的 odom/goal_reached 遥测 |

每一层都是"更贵、更慢、噪声更大"，只有通过上一层才进入下一层——这样真机
时间只花在"值得花"的候选功能上，而不是每次改动都直接烧真机。

关键设计点：

- **L2 不是跑一次，而是跑 N 次并统计成功率**，且每次随机化初始条件（起始
  位姿、目标距离、噪声种子）。行业里公认的经验是：大多数"仿真过、真机
  不过"的问题（时序竞态、传感器噪声敏感、执行器饱和、边界条件）在**域随机
  化的仿真里已经能被复现**，根本不需要真机就能发现。这是把成功率从 2%
  拉起来投入产出比最高的一层，应该优先建。
- **L3 是当前完全缺失、但性价比很高的一层**：不需要开放场地，只需要一个
  安全带/吊架或护栏，就能在真实执行器上跑，同时不用一个人全程盯着看是否
  会摔倒——这一层能把"只有真机才暴露"的问题在低风险条件下筛出来，减少
  L4 的失败次数（也就减少了需要人到场地观察的次数）。

## 5. 判定机制：双通道交叉验证，而不是单一视觉判断

不要让"外部相机看起来像不像完成了"独自决定 pass/fail。每个功能在开发时
就应同时定义**结构化验收标准**（而不是自然语言描述"应该完成什么动作"），
例如：

- 里程计/关节编码器读数：终点位姿与目标位姿误差 < 阈值，用时 < T
- IMU：过程中姿态角未超过阈值（没有摔倒/侧翻）
- 力矩/电流：未触发过载保护
- 外部相机 + 物体检测（复用 `dimos/perception`）：机器人可见位置与遥测
  位置一致（互相佐证，而不是相机单独定论）

判定 = 遥测通道通过 **AND** 视觉通道无异常。两个通道分歧时，本身就是一个
高价值信号（说明传感器/建图/定位可能有问题），应该单独归类而不是简单地
"以相机为准"。这样才能把整体判定的假阳性/假阴性率压下来，逼近 98% 这个
目标所需要的可信度。

这套"遥测优先、视觉佐证"的模式在仓库里已经有雏形——`dimos/e2e_tests` 里
的 `lcm_spy.wait_until_odom_position` / `wait_for_message_result` 就是
用遥测（odom、goal_reached topic）做确定性断言，而不是靠人或视觉模型看
图。应该把这套模式从仿真延伸到 L3/L4，而不是在 L4 另起一套"纯视觉判定"。

## 6. 失败反馈：结构化证据包 + 确定性复现，而不是"人转述现象"

当前最慢的环节是"人观察 → 口头描述给 AI → AI 猜测原因 → 改代码 → 再跑"。
即使把"人观察"换成"相机+视觉模型描述"，本质上还是同一个慢循环——因为
AI 拿到的仍然是一段"看起来失败了"的转述，不是可复现、可调试的数据。

更好的做法：每次 L3/L4 失败时，自动打包一份**失败证据包**，包含：

- 时间同步的相机片段
- 该次运行的完整结构化日志（`main.jsonl`，已有）
- 全量 LCM topic 录制（可直接喂给 `dimos --replay` 在本地/仿真里**确定
  性复现**同一次失败，不需要真机在场）
- agent 的工具调用轨迹（调用了哪些 skill、参数是什么、返回了什么）
- 本次改动的 diff

拿到这份证据包后，AI 的第一步应该是 `dimos --replay` 复现，而不是靠相
机描述去猜。这样绝大多数诊断-修改-验证的迭代可以完全脱离真机和人工在场，
只有确认修复后才需要再申请一次真机时间做确认——这才是真正把"调试速度慢"
这个问题解决掉，而不是把"人观察"换成"AI 观察"却保留同样的循环结构。

## 7. 统计学严谨性：N 次试验，而不是一次通过/失败

真机测试天然有噪声。建议：

- L2 仿真阶段：每个场景至少跑 N（如 20-50）次随机化试验，要求成功率
  ≥ 某阈值（例如 90%）才允许进入 L3。
- L3/L4 阶段：真机试验次数少但更贵，用序贯检验（例如"连续 3 次成功才
  算稳定通过""连续 2 次失败暂停并升级"）而不是单次判定，避免"蒙对一次
  就合并"或"蒙错一次就打回"。
- 把"稳定复现率"本身作为可追踪的指标记录下来（哪怕是 30% 成功率也先记
  录、可对比），而不是只记录二元的过/不过——这样才能看到方案改进是否真
  的在提升成功率，也能提前识别哪些功能是"看似能跑但极不稳定"，这类功能
  目前很可能正是"2/100"里那 2 次的真实情况：不是"稳定能用"，而是"蒙对
  了一次"。

## 8. 安全与失败停止机制

在提出的方案基础上明确化、具体化：

- **物理急停**：护栏内常驻一个可被软件和人共同触发的急停开关。
- **软件看门狗**：基于关节力矩/电流/IMU 姿态实时检测异常（过载、跌倒趋
  势），先于相机判定触发停止，防止损坏硬件。
- **连续失败自动升级人类**：例如连续 2-3 次 L3/L4 失败（尤其是同一类
  安全触发），自动暂停该功能的自动重试，把证据包和诊断摘要推送给人，而
  不是无限重试消耗真机寿命。这与用户原方案里"触发安全/失败停止条件"的
  意图一致，这里给出了具体的触发口径。

## 9. 在本仓库中的落地建议

- `ai_longrun_harness/run_to_main.sh` 当前直接调用一个尚不存在的
  `run_multi_agent_loop.sh`，且 `run_pr_pipeline.sh` 在推送/建 PR 前**没
  有任何验证门禁**。建议在两者之间插入一个 `run_sim_gate.sh`：跑
  `dimos/e2e_tests` 里带 `@pytest.mark.dimsim` / `mujoco` 的用例（域随
  机化、重复 N 次），不达标直接阻断，不进入 PR 流程。这是最小改动、最高
  杠杆的第一步。
- 扩展 `dimos/e2e_tests` 现有测试（如 `test_dimsim_walk_forward.py`）为
  参数化/多次试验版本，复用 `docs/development/grid_testing.md` 里已有的
  `Case` + `parametrize` 模式，对起始位姿、噪声、延迟做随机化覆盖。
  这一步不需要新基建，只是把现有单次场景测试改造成统计性测试。
- L3（受限硬件在环）目前完全没有对应设施/脚本，是当前链条里最大的空
  白，也是相对场地相机方案而言更值得优先投入的一步。
- L4 的相机判定，建议直接复用 `dimos/perception` 的检测/跟踪能力做机器
  人位置识别，与里程计做交叉验证，而不是新建一套独立的纯视觉"动作是否
  完成"判断逻辑。
- 失败证据包可以直接基于已有的 run registry（`~/.local/state/dimos/runs`）
  和 `dimos log --json` 产出，加一层"打包 + 关联相机片段"的脚本即可，
  不需要从零设计日志系统。

## 10. 分阶段路线图

1. **第一阶段（本仓库可立即做）**：给 `run_pr_pipeline.sh` 加 L0+L1 门
   禁（现状：完全没有）；把现有 dimsim/mujoco 用例改造为多次随机化试验，
   记录成功率而非二元结果。预期效果：过滤掉相当一部分"根本不该拿去真机
   试"的功能，减少真机失败次数，但不直接提升"到真机这一步"的成功率。
2. **第二阶段**：搭建 L3 受限硬件在环（吊架/护栏 + 结构化遥测采集），
   在真实执行器但可控风险下验证。预期效果：显著减少"只有真实硬件才暴露"
   的失败进入开放场地测试。
3. **第三阶段**：L4 场地相机 + 遥测双通道判定 + 结构化失败证据包 +
   `dimos --replay` 确定性复现闭环。预期效果：即使真机失败，诊断-修复
   周期也能大幅缩短，且不再需要人全程在场描述现象。
4. **第四阶段**：统计口径全面切换为"N 次试验成功率"而非二元通过/失败，
   建立每个功能/技能的历史成功率追踪，用于识别"蒙对一次"和"真正稳定"
   的区别。

98/100 不是靠某一层单点补强能达到的目标，而是漏斗层层过滤 + 判定可信 +
反馈可复现三者共同作用的结果。相机是第四层里的一路信号，而不是整个方案。

## 11. 一句话总结

不要用一台相机去"自动化人工验收"，而要先在仿真里建立一个多次试验、你真
正信任的自验证闭环，再用受限硬件在环把"只有真实执行器才暴露"的问题挡在
开放场地测试之前；到了最后的真机验收阶段，用遥测和视觉双通道交叉判定、
并把失败打包成可确定性复现的证据交给 AI，而不是让人转述、让相机单独裁判。

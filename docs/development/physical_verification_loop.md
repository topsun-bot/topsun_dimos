# 从"2/100"到"98/100"：AI 生成代码在真机上可靠运行的闭环设计

## 1. 问题重新定义

现在的构想是："在调试场地外加一台独立相机，自动判断机器狗是否完成指定动作；达标则代码进入可合并状态，不达标则把失败证据交给 AI 继续修改。"

这个方向是对的（引入独立于 AI 自身的物理世界观察者），但**单靠一台相机 + 一次真机试跑，不可能把成功率从 2% 顶到 98%**。原因不是相机不够好，而是这个设计只有"一层验证、一次试验"，而真实的物理可靠性问题需要的是**分层验证 + 多次统计验证**。类比 Boris Cherny 那张 AI 落地阶梯表：你们现在实际所处的位置是 **Step 1（Assisted，一人一狗，人工观察、口头描述失败）**，而"外部相机+反馈"这个方案本质上只是把 Step 1 里"人工观察"这一步自动化了——这是必要的一步，但表里从 Step 1 到 Step 2/3 真正的解锁条件是：

> "a self-verification loop you trust (tests + build + lint + e2e testing with a real dev environment)"

对普通软件来说，这一层是**便宜、确定性、可并行**的（单元测试几秒钟出结果）。对具身机器人来说，"自我验证"天然是**昂贵、随机、有物理风险**的（一次真机试跑几十秒到几分钟，狗可能摔、可能撞、电池会耗尽，人还要在场保安全）。如果把这套"tests + build + lint + e2e"的角色，全部压到"一台相机看一次真机试跑"上，就会出现现在的情况：反馈慢、噪声大、样本量不够，2/100 里那 2 次成功也说明不了这是一个 98% 成功率的技能，只能说明"至少发生过一次"。

**核心结论：要达到 98/100，目标不能是"让相机能判断对错"，而是要建一条从便宜到昂贵、从确定性到统计性的多级验证流水线，让真机试跑只用来验证"已经在更便宜的层级上大概率会成功"的候选代码，并且用统计量而不是单次结果来定义"合格"。**

---

## 2. 为什么"单相机 + 单次试跑"结构性地做不到 98%

1. **判官本身不可靠**：视觉判断"狗是否完成了指定动作"通常要靠一个 VLM/规则去看视频判 pass/fail。这个判官自己就有误判率。AI 执行者的错误率和判官的错误率是两个独立的随机变量，叠加之后系统的有效准确率只会更低，不会因为"加了个判官"就自动变高。仓库里 `dimos/perception/fiducial/fixture_verification.py` 其实已经给出了一个更可靠的模式的雏形——不是"一个模糊的是/否"，而是**结构化、可解释、多指标的 accept/reject + reject_reasons**（标签面积占比、清晰度、几何误差分位数……）。任务完成判官也应该做成这样，而不是一句"VLM 说过了"。
2. **大多数失败根本不是"高层意图错了"**：真机上失败的主因往往是步态/平衡、sim-to-real gap、时序/竞态、执行器限位、网络时延、电量、地面摩擦差异——这些是相机在几米外拍一段视频**很难定位到代码哪一行**的。相机能回答"任务完不完成"，回答不了"为什么"。
3. **真机试验太贵，样本量注定小**：100 次真机试跑意味着 100 次人工在场、100 次电池循环、100 次摔倒风险。要在这个预算下把置信区间做窄，几乎不可能——你们现在"2/100"能观察到的信息量本身就很有限，不足以指导修改方向。
4. **没有回归防护**：现在的闭环是"失败→改代码→再试"，没有机制保证"改好了 A 没有悄悄弄坏 B"。成功率因此很容易原地打转甚至倒退。
5. **反馈格式是自然语言复述**：人工描述"狗歪了一下就倒了"这种反馈信息密度低、不可复现、不可编程化处理，AI 很难从中定位根因。

---

## 3. 分层验证架构

把现有构想（相机 + 反馈）作为**最后一层**，前面补三层更便宜的过滤器，让到达真机层的候选代码本身就已经大概率是对的。仓库里已经有可以直接复用的基础设施，标注在括号里。

```
L0  静态/契约门禁      —— 秒级，零物理风险
L1  仿真批量试验        —— 分钟级，零物理风险    (dimos/simulation/dimsim, mujoco)
L2  真机金丝雀 + 多信号验证 —— 分钟级，小风险        (相机 + 遥测 + 独立安全监控)
L3  统计门禁            —— 用置信区间而不是单次结果判断"合格"
L4  结构化失败回传        —— 让 AI 拿到可定位根因的证据包，而不是一句话描述
L5  回归语料库           —— 每个修好的真实失败案例永久变成仿真回归用例
L6  接入 ai_longrun_harness / CI 门禁 —— 把 L1~L3 变成"可合并"的硬性前置条件
```

### L0 静态/契约门禁（秒级）
- 复用 `@skill` 装饰器已经强制的 schema 规则（docstring、类型标注、返回值）——这是现成的"编译期"检查，直接跑 `pytest dimos/robot/test_all_blueprints_generation.py` 之类的门禁即可，不需要新建。
- 新增一层"安全包络"静态检查：对生成代码里出现的速度/角度/力矩等参数做范围校验（比对 `dimos/hardware/*` 里的执行器限位常量），拒绝明显超限的调用——这一层可以挡掉相当一部分"根本不该跑到真机上"的候选。
- 目标：把明显不合法的代码在真机之前、甚至仿真之前就挡掉，零成本。

### L1 仿真批量试验（分钟级、零物理风险）—— 最关键的新增层
这是目前方案里**缺失、也是最能提高成功率的一环**。仓库已经有 `dimos/simulation/dimsim` 和 `dimos/simulation/mujoco` 这套 sim 引擎，`docs/development/testing.md` 里也已经区分了 fast/self-hosted/mujoco 测试标记，但目前主要用于功能测试，没有用来做**统计意义上的成功率评估**。建议：

- 对每一个新的/改动过的 skill 或 task，在仿真里跑 **N 次（建议 N≥20）**，并且每次做**域随机化**（摩擦系数、质量、传感器噪声、指令延迟抖动、初始姿态微扰），而不是完全相同的确定性场景。
- **判官只写一套**：用同一个"任务完成判定器"的接口，仿真里喂的是仿真相机/位姿流，真机里喂的是外部相机+遥测。这样避免"仿真判官"和"真机判官"标准不一致的问题，也让判官逻辑本身能在仿真里被高频、低成本地测试和迭代。
- 只有仿真通过率达到阈值（比如 ≥90%）的候选代码，才允许申请真机试跑名额。这一步能把"根本跑不动"的代码在真机之前刷掉，大幅减少真机浪费的次数，也是从"2/100"提高到"多次通过仿真、少数几次真机验证"的关键杠杆。

### L2 真机金丝雀 + 多信号验证（不要只信相机）
- **外部相机**：判断任务级别的完成情况（"走到目标点/叼起物体/坐下"），这是原方案里已经有的部分，保留。
- **机载遥测融合**：IMU、关节电流、足端接触、电池电压——很多"差点摔倒但相机角度没拍全"或者"看起来做完了但关节其实在打滑"的情况，遥测比视觉更可靠、延迟更低、噪声特性也不同。两路信号交叉验证，比单一相机判官可信得多。
- **独立安全看门狗**：倾角/电流超限触发的急停逻辑必须和"任务是否完成"的判官**物理上解耦**——判官出错不能影响安全停止，安全停止的规则要足够简单、确定性强（不依赖 LLM），可以参考 `dimos/experimental/security_demo` 里已有的模式。
- 真机试跑的目的不再是"从零开始判断行不行"，而是"验证仿真层给出的高成功率估计在真实物理世界里是否依然成立"（sim-to-real gap 检测）——所以真机上不需要 100 次去试出 98 次，通常 5~10 次金丝雀试验就足够验证仿真估计是否可信。

### L3 统计门禁（用置信区间定义"合格"，而不是"跑成功了一次"）
- 明确把目标定义成一个**成功率 SLA**，例如"该任务在真机上的成功率下界（Wilson score 95% 置信区间下界）≥ 0.9"，而不是"跑成功了就行"。
- 每个任务/技能维护一个滚动试验记录（仿真 + 真机分开记录，真机权重更高），"可合并"状态由这个统计量驱动，而不是由最近一次试跑的 pass/fail 驱动。
- 好处：直接回答了你提的目标——"100 次里 98 次成功"本身就是统计声明，必须靠统计方法而不是单次观察来验证。

### L4 结构化失败回传（把"人工描述现象"替换成证据包）
失败时自动打包，而不是等人去看再转述给 AI：
- 时间戳对齐的视频片段（相机）+ 遥测曲线（IMU/关节/电流/电量/网络延迟）
- 判官给出的失败原因（仿照 `fixture_verification.py` 的 `reject_reasons` 结构，给出可枚举的失败标签，而不是自然语言吐槽）
- 失败分类taxonomy，建议至少区分：
  - 感知误判（判官/视觉本身的问题）
  - 规划/几何错误（路径、目标点计算错）
  - 执行/步态失败（更可能是控制参数或硬件问题，不该无脑丢给"改 Python 代码"的 AI 循环）
  - 时序/竞态（模块间同步问题）
  - 硬件故障（电量、通讯丢包、电机报错）
  - 环境失配（仿真没建模到的真实地面/光照差异）
  - 安全停止触发
- 这个分类直接决定"要不要继续让 AI 改代码"：比如"执行/步态失败"很可能是底层 SDK/固件调参问题，AI 在 Python 层反复改代码是在做无用功，应该路由给人或者标记为"需要硬件排查"，而不是无限重试消耗真机资源。

### L5 回归语料库（防止成功率反复横跳）
- 每一次被确认的真机失败，把当时的状态/参数录制下来，转成一个可在仿真里重放的回归用例，加入 `dimos/e2e_tests` 或 dimsim 的用例集。
- 修复后，这个用例必须长期留在自动化套件里跑——防止"修好 A 又在下一次改动里悄悄坏了 A"，这是让成功率能够**单调爬升**而不是原地震荡的关键机制。

### L6 接入 `ai_longrun_harness` / CI，作为硬性合并门禁
仓库里的 `ai_longrun_harness/run_to_main.sh` 目前只是"跑 multi-agent 循环 → push → 建 PR"的骨架（`run_multi_agent_loop.sh` 甚至还未实现），也没有任何物理验证门禁。建议把 L1（仿真批量试验通过率）和 L3（统计门禁）接到这条流水线里，作为 `run_pr_pipeline.sh` 之前的强制前置步骤：仿真不达标 → 直接打回 AI 继续改，不占用真机；仿真达标但真机金丝雀不达标 → 生成 L4 证据包回传给 AI；两者都达标 → 才允许进入 PR 流程。这样"可合并"这个状态就有了机器可验证的定义，而不是"人观察后主观觉得行了"。

## 4. 分阶段推进（对应 Boris Cherny 表格里的阶梯，落到物理机器人上）

| 阶段 | 状态 | 解锁条件 |
|---|---|---|
| 现在 | Step 1：一人一狗，人工观察复述失败，2/100 | — |
| 阶段 A | 相机独立观察 + 结构化失败回传（L4）替代人工复述 | 先把"人工描述"自动化，但暂不指望成功率大幅提升——这一步的价值是让失败可复现、可分类，为后面的层打基础 |
| 阶段 B | 接入仿真批量试验（L1）+ 域随机化 | 这是成功率提升的主要来源：把大部分候选代码在真机之前刷掉 |
| 阶段 C | 真机金丝雀 + 多信号融合（L2）+ 统计门禁（L3） | 用少量真机试验验证仿真估计，用置信区间定义"合格"而不是单次通过 |
| 阶段 D | 回归语料库（L5）+ 接入 CI 强制门禁（L6） | 防止成功率反复横跳，"可合并"变成机器可判定的状态 |

不建议把"造一台外部相机+人工看反馈"直接当终态方案去优化——它更适合放在阶段 A，先把反馈自动化、结构化，同时尽快启动阶段 B（仿真批量试验），因为**仿真层才是能大批量、低成本地把"2/100"里那 98 次失败提前挡掉的地方**；真机相机验证是最后一道确认，不是主战场。

## 5. 具体的下一步（建议按此顺序动手）

1. 给现有 e2e 测试（`dimos/e2e_tests/test_*.py`）里已经用到 dimsim 的用例，加上域随机化和重复 N 次跑的能力，先把"仿真成功率"这个数字产出来，哪怕判官还很简陋。
2. 设计一个通用的"任务完成判官"接口（`TaskVerifier`：输入 = 相机帧/遥测流，输出 = accepted/reject_reasons，参考 `fixture_verification.py` 的结构），先在仿真里跑，验证判官本身的准确率，再考虑接真实相机。
3. 定义每个 skill/task 的成功率 SLA 和判官验收标准，写成配置而不是散落在 prompt 里。
4. 把 L4 的结构化失败证据包格式定下来（哪怕先是一个 JSON schema + 一段视频路径),让"失败反馈给 AI"这件事从"人转述"变成"程序生成"。
5. 最后再接硬件金丝雀和 CI 门禁（L2/L3/L6），这时候真机试验次数已经因为前面几层的过滤大幅减少，才谈得上把成功率往 98% 推。

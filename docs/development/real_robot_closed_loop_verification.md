# 真机闭环验证：从"外部相机裁判"到可审计的分级验收系统

> 背景问题：AI 写的机器人控制代码在仿真/编译阶段能通过，但部署到宇树机器狗真机后经常跑不起来；每次失败都要靠人在场地观察、口头描述现象，再回来改代码，反馈慢且不结构化。目标是把"AI 写代码 → 真机运行 → 验收 → 失败反馈 → 继续修改"变成一个可重复、可审计、可安全停止的闭环，并把**真机首次成功率从当前约 2% 提升到接近 98%**。

## 1. 先给"独立外部相机裁判"方案的诊断

在场地外加一台相机、自动判断动作是否完成，方向是对的——它解决了"人工肉眼判断、口述反馈"这个最慢的环节。但**单独**这一个组件不足以把成功率从 2% 提到 98%，原因是：

1. **单点观察，信息量太低。** 相机只给"完成/没完成"，AI 拿到的反馈约等于 1 bit。上真机跑一次的代价（电池、机械磨损、人工看护、排队时间）很高，而反馈信息这么少，AI 只能靠猜测下一步改哪里，收敛速度必然慢。当前 2/100 的成功率里，可能相当一部分失败根本不是"这段代码逻辑错了"，而是标定漂移、时序/延迟、安全阈值触发、无线丢包、电量不足等和这次代码改动无关的因素——纯粘度判定分不清这些。
2. **单相机有遮挡盲区和视角误差**，尤其四足在复杂姿态/翻越障碍时，单一外部视角容易误判"失败"。
3. **真实世界是有噪声的随机过程**（地面摩擦、电池电压、Wi-Fi 延迟波动），单次真机试验的成功/失败本身就有方差。只跑一次就下结论，会把"这次运气不好"和"代码真的有 bug"混为一谈，AI 可能会去"修复"一个根本不存在的 bug。
4. **没有分级、每次改动都要上真机**，等于把最贵、最慢、最有风险的验证手段当成唯一的验证手段，真机资源被大量消耗在本可以用仿真拦截的低级错误上。
5. **没有安全熔断的定义**，闭环一旦自动化运行，缺少"必须立刻停止"的硬性条件（摔倒、关节力矩超限、姿态角超限、超出场地边界），存在损坏机器人或发生危险的风险；也没有"连续失败 N 次就升级给人"的机制，闭环可能空转浪费真机资源而不自知。
6. **不可审计。** 只有相机一次性判定的话，事后无法复盘"当时到底发生了什么、AI 依据什么改的代码、改动是否真的针对性解决了问题"。

**核心结论：瓶颈不是"有没有裁判"，而是①每次真机失败能提取多少比特的诊断信息，②有多少失败原本不需要上真机就能被拦截，③如何用统计而不是单次判定来消除物理世界的随机噪声，④明确的安全边界。** 外部相机应该是这个系统里的一个信号源，而不是整个方案。

## 2. 更好的方案：Shift-Left 分级门禁 + 多信号验收 + 根因反馈

### 2.1 总体结构：证据金字塔（越往上越贵，只有通过下一级才准入）

```
Gate 0  静态检查      lint / type check / 单元测试(pytest)          秒级，任何改动都跑
Gate 1  仿真回归      Isaac Sim 重放"历史真实故障场景库"              分钟级，本地/CI跑
Gate 2  台架/低风险    吊起或小范围围栏内，只测运动学与安全边界        真机但低风险、低成本
Gate 3  全场地真机验收  多相机 + 车载遥测 + VLM 结构化裁判 + 重复N次    真机，最贵，最终验收
```

每一级失败都**就地短路**，不进入下一级；只有失败原因被自动归类清楚，才把结构化诊断信息还给 AI 继续改代码。这样可以把大量"根本不该上真机"的错误挡在 Gate 0/1，真机资源集中花在真正需要物理世界验证的问题上。

- **Gate 1 是当前系统里缺失但杠杆最大的一环。** 仓库里已经有 `dimos/simulation/isaac`（Isaac Sim 接入）。建议维护一个"历史真实失败场景库"：每次真机 Gate 2/3 失败，把当时的任务描述、初始状态、传感器输入录制下来，转成一个可在 Isaac Sim 里重放的回归用例，永久加入回归库。以后任何代码改动，先在 sim 里把所有历史失败场景重放一遍，通不过的直接打回，不许上真机。这一步能直接、持续地把"已知会在真机翻车的错误"挡在门外，是从 2% 提升到两位数成功率最快的一步，而且几乎不消耗真机资源。
- **Gate 2 台架验证**：机器狗吊起或在小范围安全围栏内，只验证"关节轨迹合理、不会撞地/撞人、姿态稳定"，不要求完成完整任务。这一级成本低、频率可以很高，专门用来拦截"会导致真实摔倒/损坏"的代码，避免把这类错误留到 Gate 3 才发现。
- **Gate 3** 才是原方案里说的"外部相机 + 全场地"验收，但要做以下几点结构性增强（见 2.2、2.3、2.4）。

### 2.2 多信号融合验收，而不是单相机判"过/不过"

同一次真机运行，时间同步地采集：

- **多台外部相机**（不止一台，覆盖机器狗四周，消除单视角遮挡盲区）；
- **车载相机/雷达**（机器狗自身视角，仓库里 `dimos/perception/detection` 已有检测能力可以复用）；
- **本体遥测**：关节编码器、IMU 姿态、关节力矩、电池电压、指令 cmd_vel、pubsub 上的全部 topic —— 仓库里 `dimos/robot/unitree/g1/g1_rerun.py` 已经在用 [rerun](https://rerun.io) 记录可视化数据，直接复用这个习惯，把外部相机视频和车载遥测**在同一条 rerun 时间线上对齐**，而不是分开存。

有了同步的多路数据，"失败"不再是相机给的一个孤立布尔值，而是一份可以逐帧回放、可以看到"关节在第几秒开始偏离预期轨迹"的完整记录。

### 2.3 VLM 结构化裁判，取代"简单动作检测"

仓库里已经有 `dimos/agents/vlm_agent.py`（`VLMAgent` 模块，接收 `Image` 流、输出 `AIMessage`，走 langchain `init_chat_model`，已支持多种模型后端）。建议在此基础上做一个 **AcceptanceJudge**：

- 输入不是"帮我看这个视频完成没完成"这种模糊问题，而是一份**结构化验收 rubric**（针对每个任务预先定义的检查项列表，例如"机器狗躯干在 5 秒内到达目标坐标 ±0.3m 范围内"、"过程中没有跌倒"、"没有触碰围栏"）；
- 输出也是结构化 JSON：每条 rubric 的 pass/fail + 置信度 + 依据的关键帧时间戳，而不是一个笼统的"通过/失败"。
- 这样即使最终判定是失败，AI 也能拿到"具体哪一条验收标准没过、大概发生在第几秒"，而不是从头猜。

### 2.4 根因分类，而不是"失败"两个字

把每次 Gate 2/3 的失败，结合遥测自动打上根因标签，再连同 rubric 判定一起喂给 AI，例如：

- `CODE_LOGIC` —— 控制逻辑/规划算法本身有错（这是唯一真正需要 AI 改代码的一类）
- `TIMING_LATENCY` —— 指令延迟、控制频率不够
- `CALIBRATION_DRIFT` —— 坐标系/标定漂移
- `HARDWARE_FAULT` —— 电量、电机、传感器异常
- `ENV_NOISE` —— 地面摩擦、光照、Wi-Fi 波动等环境噪声
- `SAFETY_STOP` —— 触发了安全熔断（见 2.5），不是任务失败
- `FLAKY` —— 重复多次里偶发失败，统计上不稳定

区分出这些类别之后，反馈给 AI 的不再是"没通过，请再试"，而是"这次失败 78% 概率属于 `TIMING_LATENCY`，参考历史上 3 次同类修复分别改了 XX 模块的控制频率参数"——这才是能真正指导 AI 改代码、把成功率往上提的信息密度。只有 `CODE_LOGIC` 类才应该触发"重新生成代码"，其余类别应该路由给不同的处理（重新标定、检查硬件、加大安全边界等），不要一律丢回给 AI 重写代码。

### 2.5 安全熔断（必须独立于任务判定之外）

明确定义一组"必须立即停止，且不算作可通过 AI 改代码解决的任务失败"的硬性条件，例如：

- IMU 姿态角超过阈值（判定为摔倒/失控）
- 关节力矩/温度超限
- 超出场地地理围栏
- 相机追踪丢失超过 N 秒（观察者本身失效，不能盲跑）

触发以上任一条件：立刻停止机器人动作，标记为 `SAFETY_STOP`，**不计入失败次数、不自动重试**，直接暂停整个自动循环并通知人工。同时应设置"连续 N 次同一根因失败自动升级给人工"的兜底，防止闭环在错误方向上空转、无意义地消耗真机寿命。

### 2.6 统计门禁，消除物理世界随机性

真机验收不应该"跑一次过了就合并"。建议同一任务重复运行 3~5 次，统计通过率和置信区间：

- 全部通过 → 进入待合并状态；
- 全部失败且根因一致 → 明确是 `CODE_LOGIC`，打回 AI 改代码；
- 部分通过 → 标记 `FLAKY`，不合并，但也不是简单打回重写代码，而是提示"结果不稳定，可能需要增加鲁棒性余量"这一类不同的修改方向。

这一步直接对应"98/100"这个目标里最容易被忽略的一点，见第 4 节。

## 3. 落地建议（贴合本仓库现有资产，不是另起炉灶）

| 需要的能力 | 复用仓库里已有的东西 |
|---|---|
| 时间同步记录视频+遥测 | `g1_rerun.py` 里已经在用的 rerun 记录方式，扩展到把外部相机也接入同一条 timeline |
| 仿真回归（Gate 1） | `dimos/simulation/isaac`（Isaac Sim 接入）+ 历史失败场景重放库（需新建） |
| 视觉裁判 | `dimos/agents/vlm_agent.py` 的 `VLMAgent`（Module + `In[Image]`/`Out` stream 模式），扩展成结构化 rubric 判定 |
| 车载感知 | `dimos/perception/detection` 现有检测能力 |
| 任务/动作的定义方式 | `dimos/skills/skills.py` 的 `SkillLibrary`——每个"指定动作"本来就是一个 Skill，建议给每个 Skill 附带一份验收 rubric，形成任务库 |
| CI/自动化编排 | `ai_longrun_harness/` 已有的多 agent + PR pipeline 脚本，可以在其中插入 Gate 0/1 作为前置步骤 |

本次改动里，我先落地了这个方案里最基础、后续所有 Gate 都要依赖的一层——**统一的数据契约**（`dimos/verification/schema.py`）：`RunManifest`（每次验证运行的完整记录：代码版本、任务/rubric、各 Gate 结果、产出的媒体与遥测引用）、`VerificationVerdict`（结构化裁判结果）、`RubricItem`、`FailureCategory`（根因分类枚举）、`SafetyStopReason`。有了这层契约，Gate 1/2/3 的具体实现（Isaac Sim 回归、rerun 记录整合、VLM 裁判)可以逐步接入，而不需要事后重构数据格式；同时它本身就是"可审计"要求的具体体现——任何一次真机运行都能序列化成一份完整、结构化、可长期存档复盘的记录。

## 4. 路线图，以及对"98/100"目标的一个重要澄清

分四个阶段推进，每个阶段解决当前系统里杠杆最大的短板：

1. **阶段一·先诊断再自动化**：只上"多信号同步记录"（2.2）+ 人工看结构化证据打根因标签，暂不自动化闭环。目的是先搞清楚现在这 2/100 里，失败到底有多少是 `CODE_LOGIC`、多少是标定/时序/安全阈值——这决定了后面该把力气花在改代码能力上，还是花在环境/硬件稳定性上。
2. **阶段二·Shift-left**：上线 Gate 1 仿真回归（历史失败场景重放），把能在 sim 拦住的错误挡在真机之外，真机尝试次数会大幅下降，但真机首次成功率会明显上升。
3. **阶段三·自动裁判 + 根因分类**：上线 VLM 结构化裁判（2.3）和自动根因分类（2.4），形成自动反馈闭环；但低置信度或连续失败的 case 仍升级人工复核，不要一步到位全自动。
4. **阶段四·统计门禁 + 安全熔断上线**：多次重复验收（2.6）+ 安全熔断（2.5）全部启用，闭环基本自动运行，只在 `SAFETY_STOP` 或连续失败超过阈值时升级人工。

**关于目标数字的建议**：把"98/100"理解为"物理世界里单次真机尝试的即时成功率"是一个几乎不可能达到的标准——即使是成熟的工业机器人系统，复杂长时任务的单次物理成功率也很少稳定在 95%+ 以上，因为物理世界的随机性是无法被"改对代码"消除的。建议把目标拆成三个更现实、也更能指导优先级的指标，而不是一个单一数字：

- **仿真门禁通过率**（Gate 1）：这个可以、也应该逼近 98%——因为这一步已经排除了物理随机性，纯粹是逻辑正确性问题。
- **真机首次尝试成功率**（Gate 3 单次）：目标从 2% 提升到远高于现在的水平（比如中期 50~70%）比直接对标 98% 更现实。
- **真机 3 次尝试内收敛成功率**：即"最多重试 3 次里至少 1 次成功"的概率，这个指标可以合理地设定在 90%+ 甚至更高，因为它同时允许闭环利用统计重试来吸收物理随机性,也是最终对人类来说真正有意义的"这个任务能不能用"的指标。

用这三个分层指标做 KPI，比用一个单一的"98/100"更能反映系统真实的改进方向，也能防止团队为了凑一个不现实的单一数字而做表演式优化（比如把验收标准放水、或者只挑简单任务跑分）。
